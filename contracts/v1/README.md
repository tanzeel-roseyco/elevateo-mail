# Version 1 session and read contract

`openapi.json` is the canonical machine-readable source for FE-01's four reads and the accepted BE-02A session lifecycle. Version `1.0.0-session.1` preserves every existing read operation and schema, and adds nine lifecycle/organization routes. Two fresh disposable Docker runs of the pinned generator produced identical client types; [generation evidence](../../docs/evidence/be02-contract-generation.json) records their hashes and cleanup. Real Rails, fixture conformance and browser acceptance remain pending. Runtime boundary validation is also required: generated types do not validate a response.

## Session and current authorization

`GET /v1/session` never signs in a user or trusts an actor supplied by the browser. Rails checks the real session, expiry and revocation, then derives the current organization and returns an opaque `context_id`, `authorization_version`, and CSRF token. Missing, invalid, expired and revoked sessions all return HTTP 401 with `code: unauthenticated`. The UI clears sensitive data, invalidates its local request generation, aborts outstanding requests and displays a session-unavailable state. It must not retain a former actor's mailbox behind an error banner or imply that a local reset revoked the server session.

The lifecycle below specifies real login, organization switching and server logout. Enable controls only against the implemented endpoints. Tests may inject session invalidation as an explicitly labelled fixture event; fixture events are not server revocation.

The host-only `elevateo_session` cookie is HttpOnly, Path=/ and SameSite=Strict, and Secure with HTTPS. A Secure=false exception is permitted only for an explicit isolated Docker HTTP test profile, never as a silent production fallback. React receives only CSRF proofs, never cookies or Auth tokens. No bearer credentials, session material or mail content may be placed in localStorage/sessionStorage, logs or the bundle. The one-time Auth email callback is the sole scoped credential-in-URL exception: scrub its query before logging, stage it server-side and redirect immediately to a fixed query-free form.

Every other read supplies `X-Session-Context` and `X-Authorization-Version` from its bootstrap. These are consistency checks, not authority. Rails rechecks current membership and compares the supplied context/version; a mismatch returns HTTP 409 `context_changed` with no mailbox data. Session responses do not duplicate mailbox capabilities: `GET /v1/mailboxes` is their sole list, and its context/version must match the session. An authorization change rotates the version before new data is returned. Current revocation still returns 401, taking precedence over a version mismatch. An inaccessible or absent object returns the same 404 `not_available`, including the same generic message. A foreign mailbox/thread relation is also unavailable.

Key cached data by actor, organization, session context/version, selected mailbox and URL filters. Increment a local request generation on session reset, mailbox switch and filter change; compare the full captured context before accepting a response even if abort arrives too late. Apply this guard to errors too: an old actor's delayed 401 must not clear a newer actor's session. Refresh session on window focus/visibility and at most every 30 seconds while active; suspend protected rendering during a required re-bootstrap after a known invalidation. Polling bounds UI freshness; it cannot replace current server authorization on every API call. Clear any sensitive state on a current-context 401, and on 409 context_changed clear it and re-bootstrap once, with an explicit retry state if the context keeps changing. Never loop automatically.

## CSRF and transport

Unsafe routes require **both** a cryptographically unpredictable `X-CSRF-Token` and an exact configured `Origin` match. Ordinary protected mutations use the session token; entry/refresh use the signed browser challenge described below. Logout accepts either the current session proof or the bound challenge. An old constant marker such as `X-CSRF-Token: 1`, Origin alone, or Sec-Fetch-Site alone is insufficient. Rotate/invalidate proof with its binding. Sec-Fetch-Site may provide additional rejection of cross-site requests. Same-origin requests only; no permissive credentialed CORS or cross-origin redirect following.

Use `credentials: same-origin`, `cache: no-store`, an abort signal and a 10-second request deadline. Requests go to relative `/v1` paths; accept no caller-provided destination or authority header. The coordinator may serve the built UI from Rails or use a fixed-origin development proxy inside Docker; a new permanent reverse-proxy service is not required by this contract. Responses and errors use JSON and no-store/nosniff headers. Reject unexpected content types, malformed schemas, oversized streams, or redirects before treating any body as data. Always bound the stream before JSON parsing; do not rely solely on Content-Length.

## Pagination, limits and display

Mailbox and summary pages contain at most 50 entries; a detail page contains at most 20 messages. `next_cursor: null` means the end. An empty page is valid. Cursors are opaque, integrity protected, expiring, and scoped to the authenticated context plus all relevant object/filter/order/limit arguments described in OpenAPI. An invalid/expired cursor returns 400 `cursor_invalid`; reset to the first page once while retaining URL filters, then offer explicit retry if it fails again. No client offset guessing. Concurrent updates may reorder summaries; deduplicate by thread ID and refresh on context/navigation changes rather than claiming a snapshot guarantee.

Each `x-max-response-bytes` is the maximum serialized UTF-8 JSON response size before compression: session 16 KiB, mailboxes 128 KiB, summaries 256 KiB, detail 2 MiB. Errors are at most 4 KiB. Servers may return fewer than the requested number of records to stay within the byte limit, with a continuation cursor when records remain. Bound after JSON escaping as well as by field length. Never truncate JSON or silently omit records. Clients enforce the same limits while streaming.

All strings are untrusted display text. Render message bodies as escaped plaintext with wrapping; no HTML, Markdown, URL autolinking, remote images, scripts or attachments are executed or fetched. `body_truncated` and `subject_truncated` must produce an honest visible indication. There is no hidden full-body download endpoint in this checkpoint. Nullable sender/subject/date fields have accessible placeholders, and a zero-message conversation is valid. `attachment_count` is descriptive only; attachment actions remain unavailable until their authorized contract exists. A GET never marks mail read or mutates any business state.

Errors use the bounded `{code, message, request_id}` shape. Branch UI behavior on `code`, not English text. `request_invalid` covers unknown/duplicate parameters, missing headers or malformed values. Reject non-finite/out-of-range limits. Rate limits may include a delta-seconds Retry-After in 1..300; the UI offers bounded retry and never busy-loops. Transport/schema failures have deliberate client errors and must never activate fixtures. Production builds must exclude the fixture entry point/data; development fixtures are visibly labelled.

## Acceptance and ownership

The BE-02A lifecycle follows [accepted decisions](../../.planning/consultations/results/be-02/decisions.md) and the [implementation brief](../../docs/completion/be02-implementation-brief.md):

- `GET /v1/auth/login-challenge` returns a five-minute proof bound to the current session and pending-entry cookies when present. The signed HttpOnly cookie is `elevateo_challenge`; it uses the session cookie flags. No Auth request occurs. A new challenge replaces only this browser's challenge.
- `POST /v1/auth/login` exchanges email/password internally, replaces any caller cookie, and selects the sole or UUID-first current organization. It returns `AuthLifecycle`, embedding the unchanged `Session`. Identity success without membership returns generic 404 with no invented session payload; a valid opaque cookie may be retained. `GET /v1/session` continues to return 404 until a usable selected membership exists.
- `POST /v1/auth/recovery` returns the same 202 body for known and unknown email. Upstream outage returns 503. Email is restricted to Mailpit. Both email-digest and source-IP PostgreSQL buckets apply: five attempts per email and thirty per IP per 15 minutes. Do not trust forwarded IP headers. Passwords and provider error bodies never enter logs.
- `GET /auth/accept` accepts only `token`, `type=invite|recovery` and optional exact configured `redirect_to`. It stages an encrypted hash for ten minutes under opaque `elevateo_pending`, then sends an empty 303 to `/auth/complete` with `Referrer-Policy: no-referrer`. GET never consumes the hash. The form obtains a challenge bound to that entry before `POST /v1/auth/accept {password}`. Verify, password setting and identity validation precede application access; successful completion clears pending/challenge cookies. An ambiguous verify requires a new link; a proven `password_pending` state may retry only password setting.
- `POST /v1/auth/refresh {}` uses a locally valid cookie and its bound challenge, including when the access JWT expired. A durable claim allows one Auth call, followed by compare-and-set publication within the original ten-second deadline. Contention returns 503 with `Retry-After: 1`. Expired/uncertain claims cannot be stolen or replayed; a late result cannot resurrect logout. Ordinary refresh preserves context and CSRF. Explicit bootstrap/login/refresh may select a newly provisioned membership when none was selected; ordinary mail reads never silently switch. If none exists, keep the valid local cookie and return 404.
- `POST /v1/auth/logout {scope?}` defaults to `local`; `global` requires a locally valid session and targets all local sessions for its bound user; an expired local session returns 401 for global scope. Local revocation and durable upstream intent commit before Auth. Clear session/challenge cookies even with expired access JWT or Auth outage. Report `upstream_status: pending` until completion is known. Missing/invalid cookie plus a valid challenge returns idempotent local completion without user information.
- `GET /v1/organizations` returns only current own memberships with the standard context, signed cursor, UUID ordering, maximum 50 entries and 128 KiB bound. `POST /v1/session/organization` requires current authority, context, Origin and session CSRF; it checks target membership and rotates context/CSRF. Foreign/absent targets return generic 404.

JSON lifecycle requests are at most 8 KiB, passwords at most 1024 UTF-8 bytes, and email at most 320 characters. Entry password minimum is the configured local Auth policy of 12 characters. Reject duplicate/unknown JSON properties and query pairs before Rails merges them. Lifecycle successes are at most 20 KiB; challenges are at most 1 KiB; logout/recovery responses and all errors are at most 4 KiB. Existing read bounds remain unchanged. CSRF/Origin/input failures use 400 `request_invalid`; definitive identity/session failures, including generic login rejection, use 401 `unauthenticated`.

Credentials remain encrypted in private server storage, with session cookie values stored only as SHA-256 digests. Absolute lifetime is capped at Auth creation plus 12 hours (and `not_after`), idle lifetime is 30 minutes, and access JWT lifetime is 3600 seconds. Reads perform current `/user` verification, then recheck the bound Auth session, local policy and membership inside one read-only repeatable-read snapshot. A revocation committed before that snapshot is observed; after it, one whole prior-authorized response may finish within ten seconds. No Auth network call occurs inside a database transaction, and no positive authorization cache substitutes for these checks. Transient/malformed Auth returns 503 without deleting the cookie or returning protected data.

On reload with an expired access JWT the UI may attempt one explicit challenge/refresh cycle. Never display protected data based only on cookie presence or loop on 401. Preserve the captured client generation/context when accepting successes and errors. A current 503 retains unsaved edits without claiming persistence.

The coordinator owns this contract; Astra synthesis delegated this first file set to `/root/plan_synthesis`. Frontend and backend writers propose changes through the coordinator. Record a new contract hash and regenerate all affected outputs after an accepted change. BE-02's required three-opinion/Astra gate must check implementability and may explicitly amend this design; no frontend acceptance overrides that gate.
