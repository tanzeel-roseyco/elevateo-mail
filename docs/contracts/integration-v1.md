# Integration v1 — simulated HTTP milestone

This is the frontend handoff for the first journey. Worker/D1 owns identity, permissions, quota and immutable send requests. All activity is synthetic; acceptance means a durable **fake** receipt, never delivery. Fable UI wiring is owned by its agent. Portable runtime schemas and a fetch client live in `backend/contracts/v1.ts` and `backend/integration/client.ts`; no frontend worktree changes are required here.

## Transport and validation

Browsers authenticate with the HttpOnly cookie described in the recovery extension; non-browser tooling may use `Authorization: Bearer <short-lived-session>`. JSON mutations require `Content-Type: application/json`. The Worker has no public session minting route. Sessions are hashed in D1, expiring and revocable by deletion. Use a same-origin proxy for a browser; unrestricted CORS is not enabled. HTTPS in production; Docker-internal HTTP only in fixtures. Responses are no-store. Bodies are capped at 131,072 UTF-8 bytes. Objects reject unknown fields. IDs match `[a-zA-Z0-9_-]{1,128}`; revisions are 64 lowercase hex characters. Times below are integer Unix milliseconds; scheduled input uses offset-bearing ISO-8601. Frontend converts these to its ISO DTOs at the gateway seam.

Send input is `{mailboxId:ID,to:email[],cc?:email[]=[],bcc?:email[]=[],subject:string,body:string,kind:"manual",revision:positiveSafeInteger,idempotencyKey:ID,scheduledAt?:ISO}`. To has at least one address; each array max30 and the combined deduplicated set max30. Addresses trim/lowercase, retain plus tags. Subject trims, 1–998 chars, no CR/LF; body 1–100,000 chars. Scheduling max30 days ahead. Hash includes the canonical validated input, including content, recipients and schedule; numeric revision is the caller's draft version, returned hash is approval authority. Edit uses the atomic replacement route with a new immutable intent/key, never patches saved content. Internal campaign/AI foundation routes remain experimental and are excluded from v1 capability support.

## Example journey

```json
{"mailboxId":"<server-issued-id>","to":["recipient@example.com"],"subject":"Synthetic test","body":"Plain text only","kind":"manual","revision":1,"idempotencyKey":"compose-001"}
```

POST send-intents → GET `/:id/content` for the saved approval preview → approve with its returned hash → inspect status. Reload discovers requests through the owner list. Do not persist recipients or bodies in browser storage. Poll with bounded backoff; stop automatic polling on unknown. Never replace a send because a response was lost. Recover the original through its idempotency key in the list; inspect before repeating approval. Accepted is simulated provider acceptance.

## Recovery and browser session extension (2026-10-05)

This additive handoff preserves the existing status-only GET response. Runtime schemas in `backend/contracts/v1.ts` are authoritative for these new routes. No endpoint accepts an owner/account ID from the caller.

| Method / route | Validated input | Exact response |
| --- | --- | --- |
| GET `/v1/me` | No query/body | `{accountId:32-lowercase-hex,session:{expiresAt:milliseconds},simulated:true}`. Stable opaque account identity across session rotation and reconnect. |
| GET `/v1/send-intents` | `limit` integer 1–50 default25; cursor is both `before` safe nonnegative milliseconds and `beforeId:ID`, or neither; unknown/duplicate query keys rejected | `{items:[{id,mailbox_id,idempotency_key,revision,status,created_at,updated_at,scheduled_at,successor_id:ID|null}],next:{before,beforeId}|null,simulated:true}`. Descending immutable `(created_at,id)`; no recipients, subject or body. Final page has `next:null`, including an exactly full final page. |
| GET `/v1/send-intents/:id/content` | No query/body | `{intent:{id,mailbox_id,idempotency_key,revision,status,created_at,updated_at,scheduled_at,successor_id:ID|null},content:{from:email,to:email[],cc:email[],bcc:email[],subject:string,body:string,kind:"manual"|"campaign"|"ai"},simulated:true}`. Saved immutable plaintext; verify content integrity before returning. Status polling continues to use the existing GET `/:id`. |
| POST `/v1/send-intents/:id/replace` | `{revision:hash,draft:manualSendInput}`; successor must have a new idempotency key | `{predecessorId:ID,id:ID,revision:hash,status,simulated:true}`. Atomic cancellation and creation of one successor; never approves, reserves quota or sends the successor. |
| POST `/v1/session/logout` | No body/query | `{signedOut:true,simulated:true}`; deletes only the current session and expires its cookie. |

Replacement permits manual predecessors in draft, pending, rejected or cancelled state. Dispatching, accepted and unknown are ineligible. The first transaction wins: identical canonical replacement input returns the same successor (including its current status); conflicting content/key returns 409 `replacement_conflict`. Load the predecessor's `successor_id` and its content instead of creating another successor. Approval racing replacement is serialized by D1: replacement either cancels safely before dispatch or fails closed. A lost replacement response is recovered by repeating the identical input or loading the saved successor. A changed predecessor hash returns 409 `approval_conflict`; a reused unrelated key returns 409 `idempotency_conflict`; an ineligible predecessor returns 409 `replacement_unavailable`. All missing or foreign requests return 404 `intent_not_found`. Invalid persisted content returns 409 `invalid_saved_content`, never content or raw diagnostics.

Existing rows receive their migration-time `updated_at` as the initial immutable `created_at`; this is a pagination baseline, not reconstructed historical creation time. New requests during pagination can precede the cursor; refresh the first page to discover them. Lists include terminal history, have no arbitrary unfinished-request cap, and require bounded, on-demand pagination. These routes are owner sessions only; they do not grant an AI bridge access.

Browsers use `__Host-elevateo_session`: opaque server-issued token, `Secure; HttpOnly; SameSite=Strict; Path=/`, no Domain. Application JavaScript never receives it. Use same-origin fetch with credentials; mutation requests send `X-Elevateo-CSRF: 1` and an exact matching Origin. Cookie requests reject cross-site/same-site Fetch Metadata; missing or mismatched mutation Origin/marker is 403 `csrf_failed`. There is no cross-origin API CORS allowance. Expired/revoked sessions return 401; logout is immediate, other sessions remain active. Mixed bearer/cookie credentials are 401. Bearer authentication remains for non-browser tooling compatibility, never browser storage. All account/session responses are no-store.

Production has no login or session-mint route: identity-provider integration remains future work. **Only the Docker fixture proxy**, excluded from the Worker bundle, exposes POST `/__fixture/session` with `{user:"alice"|"bob"}`. It requires the same Origin/CSRF marker and loopback Host, returns `{provisioned:true,simulated:true}`, and sets a fifteen-minute cookie without returning a token. Run with Docker port publication bound to `127.0.0.1`; open `http://localhost:8787` (Secure-cookie localhost exception) or proxy both `/v1` and `/__fixture` behind the frontend's same origin with the original Host retained. Bootstrap rotates fixture sessions; revocation/expiry are checked against D1 on every API request. This local fixture facility is never production authentication.

Example browser bootstrap: `fetch('/__fixture/session',{method:'POST',credentials:'same-origin',headers:{'Content-Type':'application/json','X-Elevateo-CSRF':'1'},body:JSON.stringify({user:'alice'})})`. Then GET `/v1/me`, paginate `/v1/send-intents`, and fetch content only when opening a request. Keep only opaque IDs/cursors and an optional idempotency key in browser persistence; clear account-specific UI state when `accountId` changes. Exact saved content must be shown again before any explicit approval.

Security/design references: [D1 atomic batch](https://developers.cloudflare.com/d1/worker-api/d1-database/), [cookie attributes](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Set-Cookie), [OWASP CSRF protection](https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html).

## Quota, connection lifecycle and operational bounds

Rolling 24-hour unique recipient counting is **provisional**, not an approved production decision. Pending, dispatching and unknown reserve capacity indefinitely until a safe transition; accepted usage ages from dispatch timestamp. `nextAcceptedReleaseAt` is the earliest accepted bucket release, not a promise that all capacity will be available then. A held reservation has no guaranteed release time (`reservationReleaseUnknown:true`). Draft/rejected/cancelled hold none. Remaining is clamped to zero and send admission requires both mailbox and user capacity.

Reconnect same provider subject/address retains server ID, historical sends and quota. Disconnect frees a connected slot but never deletes history or quota; disable first, then connect replacement. Reactivation atomically rechecks ten active slots. Replacement gets a new ID but still shares the owner's 300-recipient rolling ceiling, so connection rotation cannot evade the 300/user and 3,000/ten-user ceilings. Distinct plus addresses are never globally collapsed into accounts; future real providers must prove account/alias ownership and map aliases to that provider subject. Fake subjects are fixture data, not proof of real identity.

Approval immediately enqueues due work; one-minute cron attempts recovery of deferred enqueue while approval remains valid. `enqueue:"deferred"` means approval was saved but pause, scheduling or queue failure prevented immediate enqueue; inspect the intent before taking further action. TTL supports 60–86,400 seconds (default3600), starting at max(approval time,schedule). Queue delay, pause or outage can still expire approval; expired work is cancelled and must be deliberately re-created/re-approved. No latency guarantee. Queue handles max10 jobs per batch, platform max3 retries; relay max100 due rows. Recovery handles max100 stale claims and100 expired approvals per tick. Reconciliation reads max20 unknowns/tick, at least5min between unsuccessful checks, at most10 checks; unresolved rows remain unknown with quota held for operator investigation. Receipt recovery never invokes send. Database errors after a provider call may leave dispatching; after60s it becomes unknown and positive receipt reconciliation restores accepted even while sending is paused.

AI read, draft and send flags are separate, default denied. Existing owner-only experimental AI APIs are not bridge credentials. No AI bridge/session delegation is implemented or advertised; never hand an owner bearer token to an AI process. A future bridge requires selected-mailbox, tool-limited, expiring, revocable grants and its own authentication boundary.

## Errors and unsupported features

Every error is `{error:{code:string,requestId:UUID}}`; no raw SQL/provider error/body/credential. 401 `unauthorized` includes expired/revoked sessions. 400 `validation_failed`, `invalid_json`, `body_required`, `schedule_too_far`; 413 `body_too_large`; 415 `json_required`. 404 `not_found`, `mailbox_not_found`, `message_not_found`, `intent_not_found`. 409 `mailbox_identity_conflict`, `mailbox_limit`, `idempotency_conflict`, `approval_conflict`, `already_in_flight_or_missing`, `approval_required`, `approval_expired`, `mailbox_permission`, `quota_exceeded`, `owner_quota_exceeded`, `dispatch_paused`, `suppressed`, `campaign_paused`, `consent_or_reply_stop`, `event_conflict`. 500 `internal_error`: inspect saved state before retry. Queue diagnostics are redacted: `invalid_envelope`, `provider_rejected`, `provider_outcome_unknown`, `dispatch_interrupted`, `reconciliation_unknown`, `reconciliation_unavailable`, `enqueue_deferred` with persisted correlation IDs. Do not display provider IDs as delivery evidence.

Unsupported: production authentication/OAuth/MFA, real mailbox connection or sending, inbox synchronisation and message search, campaign wizard/execution product, history import, attachments, mailbox labels/mutations, AI/desktop bridge, DNS writes, real webhooks, live restore/alerts and production hosting guarantees. Experimental foundation routes do not change these capability claims. Production remains disabled and unready.

Legacy intents created before migration 0006 have no independent envelope digest. Pending legacy rows fail closed as rejected (`invalid_envelope`); create a new previewed request. Unknown legacy rows remain held for investigation. Do not manufacture a digest or resend an uncertain historical request.
