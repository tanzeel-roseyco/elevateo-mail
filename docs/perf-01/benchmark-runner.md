## 4. Execution design

### 4.1 Task directory and transfer (host side, `ops/perf/transfer.sh`)

- Project name doubles as directory name: `PERF01_PROJECT=perf01-<8..32 hex>` (generate with `echo perf01-$(cat /proc/sys/kernel/random/uuid | tr -d - | cut -c1-12)`), task directory `~/perf01-<hex>/` on fleet-02, created with `mkdir -m 0700` and refused if it exists.
- Transfer is `git archive --format=tar <HEAD> -- compose.yaml apps/server ops scripts .gitattributes | ssh fleet-02 'tar -x -C ~/perf01-<hex>'`. The path-limited archive is about 200 KB; `third_party/upstream` (79 MB of the 81 MB tree) is never shipped. `git archive` emits index content, so the archive carries LF endings and the `100755` modes recorded in the index regardless of Windows autocrlf; the script also `chmod 0755`s `ops/perf/*.sh` remotely so either `sh script` or `./script` works.
- Provenance written to `~/perf01-<hex>/source.json` and copied into every run's evidence: `git rev-parse HEAD`, branch, dirty-diff hash (`git diff HEAD | sha256sum`, covering staged and unstaged tracked changes), untracked-file count, archive SHA-256, per-path tree hashes (`git rev-parse HEAD:apps/server` etc.), transfer time and host.
- Dirty-tree policy: the archive always contains HEAD, so a dirty tree would measure something other than the working copy. The script refuses unless `PERF01_ALLOW_DIRTY=1`, and then the manifest marks the run `dirty: true`. Recommended rule: candidates are measured only as committed revisions on the branch.
- Candidate runs reuse exactly this path with a new project name: same base image digest, same pinned images, same caps, same fixtures, same matrix; only the application source (hence the server image) differs.

### 4.2 Compose overlay (`ops/perf/compose.perf.yaml`)

Invocation: `docker compose -p $PERF01_PROJECT --project-directory ~/perf01-<hex> -f compose.yaml -f ops/perf/compose.perf.yaml --env-file ops/local/.env`. Relative paths resolve against the first file's directory, the same convention `ops/compose.r1-test.yaml` relies on.

- Labels `elevateo.perf.task=perf01` and `elevateo.perf.project=<project>` on every service container, on the built image (`build.labels`), on the network and on the three volumes.
- Unique names: server image `${PERF01_PROJECT}-server:perf`; network `${PERF01_PROJECT}-runtime` (`internal: true`); volumes `${PERF01_PROJECT}-db-data|db-config|storage-data`.
- Caps via `cpus:` / `mem_limit:` / `pids_limit:` service keys. Legacy docker-compose v1 ignored `deploy.resources.limits` without `--compatibility`; Compose v2 honours both, but these keys are unambiguous and show up in `HostConfig.NanoCpus` / `HostConfig.Memory`, which the run script and cleanup read back as proof. Defaults (overridable per run):

| Service | cpus | mem_limit | pids |
| --- | ---: | ---: | ---: |
| db | 1.5 | 1536m | 512 |
| api | 1.0 | 768m | 256 |
| perf-load | 1.0 | 512m | 128 |
| storage | 0.5 | 512m | 256 |
| worker | 0.25 | 256m | 64 |
| auth, rest | 0.25 | 256m | 128 |
| mailpit | 0.25 | 128m | 64 |
| perf-sql | 0.25 | 256m | 128 |
| bootstrap, migrate, perf-fixtures (transient) | 0.5 | 512m | 128 |

Steady state: 5.0 CPUs (31% of 16) and 4,224 MB. The load client and the API live in separate cgroups with separate caps, so the client cannot consume the API's share, though both still compete with neighbours for physical cores.

- `restart: "no"` overrides the base `unless-stopped` for every service: a disposable stack on a production host must never resurrect itself after the run, a daemon restart or a reboot. This changes nothing on the request path. Flagged as a question for the lead in section 10 because it is the only semantic override of `compose.yaml`.
- New profile `perf` services, all on the internal network only:
  - `perf-fixtures`: pinned `supabase/postgres` image running `psql` as `supabase_admin` with `ops/tests/db-fixtures.sql` (two orgs, three users, three mailboxes), the R1 fixture set.
  - `perf-sql`: same pinned image, `psql` as `elevateo_api` with `ops/perf/sql/` mounted read-only; password reaches only that container's environment.
  - `perf-load`: the task's own server image running `ruby /perf/load.rb` with `read_only: true` and a tmpfs `/tmp`; results go to stdout so no writable bind mount is needed.
- Runtime network stays `internal: true`. The only network egress is the build phase (apt and bundler from the pinned Ruby base). `RAILS_ENV` is inherited from `compose.yaml` (development); the overlay does not change it, so any environment change is a candidate change committed to the branch and measured against the baseline, never a runner knob.
- Nothing publishes a port, uses `privileged`, mounts the Docker socket, uses host networking or touches a path outside the task directory. The run script verifies this from `docker inspect` before any load and aborts otherwise.

### 4.3 Run sequence (`ops/perf/run-baseline.sh <label>`)

One invocation is one fresh project, one build and one evidence directory `evidence/<run-id>/` with `run-id = <project>-<UTC stamp>-<label>`.

1. Preflight (section 5), refusing existing `perf01` resources, a busy host or under 20 GB free disk; snapshots pinned-image presence and build-cache record ids.
2. Secrets: `docker compose -p <project> -f ops/compose.secrets.yaml run --rm -T --label elevateo.perf.task=perf01 secrets` writes task-local `ops/local/.env` (git-ignored, never copied into evidence).
3. Build `api` with plain progress log; record `docker image inspect` of the built image.
4. The three disposable volumes are created by the script itself (`docker volume create` with the task, project, run and a fresh `elevateo.perf.generation` nonce; the overlay declares them `external: true` so Compose only attaches by exact name and never creates or labels a volume), each inspected immediately afterwards and its identity (name, `CreatedAt`, run, generation, project) recorded in `volume-identity.tsv`; a volume whose identity does not round-trip is unproven and the run finalizes as incomplete (exit 7) before any container starts. Then `up -d --wait db`, `run --rm` for `bootstrap`, `migrate`, `perf-fixtures`, then `up -d --wait auth rest storage mailpit api worker`. The whole run holds the exclusive project-scoped lifecycle lease `<task root>/.perf01-lifecycle.lock` (section 9) from before the first volume is created until after the proof file is in place.
5. Shape proof: image ids and repo digests for the six pinned refs, `HostConfig` of every container (ports, privileged, network mode, caps, restart policy), network `internal=true`, `compose ps --format json`, Puma boot banner from `logs api` (there is no `config/puma.rb`, so the thread pool is Puma's default and must be captured rather than assumed).
6. Idle phase: 120 s of sampling with no HTTP load, for the worker-path owner (heartbeat CPU, context switches, write bytes). Note that the worker's cgroup also contains the compose healthcheck `ruby bin/worker-health` every 5 s, so its CPU includes those execs; that is the real configuration and is identical for baseline and candidate.
7. Warmup: 15 s keep-alive at concurrency 4 against each endpoint, unrecorded.
8. Matrix: passes 2 x endpoints `/health`,`/ready` x modes keep-alive,new-connection x tiers 1,4,16 x reps 2 x 20 s = 96 measured runs, about 32 minutes of load plus sampling overhead. Pass 2 is the unmodified repeat used as the noise floor. Before each run the host-quiet guard runs; a resource sampler runs alongside each load run. The matrix stops on the first client exit code 3 (error rate above 5%) or on a busy host.
9. EXPLAIN runs as `elevateo_api` (`ops/perf/sql/explain-rls.sql`): the readiness `SELECT 1`, the four RLS-protected tables under a valid member, a member without private mailbox access, a denied principal (org-B user claiming org A) and no claims, each inside a transaction with transaction-local `set_config` claims, with row counts so visibility is checked alongside timing, and a post-transaction check that claims did not leak.
10. Logs: `api.log` (the Rails `Completed ... in Xms` lines are extracted to `api-completed-ms.txt` as server-side timing), `worker.log`.
11. `manifest.json`, then `volume-proof.tsv` (one seven-field row per volume whose identity round-tripped: project, run id, volume, generation, `CreatedAt`, `synthetic_only`, `status`; written to a temporary file and renamed into place so no reader ever sees a partial file), then the exit trap stops the owned container IDs under bounded calls, writes `stop.log`, `host-after.txt` and, if needed, `RETAINED`/`ABORTED`, and seals `SHA256SUMS` as its very last step. Containers are left stopped, not removed, so cleanup can inspect mounts and write its own manifest.

Timing method: client-observed `Process::CLOCK_MONOTONIC` around `Net::HTTP#request` including body read, inside the `perf-load` container across the internal bridge. Server-side durations from the Rails log are recorded as a second view, not as the primary metric.

Workloads covered against the brief: empty (idle phase), small (fixture set, `/health`), representative-bounded (`/ready` with four dependency round trips at tiers up to 16), valid and denied principals (EXPLAIN section), reused versus new connections (modes), concurrent failures (error-rate abort records status and exception class counts; `/ready` returning 503 under load is an error by design, since `--expect-status 200`).

Refusal rules: exit 3 if any container, network, volume or image matches the task label or the `perf01-` prefix (serialized runs require a clean slate; the owner of the leftover runs `cleanup.sh` first); exit 4 if 1-minute load exceeds `nproc/2` (8), `MemAvailable` is under 6 GiB or `/` has under 20 GB free. The pinned refs are parsed from `compose.yaml` and the Dockerfile rather than duplicated, so the list cannot drift. Foreign resources that carry neither the task label nor the project prefix (another team's volume, for instance) are never listed in `existing.txt` and cannot cause exit 3; they appear only in the aggregate counts in `host.txt`, and nothing in this harness ever names, inspects or removes them. The regression for this uses a synthetic name and makes no claim about what is present on fleet-02.

## 6. Load generator decision

Recommendation: the Ruby client in the already-built server image (`ops/perf/load.rb`), no new dependency.

- Why it is enough here: both endpoints are cheap; `/health` is a one-key JSON render and `/ready` is dominated by four dependency round trips, so expected rates are hundreds to a few thousand requests per second at tier 16. A Net::HTTP keep-alive client with 16 threads delivers that. The stack has no `config/puma.rb`, so server concurrency is Puma's default handful of threads; the client does not need to exceed it by much to expose queueing.
- Limits stated up front: Ruby's GVL serializes the client threads, so the client is roughly one core of work and can become the bottleneck before the server does at tier 16 on `/health`. The output carries `client_saturated_hint`, and the per-run `stats.csv` shows `perf-load` CPU against its 1.0 cap next to `api` CPU. If the client sits at its cap while `api` is well below its own, the tier is client-bound and is reported as such, not as server capacity. The brief forbids absolute maximum-speed claims anyway; the client only needs to be identical between baseline and candidate.
- Isolation: the client runs in its own cgroup with its own caps, so it does not eat the API's CPU share, but both share the host's physical cores with production. Caps, not co-location, are the control.
- Alternative kept in reserve: a tiny pinned image (`oha`, `hey` or `wrk`) by digest. It would remove the GVL ceiling but is a new build-phase dependency requiring justification and lead approval, plus provenance (digest, licence) in the manifest. Trigger for escalation: the Ruby client is provably saturated at tier 16 in the baseline and the candidate under test is expected to move `/health` throughput specifically.

Client behaviour: URL host must be `api` (anything else is a usage error), modes keep-alive (one persistent connection per thread, kept across warmup) and new-connection (connect per request), concurrency 1..64, duration 1..600 s, optional unrecorded warmup, abort with exit 3 when errors exceed 5% after 50 requests (non-200 statuses and connection exceptions both count), raw samples as microsecond integers up to two million (beyond that `samples_truncated` is set and percentiles are withheld), nearest-rank percentiles only at 1,000 or more samples.

### 7.1 Parent-review repairs to `run-baseline.sh` (second draft, still unexecuted)

The lead's parent review of the first draft (SHA-256 `d5e1f512...8310`) found five defects. Repairs, all in `ops/perf/`:

1. Exit trap armed before ownership. The trap now starts as `finish_before_ownership`, which only writes `ABORTED` and the host snapshot. It switches to `finish` immediately before `up -d --wait db`; `finish` stops only the container IDs recorded in `owned-containers.txt`, collected after each `up` by filtering on the compose project label, the task label and a new per-invocation label `elevateo.perf.run=<run-id>` (exported as `PERF01_RUN_ID`, required by `compose.perf.yaml`). `compose stop` by project name is gone.
2. Unvalidated tunables. Every tunable is validated as a bounded integer, allowlisted list or bounded decimal before any Docker call, using `${VAR-default}` so an explicitly empty value is rejected rather than defaulted. The planned wall time (idle + warmups + runs x (duration + 5 s sampler overhead) + setup allowance) must fit `PERF01_MAX_TOTAL_SECONDS` (default 3600, max 7200); it and the deadline epoch go into the manifest, each run checks the deadline first (exit 5), and the number of load result files must equal the expected run count (exit 5).
3. Stop failure swallowed. `finish` records every stop status, re-inspects each owned ID, writes still-running `id:name` pairs to `RETAINED`, logs them, and exits 6 when the run would otherwise have exited 0.
4. Required EXPLAIN failure swallowed. A non-zero `perf-sql` exit appends to `INCOMPLETE`, the manifest and `SHA256SUMS` are still written with `"status": "incomplete"` and `"required_steps_failed": ["sql/<file>"]`, and the run exits 7.
5. Sampler stop-file reuse. Each sample uses `<out-dir>/.stop`; the run script asserts it does not exist before starting and never removes it; `sample.sh` refuses to start if it exists and never deletes it; stopping waits at most `PERF01_SAMPLER_WAIT` (default 30 s) and then kills the sampler, recording the kill in `sampler-kills.txt`.

The lead's addendum from inspecting `sample.sh` and `lib.sh` added four more:

6. Stats pipeline masked failure. `sample.sh` now captures `docker stats` output into a variable, tests the Docker exit status first, and only then prefixes and appends; a failure or empty output writes `ts,stats-unavailable,exit=<n>,,,,,,`. A failing `docker ps` writes `ps-unavailable,exit=<n>`.
7. Worker row masked exec failure and partial output. `docker exec` exit status is captured; the awk parser requires the `---` separator and all eight numeric fields, otherwise it writes `ts,unavailable,<reason>,,,,,,` (`exec-exit=<n>`, `partial-proc-output no-separator`, `partial-proc-output missing-fields`, `ambiguous-worker`). Blank numeric fields are never written as if measured.
8. Inventory failed open. `perf01_existing_resources` now writes to a file passed by the caller, runs the seven inventory commands one at a time, and dies with exit 2 naming the failing command (`inventory command failed (docker volume ls --filter label)`, stderr kept in `existing.txt.err`) instead of returning an empty list; only a verified empty file means clean. `preflight.sh` was updated to the new signature.
9. Unbounded Docker calls in the sampler. Every `docker ps`, `docker stats` and `docker exec` runs under `timeout -k 5 $PERF01_DOCKER_TIMEOUT` (default 20 s, validated 5..60); exit 124 is recorded as unavailable like any other failure; the stop file is re-checked between every call. With three calls per cycle the worst case per cycle is about 75 s, so the main script's 30 s bounded wait may kill a sampler stuck on a frozen daemon and record it in `sampler-kills.txt`; that is the intended fail-safe.

The lead's verification of items 1 to 5 accepted them and added two residual fail-open spots in `finish`:

10. Partial `up` left unrecorded containers. `finish` now rediscovers containers by the per-invocation label `elevateo.perf.run=<run-id>` before stopping and unions them into `owned-containers.txt`; if that discovery command fails, `RETAINED` records `ownership-discovery-failed` and the exit becomes 6.

Statistics policy, applied identically to baseline and candidate:

- P50/P95/P99 (nearest-rank on sorted client samples) are reported only for runs with at least 1,000 successful samples. Below that, report median, min, max and the sample count and say that percentiles are not supported. A 20 s run at tier 1 on `/ready` may fall under the floor; that is reported, not hidden.
- Throughput is successful requests divided by measured seconds, per run; errors and non-expected statuses are reported alongside, never dropped.
- Noise floor: pass 2 is an unmodified repeat of pass 1 in the same stack. For every metric the pass-1 versus pass-2 relative delta is the noise floor for that cell. A candidate change smaller than twice the noise floor of its cell is reported as "not distinguishable", whatever its sign.
- Regressions are reported with the same prominence as improvements, including any correctness failure (visibility row counts in the EXPLAIN section, 503s under load, error-rate aborts).
- A `/health` or `/ready` microbenchmark is not whole-application evidence; the report says which cells moved and what mechanism explains it, and makes no absolute maximum-speed claim.
- Host noise: load average and `MemAvailable` before, during (sampler `host.csv`) and after each run are part of the evidence. Runs during which load1 exceeded the cap are aborted and recorded as such rather than reported as results.

## 9. Cleanup manifest design (`ops/perf/cleanup.sh`, sixth draft after five parent reviews)

Preconditions before any Docker call or evidence write: `PERF01_RUN_ID` must equal the evidence directory's run id (exit 2), the evidence directory must resolve to `<task root>/evidence/<run id>` (exit 2; a relocated proof is not read), and the exclusive project-scoped lifecycle lease `<task root>/.perf01-lifecycle.lock` (shared with `run-baseline.sh`, section 7.1 E4) must be taken with `flock -n` (exit 4 "lifecycle lease held by another producer or cleanup for project <project>; retaining all volumes" otherwise, nothing touched). Ownership boundary: single host, single task directory per project, one producer or one cleanup at a time; outside it (a same-project stack from another task directory) only the generation match below protects a volume, and it retains. Two phases, fail closed throughout. Phase A plans: every Docker call goes through one helper that wraps `timeout -k 5 $PERF01_DOCKER_TIMEOUT docker ...`, captures stdout and exit status separately and aborts with exit 4 on any non-zero status (124 recorded as a timeout), writing `{"action":"aborted","name":"docker <cmd>"}` to the manifest, so a failed or hung listing can never read as "nothing to clean"; absence is never inferred from error text but only from a successful typed inventory with zero lines; all counts are validated digits-only; nothing is removed. Phase B runs only with `--execute`: each planned removal is re-verified immediately before its `docker rm` and any Docker failure aborts the remaining deletions. Each action is one ndjson line `{time, kind, id, name, action: planned|stopped|removed|retained|failed|aborted, reason, execute}` (a successful container stop is `stopped`, never `removed`) in `evidence/<run>/cleanup-<stamp>.ndjson`, with a readable `.txt` twin, the `.plan` file and `docker system df` before and after. The evidence directory name is the run id and must match this project's run-id pattern; the volume proof is bound to it.

Exit codes: 0 clean; 1 something task-owned could not be proven or removed (`retain`); 2 usage, including the rejected `--remove-pulled-images` and `--remove-build-cache` flags and a missing or mismatched `PERF01_RUN_ID`; 4 lifecycle lease held elsewhere, or Docker failure or timeout, aborted. Policy retentions (`keep`: build cache, pinned images, volumes without the flag, already-absent objects) are recorded as retained but do not fail the run, otherwise the run could never exit 0.

Removable at all: this project's labelled containers, its network, the task-built image and task-labelled dangling layers by exact ID, and, with the flag and the bound proof, its three volumes. Ownership proof per kind:

1. 2. Network: label `elevateo.perf.project=<project>`, exact name `<project>-runtime`; zero attached containers re-verified in phase B after the containers are gone.
3.
