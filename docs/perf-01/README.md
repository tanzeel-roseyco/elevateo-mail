## 3. What exists to optimize (honest inventory)

At base `5785eba` the backend is a security-repair foundation checkpoint, not a product API:

- Two routes: `GET /health` → `200 {"status":"ok"}`; `GET /ready` → `200|503 {status, outbound_hold, checks{database, auth, storage, mail_catcher}}`. Unhandled errors → `500 {code, message, request_id}`. Unknown routes return the Rails default 404 shape, not the envelope (pre-existing, out of PERF-01 scope).
- Four `app` tables with FORCE RLS, four SELECT policies, one `STABLE` plpgsql helper `app.context_uuid`, two migrations, no explicit indexes (all come from PK/UNIQUE).
- `Elevateo::Tenancy.with_context`: three required DB round trips (BEGIN, parameterized `set_config`, COMMIT) plus Ruby-side cache clears. It has no caller outside tests.
- An idle worker that boots Rails, validates config, and publishes a heartbeat file every second; a compose healthcheck that cold-starts Ruby every 5 s to read it.
- **No first-party frontend exists at this base.** There is no `apps/web`, root `src` or `packages`; no caller of `/health` or `/ready` exists outside Compose healthchecks. "Frontend-serving backend speed" therefore reduces to health/readiness latency, framework and connection defaults, serialization defaults and the tenancy wrapper's per-call cost. The mailbox APIs described in `docs/contracts-and-reliability.md` do not exist and will not be invented for this task.
