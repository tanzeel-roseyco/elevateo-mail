# Component adoption plan

Status: **all six reference snapshots imported; no application component integrated yet**. The user authorized source intake and extensive documentation. This matrix identifies the strongest candidates without silently inheriting their vulnerabilities, runtime assumptions or dependency trees.

The user's 2026-10-13 correction selects **Rails API/worker + Laravel Blade/Livewire presentation + self-hosted Supabase + Resend**. Alpine/plain JavaScript and Anime.js provide browser interaction; React/TSX is source material to translate, never a drop-in frontend. TypeScript remains suitable for wire contracts, MCP and development tools. Follow [the architecture](../.planning/POLYGLOT_ARCHITECTURE.md) and [the step-by-step reuse playbook](component-reuse-playbook.md). Required named opinions remain pending; the selected stack does not claim completed consultation or runtime verification.

Use three different decisions deliberately: **adapt** means a small implementation may be copied/translated with notices and reviewed changes; **reference** means use the behavior/design as evidence for our own implementation; **replace** means the current implementation is unsuitable for our required boundary. Every destination below is proposed and does not yet exist. Full per-repository decisions are in [the dossiers](reference-repositories/README.md).

## Explicit replacements and deferred scope

- **All upstream send loops:** replace with the [documented send ledger](contracts-and-reliability.md) owned by the Rails domain and same-code worker. Do not retain process-local ownership, automatic reset-to-queued or success inferred from a reserved attempt.
- **All upstream authentication:** use our selected Supabase identity integration, authoritative session checks and company plus mailbox permissions. Existing single-user/global token designs are insufficient.
- **All imported schemas:** use them as evidence, not migrations to run on Supabase. Draft versions, immutable send jobs, provider receipts/routes, current memberships and private storage have different invariants.
- **Instantly generic POST retries:** replace with provider-specific idempotency and uncertainty rules; do not hide a potentially accepted send behind a generic retry helper.
- **BillionMail Postfix/Dovecot/Rspamd stack and privileged host controls:** preserve as reference only. The selected baseline delegates mail transport to Resend and does not require a conventional mail server.
- **Gmail/Graph/IMAP integrations:** defer until existing-mailbox synchronization and migration are confirmed. Importing their source does not enable those providers.
- **Campaign engines, lead enrichment, warmup and workflow builders:** defer until the shared mailbox is reliable and an approved need exists. Resend policy-compatible sending remains a product constraint.
- **Dependency trees:** do not copy package lockfiles into our future application root. Select a minimal maintained dependency set after compatibility/security/license review; preserve upstream lockfiles only as historical evidence.

The domain database has one migration lane under `apps/server/db`; Supabase manages its own internal schemas. Laravel may own a separately permissioned session store, never mailbox tables or sending. TypeScript contracts/MCP/simulator and PHP/Go/Python tools cannot become additional domain writers or send authorities. Laravel forwards the real user's authorization to Rails through an allowlisted client. Its service identity never authorizes a supplied actor ID. The expanded research inventory supplies further candidates, not approval to copy unpinned code.

## Strict port checklist

Each actual port must have a recorded component ID, original repository/revision/path and manifest SHA-256, destination, applicable notices, reason for adoption, transformations, dependencies, relevant audit finding IDs, owner/reviewer, negative tests and verification results. [The reuse playbook](component-reuse-playbook.md) defines the procedure and evidence record. Keep snapshots unchanged. The lifecycle is `candidate → reviewed adaptation → tested integration → accepted release`.

Resolve license obligations for the exact material, not only its repository label. A translation remains an adaptation when based on upstream implementation. If independently writing a replacement from behavioral requirements, record that distinction honestly. Never list a proposed target directory as an already implemented feature.

## Order of work

After the research/opinion gate, start with A03 plus the Rails-owned database model and simulated-provider path, then A01/A02/A08/A12 for the Laravel mailbox interface. Add Ruby A10/A11 and recovery tests derived from A05, then A04/A09. Evaluate optional templates/contact import and campaign features only after that vertical slice. Mac/Tauri and C# Windows may reuse the served Laravel UI only in an unprivileged remote WebView, with a separate trusted bundled CLI panel. Java Android/SwiftUI iOS port interaction specifications against the same API. No upstream project supplies verified Elevateo installers or mobile packages.
