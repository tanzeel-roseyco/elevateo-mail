# Credentials-last checklist

Backend-branch implementation, bounded reviews and final local Docker verification passed; merged-main and client release verification remain open; see completion/backend-20261030-receipt.md for exact counts and scope limits. This is not live authentication, deliverability or browser acceptance. No deployment, live mail, DNS, Workspace, Cloudflare or Google Cloud action is authorized by this checklist. Fleet-02 was excluded.

1. **Reviewed artifacts.** Supply repository digests (`repository@sha256:...`) for `ELEVATEO_PRODUCTION_IMAGE` (apps/server/Dockerfile), `ELEVATEO_MCP_IMAGE` (apps/mailbox-mcp/Dockerfile), `ELEVATEO_OPERATIONS_IMAGE` (ops/production/Dockerfile), and `ELEVATEO_BACKUP_HELPER_IMAGE` (GNU tar/sh). Use the exact accepted source revision. Deployment never builds or accepts mutable image tags.
2. **Database identities.** Generate eight distinct URL-safe random passwords, 32-128 characters: `POSTGRES_PASSWORD`, `AUTH_DB_PASSWORD`, `REST_DB_PASSWORD`, `STORAGE_DB_PASSWORD`, `MIGRATOR_DB_PASSWORD`, `API_DB_PASSWORD`, `WORKER_DB_PASSWORD`, `ATTACHMENT_GATEWAY_DB_PASSWORD`. These initialize the private database and least-privilege service identities. Existing databases require their current matching credentials; changing environment does not rotate existing SQL passwords.
3. **Application and Auth keys.** Generate `SECRET_KEY_BASE` (at least 64 characters), `JWT_SECRET` (at least 32), and independent 32-byte random keys encoded as standard base64 for `ELEVATEO_SESSION_KEY_BASE64` and `ELEVATEO_ATTACHMENT_GATEWAY_HMAC_KEY_BASE64`. From the Supabase administrator obtain signed HS256 `ANON_KEY` and `SERVICE_ROLE_KEY` JWTs using the same JWT secret, roles `anon` and `service_role`, and valid expiration. Retain recovery-critical keys separately from encrypted backups. Application API never receives the Auth signing/admin key.
4. **Existing Authentik registration.** Obtain issuer `https://<existing-host>/application/o/<application>/`, group UUID, restricted directory-read API token, OIDC client ID and secret from the existing hetzner-platform Authentik administrator. Set `ELEVATEO_AUTHENTIK_ISSUER`, `ELEVATEO_AUTHENTIK_GROUP`, `ELEVATEO_AUTHENTIK_API_TOKEN`, `ELEVATEO_AUTHENTIK_CLIENT_ID`, `ELEVATEO_AUTHENTIK_CLIENT_SECRET`. The upstream registered callback is `https://mail.elevateoco.com/auth/v1/callback`; the application's downstream callback is `https://mail.elevateoco.com/v1/auth/sso/callback`. GoTrue's private admin API registers only `custom:authentik`; foreign enabled custom providers fail admission. No Google account/project is involved. Identity must be active, verified and in the required group on every protected request.
5. **Tenant and approved assignments.** Obtain canonical organization, Auth user and mailbox UUIDs from the existing tenant administrator. Membership must already be verified/enrolled; possession of an email address or CSV row never enrolls a user. Existing operator initialization is documented in `ops/production/initialize/README.md`. Supply `ELEVATEO_APPROVED_ASSIGNMENTS` as an absolute regular CSV with exact header `organization_id,user_id,mailbox_id,address` and `ELEVATEO_EGRESS_ID` as the approved route UUID. Keep `ELEVATEO_PROVISIONING_ENABLED=false`; a later explicitly enabled run applies idempotent held assignments. Daily defaults are 30 per mailbox and 300 per user across mailboxes. Destination-domain policy remains explicit and fails closed when missing.
6. **Storage and MCP.** Choose the private `ELEVATEO_ATTACHMENT_BUCKET` identifier (3â€“63 lowercase letters, digits or hyphens; first character alphanumeric). Deployment creates a missing bucket and verifies private readback; an existing private bucket is reused, while a public or conflicting bucket is rejected. Supply the exact trusted `ELEVATEO_MCP_HTTP_HOST` authority. The storage gateway and provider event worker alone receive private object authority. MCP exposes search, read and draft only, with per-user grants; no send tool exists. Public edge routing/TLS is outside deployment and must preserve authenticated headers without publishing private data-plane ports.
7. **Mox identity and TLS.** Obtain the approved public IPv4, hostname, approved mail domains and excluded Workspace domains from the mail administrator. Set `ELEVATEO_MOX_IPV4`, `ELEVATEO_MOX_HOSTNAME`, `ELEVATEO_MAIL_DOMAINS`, `ELEVATEO_WORKSPACE_DOMAINS`. Supply full-chain PEM and private-key PEM as `ELEVATEO_MOX_TLS_CERT_BASE64` and `ELEVATEO_MOX_TLS_KEY_BASE64`. These originate from environment and are written to dedicated owned volumes; secrets never enter source. Preflight parses the certificate/key and verifies their match before persistence. The host-networked `mox-readiness` service then checks the live IMAPS certificate/hostname and SMTP/submission greetings; it never authenticates or submits mail. Initialization refuses changed existing configuration. Domains and logins remain disabled pending separate activation; this does not alter DNS/MX or create mailbox passwords.
8. **Optional Resend.** Default `ELEVATEO_OUTBOUND_MODE=held`. For explicit Resend processing, obtain worker-only `RESEND_API_KEY`, ingestion-only `RESEND_WEBHOOK_SECRET`, and approved `ELEVATEO_RESEND_FROM_DOMAIN` from the existing account administrator. Keep `ELEVATEO_OUTBOUND_HOLD=true`. Webhook path is `/v2/provider-events/resend`; signature verification, event persistence and suppression do not release sending. Real Resend usage remains six historical HTTP calls and zero sends; verification uses only isolated stubs.
9. **Independent backup destination.** Obtain an off-host restricted SFTP account and verified host public key. Set `ELEVATEO_BACKUP_SSH_HOST=user@host`, absolute `ELEVATEO_BACKUP_REMOTE_DIR`, `ELEVATEO_BACKUP_KNOWN_HOSTS` to the public pinned-host file, and private SSH key bytes as `ELEVATEO_BACKUP_SSH_KEY_BASE64`. Set independent `ELEVATEO_BACKUP_AGE_RECIPIENT`; keep `ELEVATEO_BACKUP_AGE_IDENTITY_BASE64` offline for recovery only. Set `ELEVATEO_SOURCE_REVISION`, absolute private `ELEVATEO_OPERATIONS_LOCK`, `COMPOSE_FILE` and `COMPOSE_PROJECT_NAME`. Backup stops all project writers, encrypts all six volumes and verifies off-host ciphertext readback. Restore only into a fresh isolated project, with old sessions/grants revoked and unfinished sends held. See `ops/production/completion/README.md`.
10. **Admission and future execution.** Export settings from a secret manager using the single root `.env.production.example` inventory. `sh ops/production/deploy.sh --dry-run` validates inputs without Docker or provider access. After independent release approval, `sh ops/production/deploy.sh` assembles the private stack, migrations, provider registration and held Mox configuration. This task does not execute that command. Do not treat a dry-run as live login, deliverability, restore or visual acceptance.

11. **Email finder (nonsecret).** Set `ELEVATEO_FINDER_PUBLIC_IP` to the public outbound IP of the email-finder worker. Use an address separate from `ELEVATEO_MOX_IPV4`: port-25 verification probes can get the sending IP blocklisted. This variable does not establish routing or IP binding; Jeison must configure and prove separate actual egress before Callum approves probing. Empty disables SMTP probing with an explicit health reason. No credentials are added. See [email finder operations](email-finder.md).

Jeison implements the setup; Jeison and Tanzeel share maintenance. Callum decides updates and approves each outward-facing or irreversible step. Use the [handoff approval gates](handoff/README.md) before execution. Fleet-01 is read-only and off limits.

Every deployment stops `mox` before running the initializer. Activation or TLS/configuration changes can make the existing files differ from the generated held configuration, causing initialization to fail before the final service start and leaving Mox stopped. Jeison and Tanzeel must develop and verify a post-activation update/rotation procedure, including recovery from that stop, before Callum approves such an update. Do not reuse initial deployment as an assumed safe live update command.
