# Nadia attachment backend slice

This is an isolated backend candidate for inbox attachment metadata and a private storage gateway interface. It is **not** a complete attachment UI, transport integration, scanner, or live mail capability. No application tests or Docker builds have run on this candidate.

## Contract and boundaries

- Additive V2 only: Cassian owns route and contract registration. Proposed upload accepts one file, a scoped organization/mailbox/thread/message identity, UTF-8 basename (1–255 bytes), and MIME allowlist `application/pdf`, `image/png`, `image/jpeg`, `text/plain`. File size is 1–10 MiB, matching the configured self-hosted Storage limit. Signature checks cover PDF/PNG/JPEG; text rejects invalid UTF-8 and NUL. The MIME allowlist is intentionally narrow and still requires scanner verification.
- `Attachments::Service#stage` checks current write capability, validates content, writes through an injected **private** storage adapter, checks capability again, and inserts a `pending_scan` row through a definer function. Repository failures leave bytes private and quarantined until exact-reference reconciliation; ambiguous commits never trigger deletion. The caller must arrange separate short authenticated database scopes around storage I/O; no database transaction may span object transfer.
- No scanner is configured in the repository or Compose. There is no API path to mark an attachment clean. All staged objects remain held; `assert_downloadable` denies `pending_scan`, `malware`, and `scan_failed` without returning bytes. An independently reviewed scanner and restricted verdict writer must be added before any object becomes downloadable.
- `assert_downloadable` requires current read authorization and exact composite identity, returning safe metadata only; Sabine owns the separate private byte gateway with two current-authority checks. Cassian must wire a bounded byte response with `nosniff`, attachment disposition, no-store, and safe filename handling. No route/contract change was made in this branch.
- Migration `20261015000015` stores composite message binding, private object key, bounded metadata and scan state. API role cannot directly INSERT; the definer checks current compose rights and message existence. SELECT inherits message/mailbox RLS. Scan status UPDATE has no API/worker grant. Populated rollback is deliberately refused to preserve metadata and objects. Database and private Supabase storage must be reviewed and run by Soren on a disposable fleet stack.

## Continuation: private object and inbound handoff

`PrivateStorage` uses the already pinned internal Supabase Storage service (`http://storage:5000`) with a private bucket and a token injected only into a restricted worker or attachment gateway. Construction rejects the API process. Requests have bounded timeouts, no automatic retry, no redirects, validated object keys, and bounded responses; errors contain no token or object bytes. The repository's existing `Config` rejects a service-role key in API, so Cassian's GET content route **must not** instantiate this adapter in API. A reviewed private gateway or scoped authenticated Storage mechanism remains necessary before route activation. No bucket or service key was created by this task.

The worker scan seam reads a pending object, verifies stored length and SHA-256, and accepts only an actual scanner adapter verdict of `clean` or `malware`. The default scanner raises unavailable; the claimed attempt records `scan_failed` and stays held for bounded retry. Migration 00015 grants only `elevateo_worker` access to pending metadata and verdict functions; API has no UPDATE privilege. A bounded ClamAV INSTREAM adapter is authored, but its private container/signature readiness and genuine verdict remain Soren-only NOT_RUN. Tests simulate a scanner verdict and explicitly do not establish malware detection.

Corin's MAIL819 inbound port is distinct from API compose: raw MIME <=1 MiB and each attachment <=256 KiB, intersecting PDF/PNG/JPEG/text. Worker pre-stages a stable private key `quarantine/imap/<account UUID>/<uidvalidity>/<uid>/<ordinal>`; `put_once` compares previously committed bytes and never deletes inbound keys on retry. Migration 00015 provides a worker-ingest-only metadata bind function with a unique account/epoch/UID/ordinal tuple, exact replay comparison, and `rejected` status/reason for invalid or oversize parts without bytes. Corin owns the later ingest function replacement that binds metadata in the same database transaction **before** advancing the mailbox cursor; migration ordering means this must follow 00015. The binder is not directly executable by the worker role. The metadata insert is not yet called by Corin's held worker source, so inbound attachments are not functional yet.

Clean-only availability is exposed after current read authorization; Sabine owns the private byte gateway and Cassian owns authenticated HTTP registration/response headers. A `rejected` status is held; optional `rejection_reason` is proposed for truthful UI copy. Mira's earlier dispatch failed, and root was asked to relay the read-only fields. Outbound attachments remain unsupported pending Rowan's immutable review binding.

## ATT823 repair and scanner continuation (source candidate)

Felix REV878 independently found three defects in 341 reviewed LOC (8.80 findings/KLOC): missing `elevateo_owner` policies under FORCE RLS, API-readable private key/SHA, and a concurrent same-source select/insert race. This candidate adds owner-only SELECT/INSERT/UPDATE policies for definer routines, removes private key/SHA from `elevateo_app_read` column grants and safe repository reads, and uses `ON CONFLICT` followed by exact tuple comparison. The repairs need independent re-review and actual-role fleet proof. Sabine owns a NEW narrow read-authority helper inside the private gateway; API direct table reads cannot retrieve private object identity. Her helper must check current session/context/mailbox read and exact composite binding before and after byte fetch, returning the immutable key/size/SHA tuple only inside the gateway.

The scan worker now discovers at most 25 due IDs, claims one with a UUID token and increasing attempt (maximum three), reads immutable bytes outside the DB transaction, verifies size and SHA, and sends them through a bounded `zINSTREAM` ClamAV client. Only an exact `stream: OK` is clean; an exact bounded `FOUND` reply is malware. Timeout, daemon error, unrecognized reply, byte mismatch or no scanner records `scan_failed` when the claim is still current and remains held. Retry has bounded delay; a stale token/attempt cannot overwrite a later verdict. The adapter pins host `clamav:3310`, has a 20-second operation deadline, a 10 MiB input cap and a bounded response. ClamAV protocol framing follows the [official clamd protocol](https://docs.clamav.net/manual/Usage/ClamdProtocol.html). Container image, signature readiness and real clean/EICAR evidence remain Soren/Leonie owned and NOT_RUN.

The API-facing service no longer returns bytes or private object keys. `assert_downloadable` returns only safe metadata after a fresh read callback; Sabine's gateway owns actual private byte retrieval and reauthorization. API/worker table writes remain unavailable except narrow definer functions. User-stage metadata errors retain quarantined bytes because a commit may be ambiguous; no automatic delete can destroy a committed object. Corin's later 00017 integration still needs to bind imported metadata before cursor advance. Outbound attachment sending stays disabled.

Authored tests, all NOT_RUN: fake Storage clean/malware/held/denied/oversize/cross-tenant/ambiguous-commit cases; fake clamd INSTREAM clean/FOUND/invalid/EOF/oversize framing; disposable actual-role SQL test for owner insert/select, worker claim/fenced failure, direct API/worker denial and concurrent identical/conflicting inbound tuple. These are not genuine ClamAV or integrated gateway proofs. The exact fleet request and review partitions are in `docs/completion/nadia-attachments-review-request.md`.

## ADV099 terminal-state replay correction

Ada reviewed exact `a4974de92984e246dd2af09334a57f548dda7f77`: one static defect in 286 migration/test LOC (3.50/KLOC). `SELECT FOR UPDATE` invokes the restrictive owner UPDATE policy and hides clean, malware and rejected rows during otherwise identical source-tuple replay. The binder now uses an ordinary immutable `SELECT` after `ON CONFLICT DO NOTHING`; its scan path changes verdict fields only, so no scan UPDATE privilege is widened. In READ COMMITTED, the conflict statement waits for its competing insert and the subsequent lookup sees the committed row. Other transaction isolation modes and Corin's actual caller need fleet proof; a missing/deleted source tuple still raises conflict. Three real-role regression cases assert that identical clean, malware and rejected replay returns the original ID without changing its terminal state. API and app-read `has_column_privilege` checks plus actual API SELECT-denial assertions cover `storage_key` and `sha256`; empty RLS results alone cannot prove private-column denial. All tests remain NOT_RUN by Nadia.
