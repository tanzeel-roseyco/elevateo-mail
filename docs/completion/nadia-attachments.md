# Nadia attachment backend slice

This is an isolated backend candidate for inbox attachment metadata and a private storage gateway interface. It is **not** a complete attachment UI, transport integration, scanner, or live mail capability. No application tests or Docker builds have run on this candidate.

## Contract and boundaries

- Additive V2 only: Cassian owns route and contract registration. Proposed upload accepts one file, a scoped organization/mailbox/thread/message identity, UTF-8 basename (1–255 bytes), and MIME allowlist `application/pdf`, `image/png`, `image/jpeg`, `text/plain`. File size is 1–10 MiB, matching the configured self-hosted Storage limit. Signature checks cover PDF/PNG/JPEG; text rejects invalid UTF-8 and NUL. The MIME allowlist is intentionally narrow and still requires scanner verification.
- `Attachments::Service#stage` checks current write capability, validates content, writes through an injected **private** storage adapter, checks capability again, and inserts a `pending_scan` row through a definer function. Repository failures delete the staged object. The caller must arrange separate short authenticated database scopes around storage I/O; no database transaction may span object transfer.
- No scanner is configured in the repository or Compose. There is no API path to mark an attachment clean. All staged objects remain held; `download` denies `pending_scan`, `malware`, and `scan_failed`. An independently reviewed scanner and restricted verdict writer must be added before any object becomes downloadable.
- `download` requires current read authorization on every call, exact composite identity, and a clean verdict; it returns bytes to a trusted Rails response adapter and never returns a public or signed URL or storage key. Cassian must wire a streaming response with `nosniff`, attachment disposition, no-store, and safe filename handling. No route/contract change was made in this branch.
- Migration `20261015000015` stores composite message binding, private object key, bounded metadata and scan state. API role cannot directly INSERT; the definer checks current compose rights and message existence. SELECT inherits message/mailbox RLS. Scan status UPDATE has no API/worker grant. Populated rollback is deliberately refused to preserve metadata and objects. Database and private Supabase storage must be reviewed and run by Soren on a disposable fleet stack.

## Continuation: private object and inbound handoff

`PrivateStorage` uses the already pinned internal Supabase Storage service (`http://storage:5000`) with a private bucket and a token injected only into a restricted worker or attachment gateway. Construction rejects the API process. Requests have bounded timeouts, no automatic retry, no redirects, validated object keys, and bounded responses; errors contain no token or object bytes. The repository's existing `Config` rejects a service-role key in API, so Cassian's GET content route **must not** instantiate this adapter in API. A reviewed private gateway or scoped authenticated Storage mechanism remains necessary before route activation. No bucket or service key was created by this task.

The worker scan seam reads a pending object, verifies stored length and SHA-256, and accepts only an actual scanner adapter verdict of `clean` or `malware`. The default scanner raises unavailable and leaves `pending_scan` unchanged. Migration 00015 grants only `elevateo_worker` access to pending metadata and verdict functions; API has no UPDATE privilege. A free local ClamAV container is a possible Soren-managed implementation, but none is configured or tested here. Tests simulate a scanner verdict and explicitly do not establish malware detection.

Corin's MAIL819 inbound port is distinct from API compose: raw MIME <=1 MiB and each attachment <=256 KiB, intersecting PDF/PNG/JPEG/text. Worker pre-stages a stable private key `quarantine/imap/<account UUID>/<uidvalidity>/<uid>/<ordinal>`; `put_once` compares previously committed bytes and never deletes inbound keys on retry. Migration 00015 provides a worker-ingest-only metadata bind function with a unique account/epoch/UID/ordinal tuple, exact replay comparison, and `rejected` status/reason for invalid or oversize parts without bytes. Corin owns the later ingest function replacement that binds metadata in the same database transaction **before** advancing the mailbox cursor; migration ordering means this must follow 00015. The binder is not directly executable by the worker role. The metadata insert is not yet called by Corin's held worker source, so inbound attachments are not functional yet.

Cassian's separate, noncanonical ATT823 draft proposes message-scoped GET list (`limit` 1..50, UUID cursor) and GET content. Backend list now returns `{items:[{id,filename,content_type,byte_size,scan_status}],next_cursor}` without a key or URL. Download is clean-only after current read authorization; Cassian still owns authorized HTTP registration, response headers, and the private byte-stream gateway. A `rejected` status is held; optional `rejection_reason` is proposed for truthful UI copy. Mira's earlier dispatch failed, and root was asked to relay the read-only fields. Outbound attachments remain unsupported pending Rowan's immutable review binding.

Additional tests authored, **NOT_RUN**: list safe projection and revocation, default scanner hold, simulated verified clean, tampered bytes and invalid verdict rejection, private Storage API-process denial, stable inbound retry byte mismatch. Request Soren run the bounded unit suite in a fleet Docker container and add a disposable real-PostgreSQL fixture for RLS/definer grants, imported replay, rejected metadata, and cursor rollback.
