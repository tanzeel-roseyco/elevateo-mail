## Confirmed defect

**MEDIUM — immutable retry fingerprint omits an effective mutation flag** (`repository.rb:137–154`, `161–174`). `replace` fingerprints kind, resource ID, expected version, `intent_fields`, and actor, but excludes `preserve_consent`. For a lead, `preserve_consent=true` executes a version-only UPDATE while `false` writes consent fields and an event. With the same organization, operation ID, input, intent, actor and version, an opposite-flag retry matches the prior fingerprint at line 152 and returns the stored result at line 154 without performing the requested behavior. Include the flag in the fingerprint and test opposite-flag reuse in both directions under the same operation ID; retain exact replay for an unchanged flag. The branch is source-proven; no claim is made that the current HTTP controller exposes both flag values to one caller. Cassian and root were notified immediately.

## Coverage and limitations

- **Purpose and authority:** creates inert campaign/lead/account rows, checks account mailbox visibility, uses tenant predicates for replay, page/detail, suppressions and analytics, and uses a transaction advisory lock for mutation replay. The comment makes the caller responsible for the SessionWrites tenant frame and CSRF guard. Repository itself does not assert an open protected transaction, current role, or campaign-specific authority; those call sites, RLS and schema are outside the assigned 385 LOC, so end-to-end authorization and rollback are unverified here. A role change between original mutation and replay needs an authenticated DB/HTTP regression on the integrated seam.
- **Scope and state:** page filters tenant and optionally campaign and caps `limit` at 1–100 with one extra row for the next cursor. Detail filters tenant and ID. `replace` first checks the mutation ledger, then updates, inserts a consent event where applicable, projects the row and stores the response. These effects depend on the caller's transaction for atomicity. On a lead/account update miss, the visibility probe at lines 181–183 checks only organization and ID, not campaign ID; thus a wrong-campaign request for an otherwise visible row yields `draft_conflict` rather than scoped `not_available`. Whether that is a security issue depends on campaign-level authority and controller error mapping, which were not reviewed. For `page(kind: 'campaign', campaign_id: nonnil)`, lines 115–123 add a campaign filter even though the campaign INSERT does not name such a column; the repository does not reject this invalid scope combination, and actual schema/HTTP reachability were not inspected.
- **Input bounds and errors:** `save` requires an `Input` object, `page` caps result count, UUIDs are parsed, suppression reasons are enumerated, and replace version/boolean are validated. Null, empty lists, nested intent values, maximum email/label lengths and timestamp semantics rely on `Input`, `WriteInput` and DB constraints outside scope. `rows` binds values rather than interpolating them; interpolated table/selection strings are internal allowlist returns. `CollaborationError` is used deliberately for absent, conflict, mismatch and internal timestamp errors.
- **Consent lifecycle:** suppression insert is idempotent and global by organization/email; lead projection combines local and global suppression. Consent mutation records actor and event after UPDATE, but reviewed tests do not exercise grant/revoke, suppression, preserved-consent mode, or atomic event rollback. Existing tests may live elsewhere; no claim is made about them. This assignment cannot establish immutable consent history or role-revocation handling without real PostgreSQL tests.
- **Performance and design:** page is bounded to 101 rows and projects each row once. Analytics aggregates all leads for a campaign and joins suppression rows, which requires index/query-plan evidence on realistic sizes; no latency, memory, row count or plan was measured. Advisory lock hashes only operation ID, potentially coupling same UUID across tenants; no measured contention or practical collision claim. The 252-LOC repository combines creation, read paging/detail, suppression, analytics and mutation ledger logic; consider splitting only if owner-maintained call sites show pressure, rather than prebuilding abstractions. SQL selection and projection remain centralized, with no obvious nested loops.
- **Tests and documentation:** the 133-LOC fake-connection suite has eight tests covering create success/replay/mismatch, missing tenant replay, mutation success/stale version, one-row pagination and stored-result replay. It does not test real SQL, RLS, transaction rollback, account mailbox access, lead consent/suppression, maximum limit/cursor failure, opposite `preserve_consent`, or role change. Documentation outside the two assigned source files was not read, so documentation synchronization cannot be confirmed. Styling and type gates belong to fleet linters/Steep under Soren.
