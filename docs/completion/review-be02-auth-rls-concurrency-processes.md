### Confirmed findings

1. **MED — error oracle matches a prefix, not the exact reason** (`processes.sh:103-107`). `grep -Fq` accepts any line containing the expected `ERROR:  SQLSTATE: reason` substring. For example, a sole `ERROR:  P0001: Auth additional session policy drift: <injected_name>_other` also satisfies the expected injected-name oracle, as does the expected lock-timeout text followed by unexpected extra diagnostic text on that line. Exactly one ERROR line and psql exit 3 do not fix this ambiguity. This is a test-oracle defect, not proof that the frozen production SQL currently emits such a message. Repair: account for the known psql filename/line prefix, then compare the complete severity/SQLSTATE/message portion exactly, preserving the one-error requirement. Acceptance in Docker: exact intended lines pass; appended policy-name characters, prefixed message content, wrong SQLSTATE, duplicate ERROR lines, and matching text inside a different diagnostic fail. Retain the complete real-production schedules as integration coverage.

2. **MED — late connection can escape final server-absence accounting** (`processes.sh:124-142,153-154`). Cleanup takes one named-session discovery snapshot before stopping child clients, then builds the termination and final absence predicate exclusively from captured backend identities. Concrete interrupted-start schedule: a child has been launched but its normal capture has not completed; cleanup's discovery query sees no backend; the connection appears immediately afterward; client termination occurs while the server is still processing startup/query/disconnect; no backend identity was recorded, so that child is absent from both the termination query and final absence query. The latter can report zero without observing this named session at all. The main probe remains failed when entered through interruption or a failed barrier; this finding does not claim that an unestablished schedule becomes PASS. It invalidates the stronger claimed cleanup guarantee on every terminal path, and can leave cleanup success unproven until outer cluster teardown. Repair: after clients are positively stopped/reaped, perform a fresh bounded discovery/absence check over all registered application names with database/user constraints; validate PID/start identity before terminating newly observed owned sessions, and fail closed on changed/ambiguous identities. Do not broaden kill authority to an unchecked application-name wildcard. Acceptance in Docker: delay backend visibility until after the first cleanup discovery, interrupt between launch and capture, and require either observed exact termination plus verified absence or an explicit cleanup failure; never accept an empty captured-identity set as absence of a launched child. Also cover connection never established and same-name changed-identity rejection.

### Verified structure and remaining acceptance

- Positive barriers: capture rejects empty/multiple/non-numeric PID/start results; identity combines PID, start timestamp, exact application name, database and user. Holder readiness requires its actual marker query, ClientRead, idle transaction and granted AccessExclusiveLock on the exact relation. Waiters require active lock wait, the expected LOCK statement, ungranted relation lock and holder membership in blocker PIDs. The two-waiter aggregate requires two rows. A slow host or a missing waiter fails, rather than turning sleep duration into evidence.
- Timeout paths: control queries have timeout/kill grace, connection attempts have a cap, observation barriers reject late observations, children have independent timeout wrappers, completion waits have an 18-second cap, and the top watchdog bounds work. A query started near a barrier deadline can overrun that nominal barrier by its own bounded query timeout; it cannot establish success after the deadline. These are bounded polling envelopes, not exact wall-clock deadlines.
- Exit/identity evidence: the asynchronous child PID is captured immediately with `$!`; successful termination is followed by `wait` status, exact fresh admin/READ COMMITTED identity output, then server and lock disappearance. Real production SQL runs directly via `--file`, after an identity-only command; there is no copied or rewritten transaction. Full production policy behavior and catalog preservation require the separate reviewers.
- Cleanup ownership: the code signals recorded timeout-wrapper child PIDs, uses validated numeric server PID/start plus names/database/user for server termination, rejects replacement identities, shares a five-second client grace, and reaps only after exit observation. Escalation to SIGKILL marks cleanup failure. Under a normal successful schedule every child was captured and already verified disconnected; the late-capture finding concerns exceptional startup cleanup. Outer disposable-cluster reconciliation remains mandatory on interruption or SIGKILL.
- Inputs and state: names derive from a validated private temporary token and internal constants; no raw user-provided SQL enters these helpers. Empty query results retry or fail, ambiguous capture fails, missing tools fail before the schedules, and secrets are not printed. Authentication/image provenance and catalog preflight internals were not independently reviewed here. The local requirement of happy path plus two failure schedules is authored; shell cleanup fault-injection evidence is still missing.
- Design tradeoff: retaining the production timeout and transaction untouched makes the integration test representative, at the cost of failure on hosts too slow to establish overlap. Simulated reasoning: both waiters observed before release yields valid serialization evidence; first timeout before the second waiter appears yields failure; DDL commit before a positive waiter observation yields failure. These are analytical schedules only, not measured results or Obsidian execution. Separate design/catalog reviewers own broader tradeoffs; this worker did not access Obsidian or spawn agents.
