## Design tradeoff simulations for root

1. **Admin absent from first grant page.** A list-only UI would treat that page as proof of no management authority and hide all edits, or incorrectly infer authority from title. FE808 completes bounded pagination before computing a conservative role hint. Sabine's new protected actor projection would remove dependence on list position; Cassian's strict DTO must include it before FE808 can consume it.
2. **Role change races revocation.** An admin selects `sales_lead` for a target at revision 4, while their own admin role is revoked. The UI sends the target UUID, expected revision and current session proof once. The server must reject if revocation wins; FE808 drops stale responses via `useProtectedRequest`, freezes controls on failure and never replays the old mutation. A successful response also freezes controls until session refresh.
3. **Unbound reference resembles an active person.** An organization roster contains `elev-person-001` named Allan, while an unrelated active Auth UUID appears in grants. FE808 never joins the two by name or title. A verified roster only confirms configuration display; no grant write uses the config key. This costs a less friendly active-grant label (opaque UUID) until verified enrollment mapping exists, but avoids fabricated access.

These are source-level scenarios, not executed acceptance evidence. Actual vault updates remain root-owned.
