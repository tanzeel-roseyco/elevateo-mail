## Analytical schedules and tradeoffs

Obsidian is unavailable. The following are **analytical simulations, not executed experiments**, and do not claim a connection, measured timing, or passing test. They preserve the private real Rails/Auth/PG stack, same-origin `http://app.test`, supported Auth-admin creation of nine users, closed external mail, no public test endpoints, no production credentials, and no UI edits.

### 1. Response loss after COMMIT

Start with author A, draft D at version n, operation O, frozen submission F, and a distinct later local buffer L. Capture O/F only inside the private harness. Forward the authentic PUT; hold its response. A new DB connection must observe O's applied outcome, D at n+1, and exact F (compare privately; export only bounded synthetic proof). Only then abort browser delivery. Confirm the editor becomes uncertain rather than claiming no save. Reconnect and query O through the actual API; the applied receipt resolves F while L remains unsaved. A same-O retry, if part of the accepted UI flow, must not create n+2 or a second operation.

Observations must establish `DB commit visible -> response dropped -> same-O recovery`; waiting an arbitrary duration cannot substitute. Receipt status alone is insufficient for the independent DB lane. Holding a genuine response preserves application semantics with less intrusion than a post-COMMIT Rails hook. If the driver cannot forward/hold that response faithfully, leave the case blocked and review an internal response gate; do not synthesize a 200 JSON response.

### 2. No-commit loss and missing lookup

Capture the attempted O/F and abort before any upstream dispatch; never release that request later. Await route completion and inspect a fresh DB snapshot: no O and D remains at n. Perform a real lookup of O that returns the accepted missing/unknown outcome. The harness knows why this attempt had no effect, but the browser's missing lookup does not establish that knowledge generally: retain O/F/local text and remain uncertain, without minting a replacement operation.

This schedule covers the pre-forward loss/missing-lookup partition. It does **not** demonstrate rollback after Rails received a request, a native PG timeout, or a request cancelled during COMMIT. Those need their own acknowledged backend cuts and final transaction-state observation. A snapshot taken while a held transaction might still commit cannot prove no effect. Do not add a new save intent merely to make the test finish successfully.

### 3. Concurrent logout/write

Use two pages of the **same authenticated session**, not two independent logins that revoke different sessions. Give write O a unique draft and preserve its submission.

| Schedule | Required observations and result |
| --- | --- |
| Write wins | The real write has acquired the accepted session guard; its test-only barrier acknowledges that phase. Start logout and prove it reached the competing guard. Release the write; observe its durable result before revocation can win. Logout then completes. Later protected calls deny, and a delayed earlier response cannot resurrect the UI. A previously committed authorized write is not retroactively rolled back. |
| Logout wins | Hold the write before acquisition of the same guard, complete and independently observe session revocation, then allow the write to attempt acquisition/recheck. The write must not apply; DB observation confirms unchanged D/no applied O. UI denial/uncertainty follows the actual contract. |

Reuse an accepted internal barrier if available and separately reviewed; otherwise add a narrowly keyed test-only gate. It must observe/wait at the existing production lock order, not implement a second authorization algorithm. A runner-controlled private pipe/socket or equivalent internal harness channel is preferable to an HTTP test route. Missing acknowledgements fail the test; timers are watchdogs, not the mechanism that decides which transaction won. Server deadline observation does not prove rollback or a guaranteed ten-second return. This is the only listed product transaction-order gap that necessarily needs deeper-than-browser phase observation.

### 4. Another author's private draft

In one primary mailbox, A=`composer` creates a unique D and reads it; B=`approver` has legitimate mailbox read/compose yet is not D's author. B lists drafts, deep-links/GETs D, and, if the wider security sample is claimed, attempts a protected mutation/operation lookup. Test those added endpoints against their exact contract in a new bounded assignment. A reads D again to rule out deletion as the explanation for B's empty/denied view. Independent DB evidence can establish D still belongs to A; privileged DB visibility does not itself prove RLS.

Repeat the ordering with B's request held at the browser while A saves a new version, then release the genuine B request. B still receives no author's content. UI assertions inspect summaries, editor fields and stale content, not just a 404 status. The manager role is not an author-privacy bypass. Shared mailbox membership is essential here; using `other_org` alone tests tenant isolation instead. No special privacy seed is needed beyond the existing two composing actors and a unique real draft.
