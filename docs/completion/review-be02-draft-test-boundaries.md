**DTB-01 — MEDIUM: the fixture helper can mask a broken authorization-generation lock.** Location: `test/be_02/draft_database_test_helper.rb:24-29`, especially line 26; the assigned revocation setup uses this helper at `draft_authorization_test.rb:35-37`. The helper locks every session row in the organization before acquiring generation guards. A concurrent draft save already holds its own session lock under the published write contract, so a revocation using this helper can wait on that same session even if generation locking is missing or ineffective. Merely observing a PostgreSQL lock wait would then appear to prove the intended revocation guard while exercising a stronger administrative locking path. The documented production membership path locks the acting request's session and affected generations; it does not first lock every target session. This is an analytical false-positive scenario, not an executed race and not a finding about the unreviewed concurrency test implementation. Minimal fix: retain a convenient setup helper if needed, but use a distinct authorized manager session and the published membership mutation boundary for race evidence, with no broad organization-session prelock. Regression: hold a compose save after its generation guard, start revocation from a different session, establish that blocking depends on the affected generation guard rather than the saver session, and prove both commit orders. After revocation commits first, stale valid context is 409; after a fresh context/bootstrap, missing compose is generic 404. Do not require an after-snapshot read to retract an already authorized whole response.

**DTB-02 — MEDIUM: the composite-scope tests never cross an organization boundary.** Location: `test/be_02/draft_authorization_test.rb:46-59,62-77`, with the one-organization fixture in `draft_database_test_helper.rb:10-14`. The random missing reply at lines 55-56 proves only a dangling reference is rejected. The real second mailbox and thread at lines 65-68 deliberately use the same `@org`, so they test mailbox mismatch but cannot distinguish removal of the organization component from a composite relationship or an organization predicate from scope authorization. A user with memberships in organizations A and B could then reference B's mailbox while the current session is scoped to A, yet every assigned fixture remains satisfied. This finding is limited to these assigned tests; other suites are unreviewed. Minimal fix: add a genuine organization B, real current memberships and a mailbox/thread there, ideally using the same actor in both organizations so actor ownership alone cannot cause denial. Regression: while scoped to A, foreign B save/lookup and a B reply under an A mailbox return generic not_available without changing either draft or ledger; administrative attempts to create cross-organization composite rows fail. Also verify permitted own saves separately in each context and keep the same-organization/wrong-mailbox case.

**DTB-03 — MEDIUM: the 101-recipient rejection can pass for an unrelated schema error.** Location: `test/be_02/draft_payload_test.rb:49-56`, specifically `{ "to" => [{}] * 101 }` at line 50. **DTB-04 — MEDIUM: the cursor fixture cannot distinguish an included row from the excluded lookahead row.** Location: `test/be_02/draft_reads_test.rb:49-59`. Both rows supplied at line 50 come from `row`, so they have identical `id` and `updated_at` values. With limit 1, generating the cursor from the second, omitted row therefore produces exactly the same bind values as generating it from the included row; the assertion at line 59 cannot detect the error. With real distinct rows, that regression skips a draft on the next page. The fixture also represents duplicate primary keys rather than a possible two-row database result. Minimal fix: give the two rows distinct canonical IDs and ordering keys and assert the page contains exactly the included row. Regression: decode/reuse the issued cursor and assert its seek tuple comes from the included row, not the lookahead; continue a page to establish that the lookahead appears exactly once and terminal next_cursor is null. A separate equal-timestamp/different-ID case should exercise the descending UUID tiebreaker. SQL execution remains the integration owner's evidence requirement.

**DTB-05 — MEDIUM: recipient-order preservation has no discriminating assertion.** Location: `test/be_02/draft_payload_test.rb:20-45`, particularly the test named `test_null_empty_order_and_operation_key_have_the_prescribed_meaning` at lines 32-38. All reviewed recipient examples are empty, one entry, or 100 identical entries; none compares two distinct recipients in opposite orders. A digest implementation that sorts recipients before hashing therefore satisfies the assigned assertions while violating the exact ordered canonical array. Reusing an operation ID after intentionally reversing recipients could then be treated as an identical replay instead of operation_mismatch. Minimal fix: assert exact canonical bytes for two different valid addresses, reverse their order and require a different digest; preserve the existing null/empty and operation-ID checks. Regression: the two orderings have different digests, reordering keys within either Address object does not change its semantic digest, and the integration ledger treats same-ID/different-order input as operation_mismatch without replacing the record. The latter ledger behavior belongs to the unreviewed integration suite.

**DTB-06 — MEDIUM: absent direct GET accepts any CollaborationError.** Location: `test/be_02/draft_reads_test.rb:65-74`, especially lines 72-74. The scope-denial branch verifies not_available, but the absent-draft branch only checks the exception class. Returning context_changed, request_invalid or internal_error for an authorized missing draft would still pass the test named to prove it is unavailable. Minimal fix: capture the second exception and assert code not_available and the exact generic message `This item is unavailable.`; assert HTTP 404 and the closed error envelope in the request-level counterpart. Regression: a valid current-context missing draft, a foreign-author draft and an inaccessible draft have the same 404/code/message, with no content or identity leak; invalid/revoked authentication remains 401 ahead of stale-context 409. The existing class-only assertion must reject an injected wrong collaboration code. No assertion is made that the current unreviewed implementation returns a wrong code.
