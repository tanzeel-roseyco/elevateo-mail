## Actionable findings

1. **Medium: replay assertion can miss an extra intent** (`http_approval.rb:47-55`). The response's send ID is stable, but the count predicate includes that send ID. A buggy replay that inserts another intent with a different send ID while returning the original response still satisfies both assertions. The executor is explicitly scoped to the original send ID (`app_chain_test.rb:125`), so its second `:idle` does not inspect an extra send either. Assert exactly one intent for the draft without filtering by send ID, then separately assert its ID matches the HTTP response. This is an oracle defect, not evidence that the current production API actually duplicates intents. A uniqueness constraint could prevent this scenario, but that constraint is outside this packet and should not be silently assumed as the test's proof.

2. **Medium: recipient oracle does not prove approved-send identity or uniqueness** (`app_chain_test.rb:121-129,135-150`). `verify_reply` receives the original RFC identity but not the approved send ID; it accepts the first message with matching nonce subject/body, From and ancestry. A second unintended send of the same content can satisfy it, and multiple matching deliveries also pass. Bind the received Message-ID to the canonical identity derived from the returned approved send ID (using the existing identity contract, not a second independent formatter), assert intended To, and count matching messages over a defined observation interval if duplicate-delivery absence is claimed. Keep any assertion scoped to the test interval; this cannot establish universal exactly-once SMTP. The initial inbound leg already binds its RFC ID to `initial_id` at line 107, making the missing equivalent outgoing assertion particularly clear.

**Accounting:** 2 test-oracle defects / 244 LOC = **8.20 defects/KLOC**. No demonstrated production authorization defects; no repairs by this reviewer. Coverage limitations below are not counted again as additional defects.

## Design tradeoffs and rubric disposition

**HTTP approval versus SQL fixtures.** HTTP exercises route/controller validation, authenticated identity, CSRF, draft/review versions, approval grant, response mapping and replay. It closes the previous architectural gap where a successful SQL fixture could bypass a broken public approval path. Privileged SQL remains appropriate for synthetic domain/account/consent setup and observation, but cannot prove provider verification, real consent, tenant bootstrap or production readiness. The small approval helper split is proportionate; no new service abstraction or infrastructure is justified.

**Identity and causality.** The chain composes real SMTP, IMAP ingestion, SQL-backed reader, HTTP approval and a real transport executor. Distinct nonce and original RFC-ID ancestry are materially stronger than SMTP acceptance or subject-only matching. A named send-ID executor gives deterministic attribution and avoids draining unrelated test work; the tradeoff is that it does not prove normal scheduler discovery, all-queue emptiness or independent worker-process configuration. Findings 1 and 2 should be fixed before claiming replay-safe approved-send causality. Thread causality is demonstrated for one simple original/reply, not multi-message References chains or conflicting ancestry.

**Cost and reproducibility.** Real auth/database/Mox integration is slower and more fixture-sensitive than unit tests, but valuable as one small source-bound smoke. Retain deterministic focused tests for races, ambiguous SMTP outcomes, validation limits and failure transitions rather than expanding this single end-to-end case into every boundary permutation. The documentation explicitly identifies an older baseline configuration versus concurrent OIDC changes; execution on that baseline cannot certify current OIDC integration. Require final source hashes, non-skipped case/assertion counts, exact fleet image/network and cleanup receipts. This reviewer ran no tests and transfers no historical PASS.

**Held production outbound.** The packet deliberately writes `outbound_held:false` to a temporary worker control file while using the production transport class and routable-looking host/domain names. This is acceptable only in the independently verified synthetic Docker network. Neither the environment guard nor a comment establishes isolation. The report describing held API/production settings is contextual evidence, not independent verification of the unreviewed harness. No production control changes or live sends were performed here; production outbound must remain held.

**Maintainability, state and security.** Version/digest checks, parameterized SQL, private credential-file mode and explicit denial codes are useful. Helpers have coherent roles and intent comments; no overengineering, hot-path query regression or new abstraction need is visible. Fixture setup and cleanup are inherently stateful; superclass ownership and failure cleanup remain dependencies. Null/empty external API inputs, oversized recipients/body, mismatched replay payload, concurrent approval, stale-session revocation and worker unknown outcomes are not covered here. They require existing focused-test evidence rather than claims from this happy-path smoke. Documentation honestly states runtime in progress and no release authority. Frontend/manual visual validation is outside this non-UI review.

Recommended disposition: repair the two oracles, preserve the narrow acceptance label, then have the existing test owner run the source-bound fleet Docker gate and independently verify network containment and cleanup. This report is a bounded design review, not whole-application approval.
