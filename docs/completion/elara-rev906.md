## Source observations

1. The top action now requires a ready reader, ready session, mailbox compose capability and a usable sender. With `?message=`, it uses only the matching loaded message or a validated direct-message response; while unresolved, unavailable or failed, the top action is disabled. Without selection, it chooses the latest loaded message with a usable sender. The direct-message read already checks context, authorization version, mailbox, thread and message identifiers before exposing its result (ThreadPage.tsx lines 183-228). A malformed sender with CR/LF or angle brackets is rejected by `replyAddress` (lines 47-50).
2. `replyToMessage` creates a fresh local intent keyed to actor, organization, mailbox and draft, with selected sender, `Re:` subject and `reply_to_thread_id`; it navigates to the draft editor without calling save (ThreadPage.tsx lines 91-102). The inspected editor handoff restores retained intent only after its guarded draft read path or expected new-draft 404 (DraftEditorPage.tsx lines 129-132 and 167-193). This is a UI observation, not a complete backend authorization review.
3. Tests added for sender prefill, no sender, loading and read failure, selected on-page message, unresolved and failed direct message; CollaborationPanels replaces a stable-link assertion with explicit save and bound-thread assertions. Existing test at ThreadPage.test.tsx line 208 asserts saved `reply_to_thread_id`, subject and recipient. No test was executed here.
4. Design tradeoff: using the top button and per-message buttons through one `replyToMessage` path avoids an empty compose link and duplicate draft logic. The per-message action intentionally answers its own message even when another URL selection exists. The latest usable sender fallback on unselected paged data is practical but is limited to loaded messages; it does not promise the latest message in an unloaded continuation. The new array copy/reverse scan is linear per ready render; thread page limits were outside this packet.
