# INT-801 outbound attachment contract decision packet (proposal)

2026-10-14. Source inventory and design proposal only; no API, SQL, browser, worker or Docker result. Keep the currently activated inbox candidate immutable while owners review this separate V2 slice. No live send or credential enrollment follows.

## Existing seams and incompatibilities

- `contracts/v1/openapi.json` freezes draft save without attachment fields and send review with `attachments: []`, `attachments_supported: false`. `apps/server/lib/elevateo/drafts/payload.rb` accepts an exact seven-field body. No V1 shape can carry a draft attachment reference without breaking BE02/BE03.
- `apps/server/lib/elevateo/attachments.rb` stages a 1-byte to 10 MiB private object against an **existing inbox message** tuple, with current write checks around object I/O. `attachments_repository.rb` calls `app.stage_inbox_attachment`; these are not draft objects. The current V2 registry only activates inbox list/content GET. Reusing its message binding for outbound would grant the wrong authority/lifecycle.
- `send_api/canonical.rb`, `send_api/review.rb` and `db/be03_send/canonical.sql` bind an empty attachment array in `elevateo.send.snapshot.v1`. `db/be03_send/approve.sql` stores exactly that format and an immutable <=1 MiB snapshot. `send_worker/smtp_snapshot.rb` rejects nonempty attachment arrays and renders text/plain MIME capped at 524,288 bytes. `smtp_transport.rb` has a held remote profile and a local `.invalid` Mailpit profile. Rowan's `worker_authority.sql` final attempt guard protects the existing snapshot; it does not authorize outbound private bytes.

## Proposed V2 interface (requires Nadia, Rowan, Mira and root agreement)

1. **Stage one private object:** `POST /v2/mailboxes/{mailbox_id}/drafts/{draft_id}/attachments` with a single bounded binary body and declared filename/content type, an `operation_id` UUID idempotency key, current session/context/Origin/CSRF, and no Storage token or object key in any response. Response `202` returns only `{id, draft_id, filename, content_type, byte_size, scan_status:"pending_scan"}`. Keep the upload limit separate from the existing 10 MiB inbox limit; recommend an initial **1 MiB outbound cap**, with rendered-MIME budget checked before review. The precise body transport (multipart versus raw bytes plus bounded headers) belongs to Nadia/Cassian implementation review; request validation must reject duplicate/unknown fields and redirects.
2. **Inspect and bind:** `GET /v2/mailboxes/{mailbox_id}/drafts/{draft_id}/attachments` returns at most one safe metadata item with `pending_scan|clean|malware|scan_failed|rejected`; `PUT /v2/mailboxes/{mailbox_id}/drafts/{draft_id}/attachments/{attachment_id}/binding` uses `{operation_id,expected_draft_version}` and atomically selects that exact clean, owned, immutable object for the editable draft, increments draft version, and records replay. A replacement/removal is another versioned operation, never a mutation of object bytes. A viewer cannot stage or bind. Session/org/mailbox/compose authority and row identity are rechecked after storage I/O and in the binding transaction; object transfer never holds a DB transaction.
3. **Idempotency and failure:** Unique `(organization_id,actor_id,operation_id)` stage ledger records the canonical request digest, object ID and final outcome; identical retry returns the same ID/state, different bytes/filename/type/draft returns `409 operation_mismatch`. An ambiguous metadata commit leaves bytes quarantined for exact-reference reconciliation; it must not delete a potentially committed object. Binding has a separate operation ledger and replay result. Revocation during stage denies binding. Foreign or stale IDs return non-enumerating 404; held verdict returns 423 and no byte route; invalid/oversize/type returns 400 or 413 as versioned closed errors.
4. **Review and approval:** Add `GET /v2/drafts/{draft_id}/send-review` and `POST /v2/drafts/{draft_id}/send-approvals` only after Rowan supplies a versioned snapshot/SQL validation path. Its canonical `elevateo.send.snapshot.v2` references one ordered tuple `{attachment_id,sha256,byte_size,content_type,filename}` plus draft version, actor/mailbox/policy binding; the digest covers that exact tuple. A successful review requires `clean` and a current private byte hash match. Approval under existing lock order rechecks current compose/approve authority and the exact clean tuple, then stores the immutable snapshot and approved attachment reference atomically. Any reference, bytes, verdict, policy or draft-version change yields `review_stale`/held before new authorization. V1 review/approve and snapshot validation stay byte-for-byte frozen.
5. **Worker:** A separate V2 final-attempt guard obtains an exact fenced approved reference, rechecks authority/verdict/hash/length and renders multipart MIME from private bytes in the restricted worker/gateway process, never API/browser credentials. It must fail closed before first possible SMTP I/O on mismatch or unavailable Storage, preserve Rowan's one-attempt uncertain/reconciliation semantics after possible I/O, and keep remote delivery held. The worker output budget and deadline must be separately reviewed; the existing text-only 524 KiB renderer cannot silently accept a 1 MiB file.

## Decision and test simulations

- **Choose draft-owned staging over inbox-message reuse.** It adds one new relation and V2 operations, but makes compose authority, draft version and cleanup explicit. Reuse saves schema code while falsely assigning an unsent file to a received message and bypassing draft approval binding.
- **Choose immutable reference, not embedded bytes in the approval snapshot.** A 1 MiB object plus MIME encoding exceeds the current snapshot/renderer limits; a digest/metadata tuple fits the existing snapshot-size envelope but requires private worker retrieval and exact hash verification. To keep the old worker untouched, version the snapshot/renderer/SQL path rather than widening V1 acceptance.
- **Stage succeeds, metadata commit fails:** quarantine object and reconcile by operation ID; never advertise a bound file. **Scan finishes after review:** review remains held until clean; no optimistic send. **Same operation retried:** return one immutable reference. **Bytes replaced after approval:** hash mismatch holds before I/O. **Revocation after staging:** binding/approval deny. **SMTP times out after possible submit:** retain unknown and no automatic replay.

## Root decision and interface freeze request (2026-10-14 18:53 UTC)

Root accepted draft ownership and a one-file **1,048,576-byte raw maximum**, with a separate proposed **2,097,152-byte maximum for the complete rendered V2 MIME message**. This deliberately differs from ADV161's 256 KiB/524,288-byte minimum-scope recommendation: common 1 MiB documents remain useful, while Rowan must explicitly implement and test the larger V2 multipart renderer and transport deadline/buffer budget. The V1 524,288-byte text-only limit and all V1 schemas remain frozen. Even a 1 MiB file can exceed the 2 MiB complete-MIME cap when the body is large; V2 review must return a closed `message_too_large` issue before approval, with no truncation.

The proposed exact owner split reserves migration `20261015000020` for **Nadia** only: draft-owned attachment rows, reservation/operation ledger, scan integration and versioned selection functions. Migration `20261015000021` is reserved for **Rowan** only: V2 approved snapshot/SQL validation and fenced worker authority. No current branch has either number; reservation is a coordination decision, not a migration file. Keep root's 19 existing migrations unchanged. Nadia and Rowan should confirm both numbers before authoring.

Recommended HTTP transport: one raw `application/octet-stream` POST body, read with a strict 1,048,577-byte cap, plus canonical single-value control headers `X-Attachment-Operation-Id` (UUID), `X-Attachment-Filename-B64` (unpadded canonical base64url of 1–255 UTF-8 filename bytes), and `X-Attachment-Declared-Type` (one exact allowlisted MIME). Reject duplicate/coalesced/unknown `X-Attachment-*` headers, malformed decoding and type/signature mismatch before storage. This avoids multipart parser field merging and preserves arbitrary validated Unicode names without non-ASCII header ambiguity. The header names/encoding are a **proposal for Nadia/Cassian confirmation**, not a published contract. Never trust `Content-Length` alone; stream with a byte cap and compute the SHA-256 over the actual body. An absent/malformed length does not bypass the cap.

Proposed operation names and response seams for owner confirmation: `stageDraftAttachment` POST `/v2/mailboxes/{mailbox_id}/drafts/{draft_id}/attachments`, `listDraftAttachments` GET on that collection (safe metadata only), and `replaceDraftAttachmentBinding` PUT `/v2/mailboxes/{mailbox_id}/drafts/{draft_id}/attachment-binding` with strict `{operation_id,expected_draft_version,attachment_id}` where `attachment_id` is UUID or null for removal. Success returns exact new version, selected safe metadata or null and replay flag; no object key/digest/credential escapes. Stage operation must be **reserved durably before object I/O** under `(organization,actor,operation_id)` and request digest; a concurrent identical retry returns the same result or bounded `operation_in_progress`, never performs a second independent upload. A conflicting payload returns 409. After I/O, a fresh session/context/compose/draft check precedes metadata commit; ambiguous outcomes quarantine bytes for reconciliation. V2 review and approval operation names remain `getDraftSendReviewV2` and `approveDraftSendV2` until Rowan confirms exact authority inputs and error set.

Required explicit byte order: private fetch/hash/render first, then Rowan's final current Auth/cancel/lease fence immediately before first possible SMTP I/O. This makes cancellation during retrieval effective. An already possible submission retains existing unknown/reconciliation behavior. Root retains all live transport held; no generated DTO or Rails route is activated by this packet.

## Rails boundary inspection (source only)

`V1::WriteController#protected_write` is explicitly JSON-only: it calls `WriteInput.transport!` (`application/json`), `WriteInput.read` (which force-encodes UTF-8), and `WriteInput.body` (closed JSON object). Do not adapt it in place for binary upload, because that would broaden frozen V1 writes and mis-handle arbitrary bytes. The outbound POST needs a separate V2 binary boundary that checks the same Origin, CSRF, current session/context/version and deadline rules, enforces the 1,048,576-byte cap on the actual stream, validates canonical single-value metadata headers, and hands bytes to Nadia's stage service only after a durable operation reservation. It must exit the database transaction before private Storage I/O and re-enter fresh authority afterward. The initial boundary may call existing pure UUID/text validators, but must not route the binary through `WriteInput.body` or log payload/header secrets. This is a source design finding, not an implemented controller or runtime result.
