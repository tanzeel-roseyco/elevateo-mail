# BE02 pool disposition amendment

Adopted by the coordinator on 2026-10-13 for the already authorized local repair. This supersedes the unconditional prohibition on holding an outer pool monitor during abnormal removal in `be02-write-deadline-decision.md`. It does not approve deployment or certify runtime behavior.

<!-- AIDEV-NOTE: A queue lease uses the pool monitor, so adapter locking alone cannot protect rejected handoff cleanup. -->

The dedicated design review found WD-DESIGN-01, one HIGH defect over 295 reviewed source lines (3.39 defects/KLOC). A failed post-checkin acceptance can expose the adapter to a waiter before cleanup. Worse, cleanup can observe a nil owner and then disconnect a new owner. A callback can also remove registration before Rails enqueues an unregistered adapter. The schedules and pinned Rails 8.1.4 facts are in `review-be02-write-deadline-design.md`; this decision is analytical, not executed evidence. Obsidian is unavailable.

Use the existing public Rails pool methods; do not mutate queue/registry instance variables in production or introduce a general connection framework. Preserve adapter-before-pool lock order. Establish exceptional disposition before checkin can publish or clear ownership, covering exceptions and nonlocal exits. A fully completed, registered, correctly transferred checkin records handoff under the pool monitor. Any later observed expiry suppresses the response and must never dispose of that transferred adapter.

For rejected or partial checkin, retain the pool monitor across current-owner validation and the single supported `pool.remove` attempt. A nil owner is safe to act on only while the same monitor excludes a queue lease. Never unwind the protected section while a rejected adapter remains available. Record the removal attempt and its error; outside cleanup must not blindly call remove again. After proven detachment, release the pool monitor and attempt disconnect even if removal raised during replacement creation. Refuse a pre-existing foreign owner without removal or disconnect. Registration absence alone is insufficient proof of queue detachment after a callback anomaly.

Rails 8.1.4 exposes no public available-queue membership query. The repair may use one narrowly scoped, read-only inspection of the pool's available queue under that same pool monitor to prove detachment. Pin and document this private seam, check the expected queue shape, and fail closed when inspection is unavailable or inconsistent; an inaccessible queue is never an empty queue. Do not mutate either private structure. Inspect registration and queue membership together, preserving foreign-owner protection. The pinned source is `activerecord/lib/active_record/connection_adapters/abstract/connection_pool/queue.rb` at Rails tag `v8.1.4`; `remove` may delete registration before queue deletion and may raise afterward while replenishing.

Pre-publication disposal may remain outside the pool monitor only when ownership and the inability of another request to lease the adapter are established. Otherwise use the same protected validation/removal sequence. A failure before detachment is an unresolved pool invariant: preserve the primary failure, report sanitized cleanup evidence, never disconnect a possible new owner, and never claim a healthy reusable pool. The implementation and tests must distinguish failure before eviction from failure during replacement creation.

Tradeoff: Rails removal can replenish outside its inner synchronized block while this caller still holds the outer monitor. This can block waiters during native connection creation; it provides no absolute cleanup deadline. The bounded repair accepts that exceptional-path cost to prevent ownership corruption. Prove callback/reentrancy, replacement failure and next-request behavior with the real pinned Rails pool. No new connection timeout or pooling subsystem is implied.

Acceptance requires observed size-one-pool waiter schedules on both sides of the old nil-owner observation; normal safe handoff then expiry; callback removal and exceptions before/after owner clearing; remove failure before/after detachment; disconnect/logger failure; original-error preservation; successful 2xx and committed 409; next tenant/session transaction and GUC isolation; pending deadline delivery; and bounded thread teardown. All remain NOT_RUN until root executes the Docker suite on fleet-02. Existing operation identity and possible-COMMIT uncertainty remain unchanged.

Repair ownership: the fresh Astra LOW worker may edit only `apps/server/lib/elevateo/session_writes.rb`, its RBS, the necessary existing Rails pool signatures, the write-boundary pool tests/helper (including the new focused `apps/server/test/be_02/write_boundary_pool_disposition_test.rb`) and narrowly required deadline test/helper assertions, plus its repair report. Root owns this decision, review ledger, fleet execution and shared state documentation. No frontend, domain ledger, SQL guard, provider, production deployment or persistent schema changes are authorized by this amendment.
