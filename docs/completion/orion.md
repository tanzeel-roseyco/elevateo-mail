## Online WebView design simulations for root review

1. If the first-party web server deploys a bad frontend, every installed shell loads that version immediately. The tradeoff removes installer cadence for UI fixes but requires server-side rollout/rollback discipline and target-WebView compatibility testing against the same deployment SHA. Tauri remote capabilities remain empty, so a compromised page cannot call app-native commands, but it can still act within its authenticated web session; server authorization, CSP and cookie policy remain primary defenses.
2. If Android is backgrounded and the process is killed, a later cold start reloads the HTTPS app. Server-owned draft versions and send intents must determine whether an operation was accepted; the shell cannot infer success from a lost response or replay an uncertain send. The browser session cookie's persistence/revocation behavior needs real-device evidence.
3. If the web origin or network is unavailable, the shell cannot render a local mailroom. A bundled React shell would preserve some static UI but still could not authenticate/read/write without a supported native API contract; the online choice keeps one first-party cookie boundary at the cost of full offline unavailability. The app must show a deliberate network failure from target WebView evidence, not imply cached mail is current.
4. If a sign-in flow redirects to a different host, the exact-origin navigation guard denies it. A system-browser handoff would require a separate callback/session contract and target-platform tests; no exception to the guard is enabled by this candidate.
