## Pass 1: pool handoff, interrupts and cleanup

Confirmed finding **WD-DESIGN-01: HIGH**, one root cause. A failed acceptance check after Rails checkin permits another request to acquire the adapter while the old request still considers itself responsible for disposal. Cleanup can lose the ability to discard, remove/disconnect another request's adapter after a stale nil-owner check, or let a callback-removed adapter reach a waiter. Evidence: `session_writes.rb:80-102`, especially checkin at 90, postconditions at 91-95, `handed_off = true` at 96, and the outer ensure at 100-102; cleanup snapshots ownership at 110-111 before later removal/disconnect at 117 and 122. Only the early-waiter/clean-adapter schedule is MEDIUM by itself; the later-waiter cleanup race and registration failure warrant HIGH.

The failure path is outside both synchronization blocks. Atomic successful checkin does not make its later failure cleanup atomic. The original request can lose the ability to perform the discard required for an unaccepted handoff. Both synchronization blocks unwind before the method-level ensure calls `discard_connection`; the discard helper then enters the adapter lock again. The pool monitor is the decisive queue-ownership exclusion, even when the adapter lock is a real monitor.

Analytical schedule A, early waiter after a clean completed transaction:

1. T1 has a verified response, a closed transaction, and registered adapter A owned by T1. It holds A's lock and the pool monitor.
2. At line 90, Rails checkin clears ownership and enqueues A. A waiting T2 cannot yet poll/lease A while T1 holds the pool monitor.
3. The final deadline check at 94 or pending-interrupt check at 95 raises before `handed_off` is set. Both synchronized blocks unwind.
4. Schedule T2 before T1 reaches cleanup. T2 polls/leases A under the pool monitor and becomes its owner. It does not need to acquire A's lock to change that owner.
5. T1's cleanup observes the foreign owner at 111, reports an ownership failure, and correctly refuses to disconnect T2. Its primary deadline failure survives, but A was reused despite never passing T1's acceptance point.

This schedule does **not** establish reuse of an open or uncertain transaction: T1 already returned from transaction completion and passed the closed-transaction check at 85. Its direct consequence is a clean-but-unaccepted adapter contract violation and unexpected cleanup failure. Disconnecting the foreign owner would turn this into a more severe bug and is not a repair.

Analytical schedule B, waiter leases after cleanup's owner snapshot:

1. Use the same clean transaction, post-checkin expiry, queued A and uncompleted local handoff as schedule A. This time T1 reaches cleanup before the waiting T2 leases A.
2. T1 enters `connection.lock.synchronize` at 109 and reads `owner == nil` at 110. It takes the disposal branch. Pause T1 before line 117.
3. T2 polls/leases A while holding the pool monitor. It does not need T1's adapter lock to set ownership. T2 is now the adapter's owner; with the documented default `NullLock`, that adapter lock does not exclude T2's subsequent work either.
4. T1 resumes. The earlier local `owner` is not refreshed, and no pool monitor has protected the owner test through quarantine. The membership check in 117 does not verify ownership; `checkin_started` also permits removal for a callback-removed A. T1 calls `pool.remove(A)` and then `A.disconnect!` against an adapter now owned by T2.

This is a separate consequence of the same exposed-publication window: the foreign-owner guard is a stale observation, not synchronization with queue leasing. It is not enough to test only the case where T2 owns A **before** line 110. Root's pinned facts confirm neither called method rejects foreign ownership, so T1 can actually remove/disconnect the next request's adapter. With the default `NullLock`, T2 may already be using its native connection; with a real adapter monitor, leasing still occurs and T1 can close the newly owned adapter before releasing that monitor. This is not reuse of T1's failed transaction: it is interference with T2 after T1's clean completion. No executed native-I/O damage is claimed.

Analytical schedule C, callback removal followed by failed registration postcondition:

1. Start with the same clean, registered A and T1 holding the pool monitor at line 90. A checkin callback removes A from registration and returns normally. This is an expressly named fault case in the repair handoff, not a claim that an ordinary callback does this in every request.
2. Expire finishes with a nil owner, and checkin then adds A to the available queue without rechecking registration. At this moment A is available but unregistered. Any replacement creation is a separate event; it does not remove this queued A again.
3. The registration postcondition at 91 raises at 92. Both synchronization blocks unwind before the outer ensure. T2 can now poll the available A and own it; choose a schedule in which A is selected, or sufficient waiting checkouts to consume any other available entry first.
4. T1's discard sees T2's ownership and cannot repair A's registry/queue history without interfering with T2. Pool accounting no longer covers every issued adapter, violating the accepted available-subset-of-registered invariant and allowing capacity accounting to miss that issued adapter.

Schedule C is a pool registration/lifecycle failure, not evidence of leaked tenant claims, a live failed transaction, or guaranteed excess PostgreSQL backends in every run. The earlier transaction checks still matter. A callback **raising** before queue insertion is different: Rails does not enqueue, so nil ownership alone does not let a waiting poll acquire A. That branch still requires cleanup, but does not by itself reproduce this publication race.

The repair handoff's analytical claim at `docs/completion/be02-write-deadline-repair.md:33` that callback removal forces eviction before a waiter can obtain an unregistered spare is therefore disproved by the assigned implementation and pinned ordering facts. The claim at line 16 that callback outcome/expiry acceptance is atomic needs the same correction. Record these as consequences of WD-DESIGN-01, not extra defects.

### Smallest repair boundary and design tradeoffs

The minimum correctness requirement is to resolve a failed publication **before releasing the pool monitor**: either prevent publication until all reuse invariants have been accepted, or quarantine the rejected queue entry under that same monitor before releasing it. Owner verification and quarantine must form one exclusion interval against queue leasing; adding another unlocked owner check only moves schedule B. Then disconnect and any replacement-capable removal work must occur without exposing that adapter to checkout. The queue/owner transition, not a local boolean, is the linearization point visible to other requests.

There is a real constraint conflict in the accepted design: it prohibits production queue-internal mutation and prohibits holding an outer pool monitor across disposal, while the supplied public `checkin` publishes before caller postconditions and public `remove` can replenish. The allowed facts do not establish a public primitive that separates quarantine from replacement. Consequently, no repair preserving every original constraint is proved here. Root has explicitly stated it will revise the narrow disposition rule before the LOW repair; the preferred bounded direction below makes that tradeoff concrete rather than leaving contradictory acceptance criteria.

**Preferred smallest repair direction: use supported `pool.remove` while retaining the pool monitor on a rejected/abnormally interrupted checkin, and explicitly accept its exceptional-path replacement latency.** This keeps conservative disposal and avoids private queue mutation or a new pool abstraction:

1. Keep the existing adapter-then-pool lock order and outer deadline interrupt mask. Establish the checkin-attempt failure guard inside the pool-monitor block, before checkin can clear ownership or enqueue; cover exceptions and nonlocal exits, not just selected rescue classes.
2. On a successful fully accepted checkin, mark handoff under that monitor. Once safely transferred, later expiry only suppresses the response and must not touch the transferred adapter.
3. If checkin/postconditions fail, retain the pool monitor through current-owner validation and the supported `pool.remove(connection)` call. A nil owner is disposable only while this same monitor excludes a queue lease. Do not unwind to the existing outside ensure while a rejected adapter can still be available. Refuse a pre-existing foreign owner without theft.
4. Record that this removal attempt already occurred, and capture its error separately. Do not blindly call `remove` again in the outside ensure: a second call can trigger another replacement attempt. Once quarantine is established, release the monitor and attempt disconnect in an ensure even when the first removal raised during replacement creation; preserve the original request failure and sanitized cleanup evidence.
5. Keep pre-checkin abnormal-work disposal outside the pool monitor when the adapter was never published and is still owned here. Share error/disconnect handling only as far as needed to avoid duplicated failure logic. No new retry ledger, dependency or generalized callback framework is needed.

The amendment is narrowly necessary because Rails replenishment after removal runs outside its **inner** synchronized block but still under this caller's **outer** monitor. Waiters may be blocked during native replacement connection creation; lock/reentrancy behavior and replacement failure must pass the real-pool regressions. There is no absolute cleanup deadline. If an exceptional removal failure prevents actual quarantine, absence from registration alone does not prove absence from the available queue, especially in schedule C; do not report safe cleanup or release acceptance on that evidence. The pinned normal removal prefix and its replacement-failure boundary must be verified by tests. A failure before detachment is an unresolved pool invariant, not permission to disconnect a later owner or claim health.

Root owns the written amendment and exact patch approval; this review does not itself modify the decision. If the real-pool evidence invalidates this narrow monitor-held removal approach, the alternative is a separately approved supported quarantine seam, not silent production mutation of Rails instance variables.
