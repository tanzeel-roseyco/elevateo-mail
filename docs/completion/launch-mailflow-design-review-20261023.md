## Findings and defect accounting

1. **Medium — teardown exceptions bypass later cleanup** (`app_chain_test.rb:58–64`). If either DELETE raises, temporary credential removal and `super` are skipped; if file removal raises, `super` is skipped. This is directly visible control flow, independent of superclass implementation. A broken database connection after a timeout is a practical trigger. Use independently attempted cleanup steps with an outer ensure guaranteeing superclass teardown, preserve/report failures, and test injected DELETE/file-removal failures. Cleanup must not silently convert the original failure into success. Which residual resources the superclass owns is unverified.

2. **Medium — revoked outbound sender is not exercised** (`app_chain_test.rb:118–132`, `http_chain.rb:47–48`). A reply is accepted before only the inbound IMAP account is deactivated; the following exception proves at most that particular inbound denial. HTTP logout proves session denial, but subsequent approval/dispatch use superclass helpers and the original fixture identity rather than the HTTP user. The chain can pass even if a worker wrongly submits queued mail after sender/mailbox send authority is revoked. Add a separate queued-send revocation case at the existing authorization boundary, assert the denied durable result and zero submission/no matching recipient message, and identify the actor used for approval. This is an acceptance-coverage gap, not a demonstrated production authorization vulnerability. If the intended claim is only SMTP/IMAP connectivity plus HTTP draft persistence, narrow the evidence label instead.

3. **Medium — authenticated wrong-mailbox denial is absent** (`app_chain_test.rb:99–115`, `http_chain.rb:29–46`). The positive HTTP inbox checks the imported mailbox, and a direct SQL-context reader check uses a random user. Neither exercises a valid authenticated principal with authority for mailbox A attempting to read or reply in mailbox B. A missing mailbox-specific HTTP guard can therefore evade this packet. Add one nonmember mailbox/thread fixture, keep the same valid session/CSRF headers, assert the documented denial, unchanged draft/send state and no message exposure. Use an authorized positive control so a generally broken session cannot satisfy the negative. Again this is a test coverage defect, not proof that application guards are missing.

## Design tradeoffs and practical adequacy

**Real chain versus protocol-only tests.** Protocol-only SMTP/IMAP tests establish negotiated transport and delivery without proving application persistence, role-scoped reads or draft integration. This composition adds those links using real SQL adapters, authentic HTTP cookies according to the helper contract, and actual transport objects. Nonce-bearing data and message ancestry are stronger oracles than SMTP acceptance alone. The tradeoff is more external fixture state, longer polling and poorer failure localization. Keep a small real-chain smoke and separate deterministic unit/database failure tests; do not replace either with the other. No broad architectural rewrite is justified.

**HTTP versus in-process boundaries.** HTTP covers authentication, session organization switching, inbox projection, CSRF rejection, draft persistence and logout. Approval, review and dispatch are driven directly. That deliberately reduces setup complexity, but it cannot establish the HTTP send/approval route, identity continuity from the draft actor into approval, background process scheduling, browser UX or current Authentik SSO behavior. Adapter calls are not proof that separately deployed workers share correct configuration. Document this as a hybrid chain.

**Positive and negative oracles.** The invalid-CSRF branch checks any 4xx plus unchanged draft version; that is sufficient for a broad fail-closed assertion but does not identify the specific CSRF error. The following valid write is a useful positive control. The second executor result `:idle` checks queue behavior but not independent recipient-side duplicate count; `find` accepts one matching reply even if duplicates exist. No exactly-once delivery claim is warranted. Check actual recipient and uniqueness only if those become acceptance claims.

**Fixture isolation and egress.** Fresh nonce, synthetic UUIDs and a mode gate reduce accidental matching. The filtered credentials file uses permission 0600 and copied binding metadata; malformed/empty entries, absent second identity or invalid bundle fail through unreviewed resolver behavior rather than explicit local validation. SQL values are parameterized. Privileged fixture grants and `outbound_held:false` are intentional test bypasses: internal-only Docker networking, DNS containment, approved endpoints and teardown must be independently verified before any execution. A comment saying internal network, an environment flag and a destination-domain list are not a firewall. The visible hostname resembles a routable name; this report does not conclude that egress is blocked or enabled.

**Practical limits.** Recipient polling fetches only the first 50 messages after UID zero on every attempt. In a genuinely empty disposable mailbox this is simple and adequate; in a reused mailbox with more than 50 earlier messages it may time out without ever examining the new reply. The superclass and harness must prove fresh mailboxes or the poll should use a captured UID boundary/pagination. The inbox polling SQL filters organization and nonce but not mailbox; later positive HTTP assertions tighten the happy path, while the missing negative boundary remains Finding 3. Explicit database transactions, role grants, identity fixture cleanup and Auth-user cleanup are all unverified. Do not infer a leak or clean teardown without those dependencies.
