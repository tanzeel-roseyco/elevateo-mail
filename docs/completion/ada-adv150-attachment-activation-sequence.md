## Fail-closed readiness

Unavailable gateway must yield the existing deliberate unavailable/internal error, never metadata-derived clean bytes, direct Storage URLs, service-role exposure or a fake successful download. Metadata can remain useful when bytes are unavailable if its existing authority path supports that; the UI must show an explicit retry/error state, not claim download success. Missing deployment configuration should prevent privileged gateway readiness; it must not cause Rails to acquire Storage credentials.

Two short authorization snapshots around Storage network access remain the intended boundary. Do not hold a DB transaction across network fetching. No browser-supplied organization/mailbox claim or arbitrary URL may choose storage authority. Before/after tuple/session proof must continue to gate release; runtime testing cannot bypass these checks to reach its oracle.

## Section-specific acceptance simulations

- **Routing:** ordinary candidate GET reaches the exact content controller; an override-only PASS cannot prove this. Route count/contract/generated declarations agree and optional port omitted elsewhere retains its disabled UI state.
- **Producer:** crash after upload/before metadata leaves no downloadable row. Retry is idempotent for the immutable tuple; task-owned orphan cleanup may recover storage without inventing clean status.
- **Scan:** pending/malware/rejected remains held with no bytes. Real clamd clean proof precedes release; scanner failure stays held.
- **Download race:** read authority succeeds, Storage fetch starts, mailbox/session revoked, second check denies and fetched bytes are discarded. No cached grant or successful first snapshot releases content.
- **Infrastructure failure:** gateway/storage unavailable produces an error and no private response body; restored infrastructure permits an authorized retry through fresh checks.
- **Viewer/composer:** inbound viewer permission is mailbox READ, distinct from compose/send authority. Activating this viewer must not activate outbound attachments or mutable approval payloads.

## Tradeoff and completion boundary

Activating a reviewed candidate before runtime proof creates a testable product without increasing public exposure. A frozen isolated source and network boundary contain that risk; testing a different override app costs confidence and maintenance. Successful private proof then promotes the exact source, avoiding duplicate activation implementations and circular scheduling.

Omitted source: adapter/controller/helper internals, SQL/storage/scanner/producer, route flag environment setup, OpenAPI generated content and UI consumers. Their prior reviews do not replace exact runtime proof. Product gap is the missing normal activation seam; runtime uncertainty is clean production/retrieval/revocation/visual behavior. Keep these separate. No extra authentication protocol, broad grant or general framework is needed.
