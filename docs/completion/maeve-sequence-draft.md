# MAC-814 sequence gap: isolated draft primitives

This packet proposes the smallest persisted sequence draft for later schema/API agreement. Current implementation is **pure Ruby only** in `apps/server/lib/elevateo/outreach_sequence/schedule.rb`; it creates no table, route, send intent, worker job or provider call. The tests are authored and requested for Soren's fleet Docker lane, **NOT RUN** here. There is no live sending path.

## Proposed persisted shape, pending root/Cassian/Dorian decision

A campaign sequence draft needs campaign ID, optimistic draft version, ordered step ID, bounded delay, IANA timezone and exact local wall time. A lead/step occurrence needs a unique `(campaign_id, lead_id, step_id, draft_version)` key, frozen `due_at` UTC and explicit pending/cancelled/claimed state. Duplicates must be rejected by PostgreSQL uniqueness and an atomic due claim, not by this in-memory hash. Editing a draft increments version and invalidates only unclaimed occurrences. Migration `00016` is reserved and uncreated pending schema agreement.

Before any existing BE03 send-intent creation, the integration must recheck current campaign state, mailbox permission, explicit consent provenance, global and campaign suppression, replies, unsubscribe, prior send outcome and worker controls in one authorized transaction. A manual attestation is an operator claim, never independent delivery consent. A reply or unsubscribe cancels all unsent follow-ups. Delivery remains exclusively with the existing reviewed send-intent/worker authority, which must repeat the final checks immediately before dispatch; this module cannot grant send eligibility.

`Schedule.due_utc` rejects malformed local time/zone and returns no candidate for a DST gap or fold; product must ask the author for an unambiguous time instead of guessing an offset. `occurrence_key` deterministically identifies one draft revision's lead/step occurrence, but durability and exact-once claims require future database constraints. `stop_required?` observes explicit signals and can only block. Future integration must define a late-arriving reply, timezone database version changes, and retry leases without double sends.

Soren-only Docker request from repository root on exact candidate SHA: run `cd apps/server && bundle exec ruby -Itest test/outreach_sequence/schedule_test.rb`, `bundle exec steep check`, and affected RuboCop on the new Ruby/test files under the shared lease. Record exact image/source SHA, case counts, exits and cleanup. No host application tests or Docker builds were run by Maeve. Root owns bounded functional/design review and actual acceptance.

Design tradeoff for root: persisting frozen UTC due times makes claims deterministic and auditable even if timezone data changes; it also requires an explicit reschedule/review when the author edits the draft or timezone rules change. Recomputing every due time at claim time would silently shift already promised timing. The proposal chooses frozen due time and a draft-version key, pending owner approval.

The local-time resolver uses TZInfo 2's `local_to_utc(local, nil)` API, which treats the input as local wall time and raises for missing or ambiguous periods. This is a source-design choice based on the [TZInfo 2 method reference](https://www.rubydoc.info/gems/tzinfo/TZInfo/Timezone); Soren's fleet tests still must establish actual behavior with the pinned gem and timezone data.

## Proposed versioned API and schema sections for decision

1. **Draft aggregate:** `app.campaign_sequences(id uuid, organization_id uuid, campaign_id uuid, version integer, status draft|held, timezone text, operation_id uuid, created_at, updated_at)` with organization/campaign composite FK and unique `(organization_id,campaign_id)` for one active draft. `held` permits edits and preview but forbids due claims; neither status grants delivery. A sequence version increments on every change.
2. **Ordered steps:** `app.campaign_sequence_steps(id uuid, organization_id uuid, sequence_id uuid, position integer, delay_seconds integer, local_time HH:MM:SS)` with unique `(organization_id,sequence_id,position)` and `(organization_id,sequence_id,id)`. Proposed bounds: 1-20 steps, positions 1-20, delay 0-2,592,000 seconds (30 days). These are provisional product bounds and require owner acceptance.
3. **Due occurrences:** `app.campaign_sequence_occurrences(organization_id,campaign_id,sequence_id,draft_version,lead_id,step_id,local_at,timezone,due_at,state,lease_token,leased_until,stop_reason)` with unique `(organization_id,campaign_id,lead_id,step_id,draft_version)`. Due UTC is frozen only after strict DST resolution; gap/fold yields no occurrence and a visible author correction. `pending|cancelled|claimed` is not a delivered status. PostgreSQL performs atomic due claims and unique enforcement; hash keys in this packet are advisory only.
4. **HTTP draft seam:** Cassian-owned additive V2 campaign-scoped `GET/POST/PATCH` sequence draft and step operations, with `operation_id`, `expected_version`, strict DTOs, generic inaccessible responses and current tenant/campaign authorization. GET projects draft/held state and validation errors only, no eligibility or provider claims. Exact paths and replay/conflict response shapes require Cassian agreement.
5. **Delivery handoff:** A future scheduler may produce a *candidate* from an atomically claimed due occurrence. Rowan/Elara own the existing SQL/worker send authority and must recheck live tenant/mailbox grant, explicit independent consent provenance, suppression, reply/unsubscribe, draft/campaign state, existing send outcomes and worker controls before any BE03 send intent. On failure, persist a bounded stop reason and never retry a live send implicitly. Replies/unsubscribes must cancel pending later occurrences. No synthetic delivered status or automatic opt-in.

Open decisions: whether one campaign may have multiple held drafts, which authenticated role may edit sequence drafts, when a reply is attributed to a lead/campaign, whether timezone database version changes require a reschedule prompt, and whether one step may target multiple authorized accounts. None is silently decided in source. This proposal was sent to root/Cassian/Dorian before migration 00016; schema and API remain unapproved.

Boundary follow-up: source rejects invalidly encoded or non-ASCII local-time/zone/UUID strings before regex or TZInfo processing; an invalid UTF-8 regression is authored. This is still unexecuted source, not a runtime pass.
