# Database design and integrity exceptions

The catalog gate reads `apps/server/db/schema_integrity/exceptions.json` as the exact exception registry. It rejects missing or stale UUID/JSON/array entries, unindexed foreign keys, missing primary keys, invalid indexes and unvalidated constraints. Index candidates include leading-column prefixes and backward-scan alternatives; every retained index exception must be the actual target of a catalog foreign key. Derived values require source review because a catalog cannot infer functional dependencies.

All application entities have primary keys. Tenant relationships use organization/mailbox composite foreign keys. Many-to-many membership, star, budget and enrollment relationships use junction tables. JSON values below are bounded request/evidence snapshots rather than independently editable entities. Changes 111-117 normalize finder job items and domains, centralize hard suppressions, add missing FK indexes and validated constraints, and remove confirmed redundant indexes.

Migrations fail on incompatible data rather than silently deleting rows. New checks are installed NOT VALID and explicitly validated. Existing-table index builds use CONCURRENTLY outside the migration transaction and can resume after an interrupted build. Rollback reconstructs finder input JSON and preserves suppression provenance.

## Deliberate boundaries

Supabase owns `auth.users` and its authentication lifecycle; the application owns `app` and private schemas. UUID snapshots in authentication, audit, operation replay and consent records retain attribution after membership revocation. Active application membership edges have composite foreign keys; authorization functions recheck current membership and revocation independently of historical records. No cross-provider identity deletion cascade is introduced.

`messages.attachment_count` records provider metadata; materialized attachments can arrive later. Reads expose the greater count, and ingestion rejects materialization beyond the API limit. Finder `domain` was removable duplication and is now computed from canonical email with a matching expression index. Finder job inputs now use one row per item; small provider/request/result objects remain immutable snapshots.

Multi-step writes stay in database transactions: send approval snapshots plus jobs, budget reservations, finder item completion plus progress, and suppression propagation. Provider I/O stays outside transactions. Exact checks and regressions are in the three `test/sends/schema_integrity*database_test.rb` files; execution evidence is recorded separately in completion logs.

## Design tradeoff scenarios and rollout

<!-- AIDEV-NOTE: These analytical scenarios explain retained boundaries; execution evidence lives in completion logs. -->
Obsidian was unavailable in this session. The scenarios below are analytical comparisons, not claims of executed simulations.

- **Suppression scope:** A campaign unsubscribe should stop outreach while preserving ordinary correspondence; a hard bounce must stop both. Finder opt-outs govern research of people or domains. Combining these purposes into one undifferentiated table would lose those distinctions. Separate source tables retain provenance, while `delivery_suppressed` supplies one indexed, canonical hard-stop predicate for recipient suppressions and campaign bounces at send boundaries. Bounce promotion cannot be downgraded by a later unsubscribe update.
- **Finder work and progress:** With 5,000 inputs, changing one resumable item in the old array rewrote the job's collection. Child rows isolate that mutation and enforce identity, ownership and row bounds. Cached totals avoid aggregating each progress read; deferred checks enforce totals and contiguous completion at commit. Repeated deferred counts have a bounded quadratic enqueue cost at the 5,000-item limit. The measured finder suite passed 9 tests and 47 assertions in 8.832980 seconds, including the maximum-size regression; that is whole-suite timing, not an isolated benchmark or a claim about larger jobs. Advisory serialization requires fresh READ COMMITTED snapshots, so other isolation levels fail loudly for checked mutations.
- **Attachment metadata and replay:** A provider count of three with no downloaded rows must still display three; a zero provider count with one materialized row must display one. Therefore reads use the greater value instead of replacing provider metadata with a derived count. At 999 rows, two concurrent additions serialize through a parent-row update: one can reach 1,000 and the other fails. The AFTER trigger counts actual inserted rows, allowing an idempotent `ON CONFLICT DO NOTHING` replay at capacity. The parent update also prevents stale repeatable-read snapshots from bypassing the cap.
- **Coordinated release:** Finder inputs and resumable work move losslessly to child rows, and rollback reconstructs the ordered JSON array and derived domain. Removing the old columns still makes this migration incompatible with old finder application code. Drain finder writers and coordinate the migration with the matching application release; rollback likewise requires matching old code. This is a release prerequisite, not evidence that deployment occurred. Constraint validation fails on incompatible data rather than deleting it.
- **Concurrent index retries:** An interrupted concurrent build may leave an invalid index. The helper checks its expected definition before replacing an invalid task-owned index, reuses a ready matching index, and rejects a mismatched definition. Rollback recreates necessary indexes concurrently before attaching restored UNIQUE constraints. Concurrent builds reduce write blocking, but attaching or dropping constraints still requires brief table locks and should be scheduled accordingly.
