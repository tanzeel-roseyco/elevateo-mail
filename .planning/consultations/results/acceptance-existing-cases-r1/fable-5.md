## Recommendations

**R1 — SCN-AUTH-001-F2: implement, with a request counter and fresh-challenge retry.** (unavailable.e2e.ts:5; support.ts:14–27; matrix SCN-AUTH-001-F2.) `responseAt` (support.ts:14–19) returns the *first* response matching path/method and cannot distinguish two POSTs to `/v1/auth/login`. The matrix's SCN-AUTH-001-P invariant ("exactly one real Auth exchange") and this F2 both require counting requests, not responses: add a `page.on('request')` counter scoped to `/v1/auth/login` in the spec, asserting one forwarded request during the held window and exactly one on retry. Hold via `page.route` on the genuine request, attempt duplicate submit, assert the submit button is disabled or the second request never issues, then `route.abort()` before forwarding and retry through real Auth. Because the abort happens before forwarding, the server never consumes the challenge — but assert nothing about challenge state without evidence; the retry must fetch its own `GET /v1/auth/login-challenge` (matrix api list) since the client may discard the prior challenge. Assertion set: bounded error UI distinct text/state for transport abort; no authenticated chrome (`Account and sign-out` count 0, mirroring support.ts:31); successful retry reaches support.ts:35 state. Do not inject a fabricated 503 — the Auth-outage half of F2 stays an explicit gap (keep a narrowed `unavailable` entry for outage only, updating unavailable.e2e.ts:5 in the same change so the reason doesn't go stale). Evidence limit: the login form's duplicate-submit guard behavior is uninspected; if the UI permits a second request, record it as a product finding, not a fabricated pass. Allowed paths: `tests/acceptance/playwright/auth.e2e.ts` (new), `unavailable.e2e.ts` (reason edit only).

**R2 — SCN-AUTH-003-F2: adapt; require proof the delayed response was delivered.** (unavailable.e2e.ts:7; matrix SCN-AUTH-003-F2.) Design: fulfill a genuine protected GET via `page.route` that forwards the real request, holds the real response, logs out the same browser session, then releases the unchanged response. The honest-evidence trap: if the SPA aborted the fetch on logout/navigation, the browser cancels and "no stale UI" is vacuous. The spec must record whether the response reached the page (response event fired without request failure) and report cancellation explicitly as a weaker result ("browser cancelled; resurrection untested") rather than a pass of the resurrection assertion — this matches the task's "explain what cancellation does and does not prove." Then assert the *same session* is denied: issue a protected request from the same page context (reload or in-page fetch through the gateway, not a new browser context — a new anonymous context proves nothing about revocation). Expected: 401/revocation per the session contract; exact status is uninspected, so assert "not 200 and no protected data rendered" plus the sign-in heading (support.ts:22). F1 (held write vs logout race) stays unavailable — it needs the backend lock barrier owned elsewhere. Allowed paths: same spec file as R1; no `support.ts` changes needed if `responseAt` suffices; if a hold helper is added, put it in the spec, not shared code.

## Strongest dissent and simpler alternative

**Dissent against my design:** route-level holds (R1/R2) test Playwright's interception semantics as much as the application; a reviewer can argue that without a backend-owned barrier, "bounded in-flight behavior" is browser-dependent and the delayed-response case will usually land in the weak "cancelled" outcome, yielding little real evidence for its implementation cost. **Simpler alternative:** implement only R3, R5 and R6 now (pure existing-seed, zero interception), and defer both AUTH F2 cases to the backend-barrier work already owned by root — at the cost of leaving two P0 failure paths NOT_RUN longer. I still prefer implementing R1/R2 with honest delivered/cancelled labeling, because abort-genuine-traffic is explicitly permitted and even the weak outcome documents real client behavior.
