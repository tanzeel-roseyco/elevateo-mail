# BE-01-R1 security repair — independent opinion (claude-fable-5)

**Overall verdict: support the repair as framed, with one scope split (R1-A code vs. R1-C test infrastructure) and one explicit B01-03 refinement for R1-M1.** All ten findings are substantiated by the supplied source; none needs further evidence before design acceptance. Below I answer each required section, with maintainability and implementability as the lens.

## 1. Which findings are substantiated

**R1-T1 (P1, confirmed).** `tenancy.rb:27` uses `transaction(requires_new: true)`. Rails documents that on PostgreSQL this creates a savepoint when a transaction is already open. `set_config(..., true)` is transaction-local per PostgreSQL 17 SET semantics — it survives savepoint release and dies only when the *real* transaction ends. So if a caller already holds a transaction, the wrapper's "exit" clears only the Ruby marker (`tenancy.rb:35`) while `app.user_id`/`app.org_id` remain set for the rest of the ambient transaction. Any subsequent unwrapped query in that transaction reads with stale authority. Fully supported by the pinned source and cited mechanism evidence.

**R1-T2 (P2, confirmed).** Lines 21–24: nested calls compare principals via a thread-local but yield whatever `connection:` the caller passed, without checking it is the connection that actually holds the claims or that its transaction is still the one that set them. A nested call with a second pool connection gets a verified-looking yield on a connection with *no* context — queries return nothing (fail closed by RLS default-deny) or, worse, run inside someone else's leftover transaction-local settings.

**R1-T3 (P1, confirmed).** The wrapper changes authority via `raw_connection.exec_params`, which the Rails 8.1.4 adapter source shows does not touch the SQL query cache. With caching enabled (default inside Rails request/job execution contexts), an identical ActiveRecord SELECT issued under principal A can be served from cache under principal B or after the wrapper exits, because the cache key is the SQL text, not the session settings. This is the most dangerous of the three because no amount of SQL-side fixing helps — the query never reaches PostgreSQL.

**R1-M1 (P2, confirmed as a binding-design conflict).** `bootstrap.sql:24` (`GRANT elevateo_app_read TO elevateo_api`) reapplies a runtime membership on every bootstrap, while B01-03 assigns membership evolution to the migration lane. A future migration that revokes this membership is silently undone by the next bootstrap. Real conflict, correctly classified P2.

**R1-S1 (P1-equivalent in my view, coordinator-confirmed).** `compose.yaml` line 7: the `x-server` anchor sets `env_file: ./ops/local/.env` for api, worker, and migrate alike. That file contains `POSTGRES_PASSWORD`, `JWT_SECRET`, `MIGRATOR_DB_PASSWORD`, `SERVICE_ROLE_KEY`, and all sibling role passwords. The API container therefore holds the administrator password and the JWT signing secret. This defeats invariant 4 directly. I can confirm the mechanism from the supplied compose.yaml without the reviewer's exact line references.

**R1-S2 (confirmed).** `generate-secrets.rb:42`: `File::TRUNC` on the sole credential file before the values are written. A crash between truncate and completed write destroys credentials that the retained database volume still requires — unrecoverable without resetting volumes, which invariant 5 forbids.

**R1-E1/E2/E3 (confirmed).** The egress script treats any `docker exec` failure as "unreachable" (a stopped container passes the security check); the fixture lives on a separate bridge, so the test proves bridge separation, not egress confinement — deleting `internal: true` from the runtime network would still pass; and the static names plus unconditional `trap cleanup EXIT` can remove a foreign container named `be01-egress-server`.

**R1-H1 (confirmed from supplied source, correctly classified).** `compose.yaml:183-190` (worker service) has no healthcheck and the Dockerfile defines none, so `up -d --wait` only waits for process start. The worker already writes `/tmp/worker.alive` every second (`bin/worker:10-13`), which is an existing liveness signal going unused. This remains a standards/acceptance gap, not an observed failure; preserve that classification.

No finding needs more evidence. The disproved search-path concern stays closed; `app_meta` bookkeeping is handled correctly in `config/application.rb`.

## 2. R1-A: smallest safe design

**Transaction ownership.** Adopt the brief's preferred shape: the outermost `with_context` must *reject* an unrelated ambient transaction (`raise ContextError if connection.transaction_open?` before doing anything) and then open and own the real transaction itself (`requires_new:` becomes unnecessary — plain `transaction do`). Record a context struct in the thread-local: principal, `connection.object_id` (or better, a token stored per-connection), and a transaction identity (the ActiveRecord transaction object from `connection.current_transaction`). Same-principal nesting is legitimate only when principal, connection, and still-open owned transaction all match; reject anything else *before* yielding. This fixes T1 and T2 in one bounded change.

**Against save/restore of previous settings:** restoration would require tracking prior values across rollback-to-savepoint (which restores settings to the savepoint snapshot, not your saved Ruby copy), aborted-transaction states where `SELECT set_config` itself fails, and after_rollback callbacks running in ambiguous states. No caller in this foundation needs composition with an ambient transaction — BE-01 has no business endpoints yet. Rejection is strictly simpler, fails loudly, and can be relaxed later with evidence. **Failure case the design must handle:** an exception inside the block — because the wrapper owns the transaction, rollback discards the transaction-local settings automatically; the `ensure` clears the Ruby marker; verify in V03 that post-exception unwrapped queries have no authority.

**Query cache.** Wrap the protected block in `connection.uncached { ... }` *and* call `connection.clear_query_cache` on entry and in an `ensure` on exit. Entry clearing prevents the block from consuming rows cached under prior (unscoped or other-principal) authority; exit clearing prevents the caller from consuming rows the block cached. `uncached` restores the caller's prior cache-enabled state by design (it is a block API in the pinned Rails 8.1.4 source), satisfying the restore requirement; the `ensure`-based clear covers exception/rollback paths. One unverified-semantics caveat to label: whether `uncached` on the *connection* fully covers the Rails 8.1 executor/pool-level cache in all execution contexts — V04 exists precisely to prove this with real cache-enabled ActiveRecord queries, and the test must run through the pool, not raw PG. The brief's prohibition on a tenant-aware cache is right; a per-principal cache key is a new security-critical mechanism with its own invalidation bugs.

**Maintainability note:** this keeps `tenancy.rb` a single ~60-line module with one entry point. That is the right shape for a security boundary — Astra LOW can implement it from this description without further design, and V03/V04/V05 map one-to-one onto its branches.

## 3. R1-M1: membership/grantor and migration reversal

**Design:** delete line 24 (`GRANT elevateo_app_read TO elevateo_api`) from bootstrap.sql; bootstrap keeps login/ownership prerequisites only. Add one additive migration that executes `GRANT elevateo_app_read TO elevateo_api` idempotently (guard with a `pg_auth_members` existence check); its `down` revokes it. This is an explicit **refinement of B01-03**, as the brief invites: "application membership evolution" now concretely includes the api→app_read membership, and bootstrap must never reapply it — state this for Astra MAX rather than pretending current code conforms.

**Grantor semantics (labeled partially unverified):** migrations run as `elevateo_migrator` with `SET role = elevateo_owner` (bootstrap.sql:23). Under PostgreSQL 17, granting membership in a role requires `ADMIN OPTION` on that role or `CREATEROLE`; the bootstrap actor (`supabase_admin`) created `elevateo_app_read`, and PostgreSQL 17 gives the creating CREATEROLE user implicit admin. `elevateo_owner`/`elevateo_migrator` likely have **no** admin option on `elevateo_app_read`, so the migration's GRANT would fail. The smallest conforming fix: bootstrap (the already-privileged actor) grants `ADMIN OPTION` on `elevateo_app_read` to `elevateo_owner` — a one-time prerequisite, which B01-03 permits bootstrap to establish ("narrowly scoped migration authority") — and the migration then owns grant/revoke. For already-granted memberships on initialized volumes, PostgreSQL 17 records the grantor; a revoke by a different admin-capable grantor still removes membership, so `down` works. This is narrower than CREATEROLE and adds no runtime privilege. **V06 must prove it on both fresh and already-initialized databases**, including the up/down/up cycle and unchanged application rows. Do not rewrite the applied foundation migration; the additive file is compatible with retained volumes, which editing history is not.

## 4. R1-B: credential isolation and crash-safe generation

**Service/secret matrix (Compose `environment:` mappings via interpolation; drop `env_file` from `x-server`):**

| Service | Allowed secrets |
| --- | --- |
| db | POSTGRES_PASSWORD |
| bootstrap (tools) | POSTGRES_PASSWORD (connects as supabase_admin) + MIGRATOR/API/WORKER_DB_PASSWORD (to set them) |
| auth | POSTGRES_PASSWORD (auth_admin DSN), JWT_SECRET |
| rest | POSTGRES_PASSWORD (authenticator DSN), JWT_SECRET |
| storage | POSTGRES_PASSWORD (storage_admin DSN), JWT_SECRET, ANON_KEY, SERVICE_ROLE_KEY |
| api | API_DB_PASSWORD, SECRET_KEY_BASE |
| worker | WORKER_DB_PASSWORD, SECRET_KEY_BASE |
| migrate (tools) | MIGRATOR_DB_PASSWORD, SECRET_KEY_BASE |

The `--env-file ops/local/.env` flag in `scripts/dev` remains for interpolation only; interpolation does not inject into containers, so this is the brief's preferred shape with no new secret files. One necessary companion change: `Config#initialize` currently demands `SECRET_KEY_BASE` and the role-matched password for every process, which the matrix satisfies, but validation must not force the API to see worker/migrator passwords — the existing `ROLE_PASSWORDS` lookup already fetches only the own-role key, so config.rb may need no change at all; verify rather than refactor. The B01-05 Storage service credential exception is not yet needed (no Storage adapter exists in this slice) — do not pre-add it. **V07 is the right acceptance:** inspect runtime environments for forbidden key *names* only.

**Generator:** if the existing file parses completely (all nine expected keys present, non-empty), return without opening it for write — byte-identical no-op, provable by hash equality in V08. Otherwise write to `mkstemp`-style temp file in the same directory with 0600, write, flush, `fsync`, close, then `File.rename` (atomic on the same filesystem on Linux; the container runs Linux via `ops/compose.secrets.yaml`, so Windows rename semantics don't apply — document that the host only ever invokes this through Docker, which answers the brief's Windows question). Remove only this invocation's temp file on failure. For concurrency, an `flock` on a sibling lockfile is cheap and sufficient; given the generator runs via `docker compose run` in a sequential bootstrap, I'd accept flock as the whole answer rather than inventing more. Fail clearly on a partial existing file — do not merge-and-rewrite it, which is the current behavior and the source of the hazard. (This slightly tightens current semantics: "fill in missing keys" becomes "valid file is untouched; invalid file is an error." That is the brief's invariant 5 and is the safer contract.)

**R1-H1:** confirmed; the smallest truthful probe is a Compose healthcheck on the worker service that checks `/tmp/worker.alive` is fresh: `test: ["CMD", "ruby", "-e", "exit(Time.now.to_i - File.read('/tmp/worker.alive').to_i < 10 ? 0 : 1)"]`. The worker already maintains the file; no worker code change, no HTTP, no fake jobs, bounded, and a stopped/stuck loop fails it within the staleness window. V11 covers both directions.

## 5. R1-C: implementable egress regression

**Topology:** create one invocation-unique external-route fixture network (a normal bridge, *not* internal) with an HTTP fixture container on it. Run an unrestricted control container attached to that network — it must reach the fixture (positive control). Then test the runtime services: `docker inspect` each target first to assert it exists, is running, and is attached only to the expected internal runtime network; assert the probe interpreter exists inside it (`docker exec ... which ruby/wget`) before interpreting connection failure as denial. Any setup/exec/inspect failure is classified SETUP_FAILED and exits nonzero as a *broken test*, distinct from VIOLATION and PASS. Because the runtime network is `internal: true`, runtime containers cannot route to the fixture bridge — and crucially, if someone removes `internal: true`, Docker inter-bridge traffic is still blocked by default, so the connection probe alone is insufficient (R1-E2's core point). Therefore the check must *also* assert the network property directly: `docker network inspect` the runtime network and fail if `Internal` is false. The disposable negative control (V09): spin an equivalent compose override with `internal: true` removed and a control-style container on the runtime network plus the fixture network path — the network-property assertion fails, demonstrating sensitivity without any Internet contact. This combination (behavioral probe + inspected network attribute) is the smallest arrangement that catches confinement removal; probe-only designs cannot, because Docker's default bridge isolation masks the regression.

**Ownership:** suffix every fixture name with `$$`-based or `uuidgen` invocation ID, apply the task label, fail hard (`set -e` semantics, no `2>&1` swallowing) on creation errors, capture the returned IDs, and make `cleanup` iterate only captured IDs after re-verifying the label via `docker inspect`. Never `rm -f` a static name. V10 tests pre-existing collisions and interruption.

## 6. Acceptance gaps, simpler alternative, scope split

**Gaps:** (a) V04's cache test must run through ActiveRecord's executor context, not just `connection.cache do` — a raw test would pass while real requests still leak; (b) V06 needs the already-initialized-volume path, which is easy to skip since CI always starts fresh; (c) no regression asserts the config validator doesn't quietly re-expand secret requirements later — a V07 key-name allowlist assertion covers this cheaply. **Simpler alternative considered and rejected:** fix only T1/T3/S1 (the P1s) and defer the rest. Rejected because S2 and E1–E3 are small, the egress test as it stands produces *false security evidence* that would contaminate every later acceptance run, and deferral costs a second consultation cycle against a $7.74 Devin credit boundary.

**Scope split:** yes, two sequential commits under one task and writer: (1) tenancy + cache + migration + compose/secrets (invariants 1–5, verified by V01–V08); (2) egress script/fixtures + worker probe (V09–V11), which touches only test/ops infrastructure and can be reviewed independently. Both fit the 30-minute checkpoint discipline; the second cannot regress the first. Do not split into separate tasks/consultations — the findings are too interdependent (the compose change alters the containers the egress test probes).

**Residual uncertainty (labeled):** PostgreSQL 17 implicit-admin-for-creator semantics and `uncached` coverage of the Rails 8.1 executor cache are design-level readings, not runtime-verified; V04 and V06 are the proof obligations and must not be voted away. All proposed tests are **not run**. Nothing here closes any BE-01 acceptance item beyond the ten findings, and no product promise (worker health, egress safety) should be made until V09–V11 evidence exists at the repair commit.
