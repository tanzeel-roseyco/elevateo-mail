## BE02-D01: scope, dependencies and contracts

Use the existing Rails modular monolith and same-code worker, PostgreSQL/Auth/private Storage and existing pinned dependencies. No Redis, search service, new domain backend, native shell or provider adapter is introduced. Implement A sessions/mailboxes, B threads/messages, C durable drafts and reconciliation, D collaboration/membership/read-state/search. Do not dispatch all four as one unbounded coding task.

The four GETs in canonical `contracts/v1/openapi.json` version `1.0.0-read.1` remain unchanged. In particular, thread detail requires `mailbox_id`, GETs do not mark mail read, data is plaintext, and draft conflict is JSON `expected_version` plus `409 draft_conflict`. The coordinator publishes lifecycle/write amendments and regenerated consumer types before those new wire handlers/controls are implemented. Prior 412/HTML/route prose does not override the canonical contract. No recipient-truncation amendment is currently justified: the maximum single message fits the 2 MiB budget even allowing 12 serialized bytes per Unicode code point; multi-message pages must shrink with a real continuation cursor. Verify actual serializers, not this arithmetic alone.

## BE02-D02: one private session authority and legitimate entry

`app_auth.sessions` is separate from tenant-scoped `app`. One opaque 256-bit random cookie identifies one row through a digest; Auth access/refresh tokens are encrypted at rest with a dedicated application key. Store bound Auth user/session IDs, selected organization, context ID, CSRF secret, absolute/idle timestamps, refresh generation/claim state and local revocation state. No native bearer implementation now; future presenters must resolve to this authority.

The API gets EXECUTE only on narrowly scoped session functions, not SELECT on the private session table or Auth tables. Function owners are NOLOGIN, non-superuser, NOBYPASSRLS; revoke PUBLIC execution, fix `search_path`, qualify names and use no dynamic SQL. Return only fields needed for the caller's operation. The same-code worker receives only the functions needed to reconcile upstream revocation. App migrations, bootstrap grants and negative privilege tests must land together.

Login and invite/recovery are Rails facades, never an open proxy. `GET /v1/auth/login-challenge` creates a short-lived signed double-submit challenge; bind it to the current opaque session digest when present. `POST /v1/auth/login` exchanges email/password with internal Auth. All unsafe requests require an exact configured Origin and an unpredictable CSRF proof; authenticated product mutations use the session CSRF token. Login/accept use the challenge; refresh uses a challenge bound to the existing session, so a page reload can refresh an expired access JWT without making GET session perform a refresh. Challenge responses contain no account or mail information. SameSite alone, Origin alone and constant markers are rejected.

Rails receives the invite/recovery link, stages its one-time hash encrypted under a short-lived opaque challenge cookie, and immediately redirects to a fixed query-free same-origin form. GET does not consume the invitation: email scanners cannot accept it. Explicit POST verifies the hash with Auth, sets the password through the authenticated user endpoint, validates identity and only then creates the application session. A partially successful exchange remains a bounded pending entry and cannot read mail; retry only the proven password-completion step with its stored tokens. Ambiguous verification requires a fresh invitation/recovery rather than guessing that the hash is reusable. Never place access/refresh tokens in browser responses, fragments, storage or logs. The email's one-time link is an explicit onboarding credential, must be redacted from access logs, and is scrubbed before rendering third-party-free UI.

Initial organization selection uses a server-side identity bootstrap query, choosing the sole membership or a deterministic first membership, with an explicit later switch. The bootstrap function derives memberships from the Auth-verified user, not browser actor headers; its dedicated function-owner RLS policy may read only that user's own organization memberships. The API role's existing tenant policies remain restrictive. A valid identity with no membership is unavailable, not an empty authorized mailbox. Organization-list/switch interfaces use this same narrow bootstrap boundary; no duplicated membership store.

## BE02-D03: authoritative authentication and expiry

For ordinary protected requests: resolve the cookie; check local state/lifetimes; call internal Auth `/user` without an application SQL transaction; then open the short application transaction and recheck the local row, bound identity, current session policy and membership. Auth failure that definitively invalidates identity is 401. Timeout, malformed upstream response or outage is 503, with no protected payload and no automatic cookie deletion. There is no positive authorization TTL or fixture fallback.

The trusted `/user` response establishes signature validity; Rails additionally validates the bounded JWT shape and pinned algorithm/issuer/audience/expiry, non-nil UUID `sub`/`session_id`, and equality with the stored binding and returned user. JWT parsing alone is never authentication. The HS256 signing key can mint privileged tokens and is **not** loaded into Rails for offline validation. The existing narrowly isolated Storage credential exception remains unchanged.

**Explicit synthesis adaptation:** `/user` plus row existence does not prove expiry policy. Add one private SQL predicate resolving the cookie-bound Auth session and checking its existence, matching user, `not_after` and creation-based timebox. Grant its NOLOGIN owner SELECT only on the required `auth.sessions` columns (`id`, `user_id`, `created_at`, `not_after`), never to the API/worker roles; no writes to Auth internals. This is an explicit reviewed privilege boundary, not permission inferred from finding upstream fields. It avoids importing Auth's minting key and makes session expiry part of the same database snapshot as local authorization.

For the local profile, set and verify Auth timebox 12 hours; Rails absolute limit is no later than the bound Auth session's 12-hour deadline. Rails idle limit is 30 minutes since a successfully authorized request or refresh. A small, separate session-maintenance transaction may record activity; the protected mail read transaction remains read-only, and activity never extends the absolute deadline. Expired activity cannot resurrect a row. Auth inactivity/low-AAL/single-session policies must be explicitly verified disabled in this profile; enabling them needs matching enforcement or a revised decision. Keep JWT lifetime 3600 seconds for this slice; the suggested 300-second change is deferred pending measurement, and neither duration substitutes for current authorization. Test forced `not_after` expiry through a controlled fixture, never normal product writes to Auth internals.

The restricted predicate is a deliberate schema-coupling cost for correctness. The alternative of relying solely on local lifetimes misses an administratively shortened Auth expiry; refreshing every read would serialize parallel mailbox requests and rotate credentials unnecessarily. Broad Auth-table grants and service-role application authentication are rejected. A source/image/config mismatch blocks acceptance of this predicate, not all independent implementation preparation. [Pinned session-policy implementation](https://github.com/supabase/auth/blob/v2.196.0/internal/models/sessions.go#L196-L217) and [token-generation implementation](https://github.com/supabase/auth/blob/v2.196.0/internal/tokens/service.go#L599-L682) motivate this adaptation; source inspection is not image attestation.

## BE02-D04: refresh ownership, uncertainty and logout

Refresh has three phases: (1) short transaction conditionally claims the active row using a random claim ID and monotonically increasing generation; (2) commit/release the connection, then call Auth once; (3) short transaction publishes returned credentials only if that exact claim/generation still owns a non-revoked row. Another process/tab seeing an in-flight claim returns bounded `503 temporarily_unavailable` with `Retry-After: 1`; it never calls Auth with the same credential. A process-local mutex, a post-call CAS alone or an advisory lock released before HTTP is insufficient.

An ambiguous HTTP outcome or dead worker becomes `refresh_uncertain`; no lease stealing or blind replay of the old refresh credential. Fail closed, preserve the UI edit buffer, revoke the local row and require sign-in/recovery. An expired access JWT cannot authenticate an ordinary GET, but a locally valid bound cookie plus session-bound challenge can initiate POST refresh; Auth then validates its refresh/session policies. A late success after revocation must not insert/upsert a session, set a new cookie or return credentials. Persist its usable credentials for upstream revocation if available.

Logout defaults to local scope; global scope is explicit. Commit local revocation and durable upstream-revocation intent first, clear the cookie, then attempt Auth logout with an explicit scope. Global application logout revokes all local rows for the bound user. Local success may be reported while upstream revocation is pending, but never as proof of remote completion. The existing worker retries durable intent with bounded backoff and visible terminal failure; no new queue service. Keep an intent long enough to catch a late refresh result. A process crash after Auth issues tokens but before they are saved leaves an honest unresolved upstream outcome: local access stays denied, credentials are not in the browser, and no claim of atomic remote revocation is made.

## BE02-D05: coherent reads, context and revocation

Protected mail reads use `REPEATABLE READ READ ONLY`, set before the first snapshot-taking statement in the existing tenancy wrapper. Preserve transaction-local parameters, single-connection ownership, query-cache clearing, no principal switching in nested work, eager materialization and rollback cleanup. Auth HTTP is outside this wrapper by call ordering and tests; the current wrapper does not magically detect all HTTP I/O.

Let S be that transaction's MVCC snapshot. Recheck local session/policy, current membership and the supplied context/version at S, then read and fully materialize authorized rows from S. An application revocation or membership change committed before S is observed. One committed after S may leave one complete old snapshot response in flight. It must never produce a mixed-authorization page. Re-reading a version inside the same repeatable-read snapshot cannot detect a concurrent commit and is explicitly rejected. PostgreSQL documents this [snapshot behavior](https://www.postgresql.org/docs/17/transaction-iso.html).

No atomicity exists across Auth HTTP and S. Bound the entire server request, including Auth and serialization, by the canonical 10-second deadline; set tighter internal HTTP/SQL timeouts within it and fail rather than stream after the deadline. An Auth ban after the online check or application revocation after S can affect one already authorized response within that bound. There is no promise to retract bytes already delivered or remove already displayed text before the client learns of revocation.

Maintain authorization generation per user/organization; bump affected generations in the membership/visibility/capability change transaction, including shared-mailbox changes affecting organization readers. Never recycle a removed user's old generation. Derive opaque authorization versions with HMAC; they and context headers are consistency hints, never authority. Signed expiring cursors bind actor, organization, context, generation, mailbox/thread/filter/order/limit. Validate current auth first: revoked session 401 precedes stale-context 409; valid absent/foreign object is generic 404. Session bootstrap with no current organization is 404. An old cursor has no authority to recover revoked data.

For writes, take short locks in a fixed order: session row, then affected authorization-generation rows in sorted key order, then business rows. Membership/capability mutation routines take the same generation guards before changing membership. A business write either precedes revocation while owning the guard, or rechecks the new authority after it; no Auth HTTP under these locks. The API has no direct membership-table write grant bypassing these routines. Controlled admin fixtures must use the ordering routine for concurrency tests; a superuser can bypass application guarantees and is not an ordinary actor.

Organization switch validates current membership, rotates context and CSRF, and returns a new bootstrap; ordinary refresh does not rotate UI context. The frontend compares its captured request generation and full context before applying successes **or errors**, clears on known current invalidation, and reboots once on 409. Polling is freshness assistance, not authority.

## BE02-D06: mailbox and message ownership

Retain shared/private semantics: organization members can read shared mailboxes; private mailboxes require explicit current membership. Add explicit membership capability flags `compose`, `approve_send`, `manage_members`, default false; no inferred send authority. A mailbox absent from the authorized list has no capabilities. Admin/bootstrap fixtures may grant flags deliberately; no role is inferred from an email address. A exposes truthful flags even where later UI actions remain unavailable.

B adds tenant-scoped threads/messages and per-user thread read state, with composite organization/mailbox foreign keys, forced RLS and explicit indexes for canonical stable ordering. Counters and previews are computed from authorized rows, including user-specific unread state; GET has no read-state side effect. Preserve nullable timestamps/addresses and empty pages. Bound serialization after escaping; return fewer records and a cursor, never truncated JSON or silently skipped records. No MIME parser, HTML renderer, public attachment URL, transport or arbitrary query engine is added here.

## BE02-D07: durable drafts and operation reconciliation

Use one draft save endpoint with `expected_version`; creation requires version 0, updates require the current positive version. Keep body/recipients/subject validation and a server-owned monotonically increasing version. Drafts retain actor ownership as well as organization/mailbox scope; shared mailbox access alone does not grant another author's draft. `consumed` is a terminal state reserved for the already accepted BE-03 consume-once contract; BE-02 does not implement sending.

Use a separate durable ledger unique on `(actor_id, organization_id, operation_id)`; store mailbox/draft binding, canonical payload SHA-256, expected/result versions, bounded outcome and timestamps in the **same transaction** as the save. Look up the ledger before treating the current draft version as a replay conflict, but only after current authentication/authorization. Same ID plus different binding/payload is `409 operation_mismatch`. A replay returns its original outcome even after later operation B; a last-ID field cannot do this. Concurrent identical operations must collapse on the unique key and return one result, without duplicate version increments.

`GET /v1/draft-operations/{operation_id}` reauthorizes draft ownership and mailbox scope. A definitive applied record proves that operation; absence is `unknown`, never proof “not performed,” because a write may still be in flight. Conflict outcomes can be recorded without modifying the draft. After seven days, local development compacts detail to an `expired` tombstone retaining the identity/digest binding; expired IDs cannot execute again. No tombstone deletion in BE-02; production retention remains unresolved, and later purge semantics must preserve uncertainty. Payload hashes are identifiers, not retained mail bodies.

Revoked session still returns 401, adapting the opinions' overbroad revoked/foreign-404 suggestion. A valid foreign or no-longer-visible operation returns the generic 404. Return version/outcome metadata, not another device's full draft in error responses. Frontend autosave is one in flight with coalescing, retains the local edit buffer on outage/conflict and never interprets a timeout or missing lookup as a successful save or permission to send.

## BE02-D08: collaboration, membership and search

D adds explicit read-state PUT; versioned assignment using `expected_assignment_version` and 409 `assignment_conflict`; plaintext notes scoped to the mailbox; and capability-protected membership changes through the guarded routines. Eligible assignee means currently able to read that mailbox, including current organization membership for shared mailboxes. No silent assignment to a revoked/foreign user. Protect against removing the final mailbox manager in the normal management route; provisioning remains a supported administrative operation, not public signup.

Search is one bounded parameterized PostgreSQL query over authorized plaintext subject/body/participants. Start with existing database facilities; a stored/generated `tsvector` and GIN index are justified only for this actual search route, with representative EXPLAIN evidence. Maximum query 256 code points, page 50, stable signed cursor and a 256 KiB serialized response budget. Return no global counts or snippets from unauthorized rows; no autolinking of hostile content. A small BE-02 synthetic fixture set closes correctness without waiting for a Python fixture task that depends on BE-02. Representative sizing remains OPS/performance work.

## Analytical tradeoff scenarios and retained dissent

These are design simulations, not executed tests. The unavailable Obsidian connection remains a recorded capability gap, as in ADR 0002.

| Scenario | Selected behavior | Alternative cost / residual |
| --- | --- | --- |
| Auth stops after the browser edits a draft | Request returns 503 without cookie deletion; local unsaved buffer survives; no authorized payload fallback | Cached/offline reads improve availability but hide bans/revocation; not accepted |
| Refresh A owns claim, B logs out, A succeeds late | B's local revocation wins; A's publish updates zero rows and cannot set a cookie; persist upstream revoke intent | Post-call CAS alone prevents resurrection but permits duplicate refreshes; pre-call claim required |
| Worker dies after Auth rotation but before storing credentials | Local uncertain state fails closed; explicit reauthentication; remote outcome remains tracked | Lease stealing/reuse can recover availability but needs stronger evidence than a documented reuse window |
| Membership commits just before versus just after S | Before: deny/current context; after: complete old snapshot within deadline | A second same-snapshot read cannot promise denial; global serial locks would burden all reads without Auth atomicity |
| Admin shortens Auth `not_after` while access JWT is unexpired | Private predicate sees committed policy at S and denies | `/user` plus local TTL can miss it; broad Auth access or a minting key increases privilege unnecessarily |
| Draft A commits, response lost, B commits later | A's durable operation result remains provable; different intent cannot reuse A's ID | Last-ID field loses evidence; missing row cannot distinguish in-flight from absent |
| One hostile maximum message vs twenty such messages | One bounded item fits; accumulate only complete items under 2 MiB and continue | Unnecessary recipient-schema change breaks existing consumers; arithmetic does not replace serializer tests |

Acceptance requires Docker lint, strict type checks, unit/integration/contract and real service tests, then actual UI verification in the integrated application. Review every changed code area in assignments of at most 200 lines, plus a dedicated design reviewer; record defects and density in `code-reviews.md`. No application test or code review result is asserted by this document. Production retention, provider activation, recovery targets, native behavior and measured capacity remain outside this decision's acceptance claim.
