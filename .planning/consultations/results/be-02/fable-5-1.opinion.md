## Verdict and demonstrated facts

**Verdict: change, then dispatch only the first slice.** Support the BE-02A/B/C/D decomposition and the read contract. Change four design points before freezing: the Auth callback path, the session store's schema placement, the write-grant model, and the detail-page byte budget. Defer Devin dispatch until BE-01 has an explicit sequencing disposition, the three fresh opinions and Astra synthesis exist, and live credit is read. The credit question is a feasibility blocker, not a permission gate: the last visible balance is stale and would not plausibly cover full BE-02, so only BE-02A should be the first bounded dispatch.

Demonstrated from the packet, not hypothesis:

- **Routes expose only health and readiness.** The four reads are absent, and the API role has SELECT only on four tables with no write grants or write policies. Every BE-02 mutation needs new grants, new WITH CHECK policies and a migration test in the existing migrator-only pattern.
- **Auth mail links cannot currently resolve.** The compose file sets the external URL to the Auth container's own port and the mailer paths to a gateway-style verify path. Auth serves the bare verify path, so an invite link built from these settings points at a path Auth does not serve. This is a configuration defect in the frozen foundation, not a BE-02 feature gap.
- **Issuer and call URL differ by design.** Auth signs tokens with a localhost issuer while Rails reaches Auth by internal service name. Rails must compare the issuer claim against a configured constant, never against the URL it dials.
- **The signing secret is a minting key.** The generated secrets file holds one symmetric secret shared by Auth, PostgREST and Storage, plus a service-role token valid for decades. Any Rails process that loads that secret for offline JWT checks could mint service-role tokens Storage accepts. Config today does not load it. Keep it that way.
- **The tenancy wrapper forbids Auth I/O inside the tenant transaction** by construction, since nesting with a different principal fails and ambient transactions are rejected. Identity verification must complete before the wrapper opens.
- **The read contract's byte budgets can be exceeded by one hostile record.** This follows from the schema limits alone:

| Object | Worst case before escaping | Escaped at six bytes per char | Budget |
| --- | --- | --- | --- |
| One message, address list only | 100 addresses × 512 chars | about 307 KB | shares 2 MiB |
| 20 bodies at max length | 20 × 16384 chars | about 1.97 MB | 2 MiB |
| 50 summaries | 50 × 1024 chars | about 307 KB | 256 KiB |

Summaries shrink safely with a continuation cursor. A single message cannot, because the schema has no truncation flag for the recipient list.

## Boundary decisions

- **Legitimate browser entry.** Recommendation: Rails owns the public origin and proxies only the verify path to Auth. The mail template should carry a token hash, and Rails should exchange it server-side with Auth's verify endpoint, then set a password through the authenticated user endpoint and finally set the opaque cookie. No tokens ever reach the browser. Evidence gap: whether the pinned image accepts invite-type token-hash exchange is not shown in the packet and must be a pinned-image experiment. Objection: a proxy adds a route that could be abused as an open relay to Auth. Alternative: expose Auth directly on a loopback port for local only. Tradeoff: that leaks the implicit fragment flow into the browser, which the research delta already flags. Acceptance check, not run: invite captured in Mailpit, link resolves through Rails, no access or refresh token appears in any browser request, response or storage.
- **Refresh and logout.** Recommendation: store sessions in a separate private schema, not under the tenant-scoped app schema, because the session lookup must happen before any tenant claims exist. Grant the API role only EXECUTE on definer functions for lookup, rotate and revoke. Refresh writes must be conditional updates on an active row with a rotation counter. Browser default is local-scope logout with an explicit global option. Failure sequence: tab A begins refresh, tab B logs out and the row is deleted, then A's new tokens arrive and an upsert recreates the session. Regression check: assert zero rows updated after logout, discard the new tokens, enqueue an upstream revoke for them, and assert the cookie is rejected on the next request. Residual: Auth may have already issued tokens against a session it later deletes, so the upstream reconcile job is required, not optional.
- **Current authentication.** Recommendation: call the user endpoint once per request before opening the tenant transaction, require a non-empty session identifier in the claims, and enforce Rails-owned absolute and inactivity lifetimes locally. Treat Auth's timebox and inactivity policies as defense in depth since the packet does not show the middleware applying them. Outage fails closed with 503 and no fixture path. Objection: one Auth round trip per read adds latency on a ten-person system. Alternative: offline signature validation. Tradeoff: it requires the minting secret in Rails and cannot see bans or logout, which the official guidance already warns about. Check: ban, global logout and expiry each deny on the next protected call with 401.
- **Organization switch.** Recommendation: a CSRF and Origin protected POST that validates the target against currently visible memberships inside the tenant wrapper, then rotates context and authorization version in the session row. Refresh does not rotate context. Failure sequence: a search response from the old organization lands after the switch. Check: old context headers return 409 with no body data, and the frontend generation guard discards it.
- **Immediate revocation and read consistency.** Recommendation: store an authorization version per user and organization, bumped by a trigger inside the same transaction as any membership mutation. Each read does one tenant transaction at repeatable read: read the version, read the data, re-read the version, and return 409 if it moved. The linearization point is the commit of the membership change or local revocation. Disclosed bound: a request that passed the Auth check up to the request deadline earlier can still serialize data. Failure sequence: membership removed between version read and row serialization in a read-committed transaction. Check with two real connections: remove membership mid-request and assert the response is 401 or 409, never a partial page.
- **Durable draft operations.** Recommendation: an operations table keyed by actor, organization, mailbox, draft and client operation id, holding payload digest, outcome and resulting version, inserted atomically with the draft update. Replaying A after B returns A's recorded outcome. A different digest under the same key returns conflict. Expired lookups return unknown, never not-performed. Add a consumed state now so BE-03 can consume a draft with a single conditional update. Failure sequence: two devices save version four; one wins, the other sees 409 and must receive conflict metadata, not the full draft. Check: lost response for A, accepted B, lookup A returns version five accepted, and a revoked caller gets 404 on the same lookup.
- **Remaining BE-02 and integration.** Recommendation: amend the contract before BE-02B with a recipient truncation flag or a lower stored address bound, otherwise one message can make a conversation unrepresentable. Parse the raw query string for duplicate parameters, since Rails merges duplicates silently. Search runs as a single RLS-filtered query with no cross-organization counts, snippets built from authorized rows only, and no autolinking. Objection: the search performance check depends on a dataset from the Python fixture task, which itself depends on BE-02. Resolve by a minimal fixture generator inside the BE-02 test scope and defer sizing to OPS-01.
