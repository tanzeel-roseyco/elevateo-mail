### Baseline, repeat, and noise rule

For an accepted candidate, use sequential fresh projects in the order **A, B, A-prime, B-prime**: baseline, candidate, unmodified baseline again, candidate confirmation. A/B/A-prime is the minimum diagnostic bracket; B-prime is required for promotion. A-prime must rebuild the baseline state from its recorded source/fixtures, not merely rerun a warm pass within B. Abort further candidate work early when A is invalid or the candidate fails a contract.

For healthy HTTP cells, predeclare 15 seconds warm-up followed by three fixed 30-second measurement repetitions at each stage. Keep request count, elapsed time, errors and raw supported samples. A different duration needed to obtain sufficient samples must be declared and applied equally to all stages; do not extend only favorable runs. Report P50 with at least 200 samples, P95 with at least 1,000, and P99 with at least 5,000; these are reporting floors, not a promise of statistical confidence. Below them, report counts and descriptive ranges and withhold the corresponding tail claim. Truncated, capped, missing or failed sample streams invalidate the affected comparison.

Use this conservative decision rule in the metric's original units. For a lower-is-better metric, let each stage's value be its repetition median. Define `N` as the maximum of the A/A-prime median difference, the within-stage repetition ranges, and instrument resolution. Define `D = min(A, A-prime) - max(B, B-prime)`. A claimed improvement requires `D > 2 * N`. For higher-is-better metrics reverse the subtraction. Report all repetitions and absolute values as well as the percentage. This is an engineering acceptance rule over a small experiment, not a confidence interval or a causal proof about all production loads.

Predeclare primary metrics: E1 has health keep-alive c=1 latency and whole-Rack allocation count; G1 has attributable worker storage-write cost if observable; G2 has worker cgroup CPU time per elapsed second including health probes. E2 requires its own explicit hypothesis before code changes. A resource-only improvement must be described by that metric, not relabelled faster requests. Supporting healthy-ready, concurrent health, worker memory, probe correctness and cold-boot measurements must not show a regression larger than their corresponding `2 * N` band. A resource/boot regression that exceeds that band is rejected under this gate; accepting a tradeoff needs an explicit revised decision before promotion, not a retrofitted explanation after seeing B.

If the load client spends a sustained measured window near its CPU cap (use the predeclared 90% warning threshold) while the API has spare capacity, throughput/latency comparisons may be client-bound and are inconclusive. Do not silently increase client resources in B alone. Change the client/caps only as a separately recorded measurement repair and rerun A. A new load-tool dependency needs a demonstrated need, pinned source and review; it is not a default addition.

| No-change acceptance | Suppose a candidate lowers a primary metric by 0.5% while baseline drift/range is 1%. It does not clear the declared 2-times-noise rule. Keeping that change on a speed claim would add permanent configuration without demonstrated benefit. A larger allocation reduction with unchanged noisy latency would support only an allocation claim if it was predeclared and all guards pass. | Retain the baseline when evidence is indistinguishable. Record what was tested, uncertainty and the next useful business workload. Do not call missing tests a no-change success or imply that future mailbox paths have been optimized. |

The optimization ordering is correctness, security, maintainability, performance, then cleverness. The mechanism being measured must be small enough to explain and revert. Lower probe CPU is not a valid bargain for delayed failure detection; lower request latency is not a valid bargain for weakened tenancy; lower steady-state cost is not automatically worth an unmeasured boot or memory regression.
