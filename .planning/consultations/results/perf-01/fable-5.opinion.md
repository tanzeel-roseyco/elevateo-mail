# PERF-01 independent opinion — Fable 5 (claude-fable-5)

Read-only consultation from the supplied packet only. No tests were run; every proposed check below is **not run**. Where I rely on an omitted file (run-baseline.sh, lib.sh, load.rb, test suites) I say so.

## Q1 — Verdicts per candidate class

**A. RLS supporting indexes — support (no-change).** The database-path inventory (docs/perf-01/database-path.md §3) proves every policy predicate is PK/UNIQUE-covered except `own_mailbox_membership`, and all tables are one page. No index can register at product scale. The verdict is sound; the only evidence that would overturn it is the tier-3 stress fixture showing plan degradation, which is explicitly non-representative. Record the `mailbox_memberships(organization_id, user_id)` gap as a BE-02 note, as the team already did. No prerequisite blocker.

**B. SQL-standard-body STABLE `context_uuid` — support (defer behind P1 evidence).** The analysis is correct and unusually careful: the IMMUTABLE trap (folded tenant claim into cached generic plans) is the highest-severity silent failure in the packet, and both database-path and design-adversary independently flagged it. The ≥20%-of-execution / ≥0.2 ms threshold before P2 is reasonable. Evidence that would overturn no-change: `pg_stat_xact_user_functions` showing function self-time dominating at tier 2 — plausible only under the tier-3 diagnostic. Optional improvement, never a blocker.

**C. Tenancy round-trip reduction — support (forbidden).** Correct. Each rejected idea in design-adversary §4(c) maps to a tested invariant (transaction-local claims, T3 cache-leak class, no interpolated SQL). The only legitimate deliverable is measuring the three-round-trip floor as a BE-02 budgeting input. Nothing overturns this within PERF-01's invariants.

**D. `/ready` fan-out/cache — support (no-change / forbidden), and I agree with the correctness reclassification.** A readiness cache is global state, forbidden outright. Fan-out trades a few milliseconds on the healthy path for thread-amplification during outages — the wrong trade. The unbounded DB `connect_timeout` and the AR lease held across ~12 s of HTTP waits are real defects (five slow probes pin all five Puma threads and starve `/health`), but fixing them changes failure behavior, not speed. Classifying them as correctness work recorded separately is right.

**E. development.rb + puma.rb — support (strongest candidates), with the stated gates as prerequisite blockers.** The reasoning is solid: the image copies source and Compose mounts none, so Reloader file-watching and `ActionDispatch::Static` stats against a missing `public/` are pure per-request cost that can never observe a change. The three blockers (contract tests on the baseline image, a measured baseline, the design gate) are genuine prerequisites, and I'd add a fourth: the Steep gap must be resolved or explicitly waived, since the repository's own standards make any config/controller change untypeable today. Evidence that would overturn: baseline showing Reloader/Static cost below the pass-1-vs-pass-2 noise floor — then the truthful outcome is no-change even for the "strongest" candidate.

**F. YJIT / frozen `/health` body / log level — support as stated.** Verify-first for YJIT is right (`load_defaults 8.1` may already have enabled it; a proposal before reading `RubyVM::YJIT.enabled?` in-container would be speculation). The frozen body is safe but likely unmeasurable at whole-request level; fine as a rider on an already-gated controller change, not alone. Log level correctly stays an experiment pending a Codex operator-signal decision.

**G. Worker tmpfs + `--disable-gems` probe — support (worth measuring).** The healthcheck hypothesis (twelve Ruby cold starts per minute dominating sixty microsecond-scale publishes) is credible and cheaply testable via the cgroup-minus-PID subtraction method. The `securerandom`-without-RubyGems check must precede the (c1) proposal, as specified. One caution the packet understates: `bin/worker-health` loads `heartbeat.rb`, which requires `securerandom` at file level even though `healthy?` never uses it — so the `--disable-gems` precondition is load-time, not call-time, and the in-container check must exercise the actual probe command, not just `require "securerandom"` in isolation. Rejecting interval/window and shell-check variants is correct; the shell divergence list (newline stripping, 64-bit wrap) is exactly the drift that kills reimplementations.

**H. Truthful no-change — support.** Expected for A, C, D-fan-out, and plausibly B and even E. The brief explicitly prefers this over speculative complexity.

## Q2 — Measurement plan adequacy

The five primary metrics are well-chosen and sufficient: each maps to a candidate class (E/F → `/health` P50+allocations and boot time; D → `/ready` healthy P50; G → idle worker cgroup CPU; E/F(YJIT) → RSS). The matrix with pass 2 as an unmodified repeat giving a per-cell noise floor, and the "not distinguishable below 2× noise floor" rule, is the strongest part of the design. Percentile floors (P50≥200, P95≥1,000, P99≥5,000) are honest; note that 20 s tier-1 `/ready` runs will likely fall under the P95 floor, which the plan already anticipates.

**Missing:** (1) a stated plan for *ordering* bias across candidates — A/B interleaving appears in request-path's spec but the lead's accepted matrix runs whole projects serially; serial baseline-then-candidate on a shared production host is vulnerable to drifting neighbor load. At minimum, the host-quiet guard readings must be compared between the two projects and a large divergence should invalidate the comparison, not just annotate it. (2) The 120 s idle window with 3 samples supports means/min-max only, which worker-path concedes; fine, but the report must not present a sub-noise tmpfs "win." (3) Nothing validates that the *candidate* image differs from baseline only by the intended change — the manifest's tree hashes cover this if the comparison step is explicit; make it so.

**Unnecessary:** tier 16 on `/ready` in both modes doubles load time for little information once tier-4 queueing is characterized; shrinking is acceptable if Codex wants a shorter reservation.

**Ruby stdlib client:** acceptable, with the packet's own caveats enforced. It invalidates results when (a) `perf-load` CPU sits at its cap while `api` is below its own — the `client_saturated_hint` plus stats.csv cross-check handles this, and such cells must be labeled client-bound, never used to compare candidates on `/health` throughput at tier 16; (b) GVL-induced client-side queueing inflates latency percentiles at high tiers — client-observed latency at tier 16 measures the client as much as the server, so candidate comparisons at that tier should rely on the server-side `Completed` timings as corroboration. The escalation path to a digest-pinned `oha` is correctly gated.

## Q3 — Shared-host safety: residual gaps and regressions

The four confirmed cleanup findings (C1–C4) are real; I verified each against the supplied cleanup.sh revision. Judging the required repairs:

- **C1 (manifest grep):** the required structured, fail-closed proof is sufficient *only if* it also binds the manifest to this run — verify `manifest.json` records this `PERF01_PROJECT` and run-id, not merely "a manifest with synthetic_only:true exists in the evidence dir." Otherwise a copied evidence dir proves the wrong run. Regression: run cleanup with (i) no manifest, (ii) malformed JSON, (iii) `synthetic_only:false`, (iv) a valid manifest from a different project; all four must retain the volumes and exit non-zero. **Not run.**
- **C2/C3 (build cache, pulled images):** the required repairs are directionally right but both rest on the same weak primitive: *absence-at-preflight is not creation evidence* on a host with concurrent workloads. For C3, the fix should be stricter than "retain without exclusive evidence": record `docker image inspect` metadata (ID + pull time if available) immediately after this run's own pull completes, and remove only an image whose ID matches that record and has zero users. For C2, a named task-scoped builder (`docker buildx create --name perf01-<hex>`) and pruning only that builder is the sound fix; diffing the shared default builder's cache IDs can never prove ownership. Regression: simulate a second workload pulling a pinned image / adding cache records between preflight and cleanup via the fake-docker CLI; cleanup must retain both. **Not run.**
- **C4 (hidden list failures):** required repair matches the pattern already applied to sample.sh/preflight (items 6–9 of §7.1). Regression: fake-docker returning non-zero for each of `ps -aq`, `volume inspect`, `network inspect` mid-cleanup must produce `retained`/`failed` entries and non-zero exit, never an empty "nothing to clean" success. **Not run.**

**Remaining gaps beyond C1–C4:** (1) cleanup.sh's own Docker calls are not time-bounded — a hung daemon stalls cleanup indefinitely; apply the sampler's `timeout -k` pattern. (2) `docker ps -aq --filter ancestor=` matches containers of the exact image ID but not containers started from a retagged/different reference sharing layers; low risk, worth a comment. (3) Secrets: `ops/local/.env` is excluded from evidence and the test copies, and the secrets log is redacted — good — but the cleanup summary tee's `mounts` lines could expose host paths; benign here, verify no env values ever transit `record()`. A regression asserting no evidence file matches generated password patterns would close this. (4) The guard regression suite itself (tests/run-baseline-guards.sh) is unexecuted; its first run is evidence, and until it runs, all eleven harness repairs are unverified claims — the packet says this honestly, and the gate should hold it there.

## Q4 — Ordering and gates

**Agree on all three.** Contract tests before any request-path change is non-negotiable: `/health`, `/ready`, the 503 path, and the error envelope have zero coverage today, so a config change could silently alter the compose healthcheck's dependency without detection. The Steep gap is correctly treated as pre-existing and escalated to Codex rather than speculatively repaired — though I'd state plainly that it blocks P3/P4 controller edits specifically, while E (config-only files outside Steep's check paths) can proceed without it if Codex confirms `config/` is outside the Steep targets (`Steepfile` checks `lib/elevateo` and `app/controllers` only, so it is). The correctness classification of `connect_timeout`/lease release prevents a real repair from being miscounted as a performance win and keeps its before/after evidence in the failure-behavior lane. Ordering overall: contract tests → baseline → gate → candidates is right; I would additionally require the guard regression suite to pass **before** the first real baseline, since an unverified harness producing the baseline taints everything downstream.

## Q5 — Invariant risk and the riskiest failure sequence

Candidates E, F, G as specified touch no invariant: identity, RLS, roles, parameterized queries, hold, egress, and capture-only mail are untouched by config/Compose-fragment changes, and the overlay keeps `internal: true`. The riskiest candidate is **B**, via the IMMUTABLE/foldable-function trap:

1. A later implementer, seeing the SQL-body function, "improves" it to IMMUTABLE or a form the planner can constant-fold.
2. Rails prepared statements switch to a generic plan after five executions on a pooled connection; the plan now embeds user A's folded UUID.
3. User B's request reuses the pooled connection and the cached generic plan; the policy qual evaluates against A's identity. Cross-tenant read with no error, no log, passing all single-principal tests.

**Regression (not run):** on one connection, PREPARE the mailbox select, execute ≥6 times as principal A (forcing the generic plan), switch transaction-local claims to principal B, execute again, and assert B's row set — plus a catalog assertion that `provolatile = 's'` for `app.context_uuid`. This should land in the gate's acceptance checks for any P2 proposal and ideally as a standing guard regardless. Secondary risk: a `--disable-gems` probe that fails at load time would read as "worker unhealthy" — fail-closed, so safe, but it must be tested against a *live* worker before the Compose fragment is proposed.

## Q6 — Honest limits

With no frontend, no mailbox API, and `Tenancy.with_context` uncalled outside tests, "frontend-serving backend speed" reduces to: `/health`/`/ready` latency, framework/connection defaults, and the tenancy wrapper's fixed per-call floor. What can be concluded: whether E/F/G move those specific metrics beyond noise, and the documented cost floor future requests will pay. What cannot: anything about mailbox query performance, serialization of real payloads, pagination, concurrency under business load, or user-perceived speed — there are no business endpoints to measure. **Defer to BE-02+:** the `mailbox_memberships(organization_id, user_id)` index, any `context_uuid` work absent P1 evidence, Puma tuning beyond the explicit pool pairing, request budgets derived from the tenancy floor, and all caching questions. The single most valuable PERF-01 output may be the measured tenancy/round-trip floor and the EXPLAIN call-count evidence as BE-02 design inputs — worth stating as a deliverable even under a full no-change conclusion.

## Verdict, recommendation, objection, acceptance — consolidated

**Verdict: support with changes.** Prerequisite blockers: Codex reservation; contract tests passing on the baseline image; guard-regression suite executed and passing before the first baseline; C1–C4 repairs verified (with the C1 run-binding and C2 named-builder strengthenings); design gate for any code/config/Compose change. Optional improvements: time-bound cleanup's Docker calls; drop tier-16 `/ready`; add the prepared-statement cross-principal regression as a standing test.

**Strongest objection:** the entire measurement edifice (≈1,000 lines of unexecuted harness, eleven repaired defects, a fake-docker regression suite) is heavyweight relative to the plausible findings — likely one config file, one Compose fragment, and a no-change report. **Simpler alternative:** run only the contract tests, the in-container verification set (Puma banner, YJIT, `--disable-gems`, lease behavior), and a minimal c=1 `/health`/`/ready` + 120 s idle baseline; skip the full matrix unless E shows a visible delta at c=1. **Tradeoff:** loses concurrency/queueing characterization (W6-style starvation evidence) that genuinely informs the `/ready` correctness repair — so if Codex funds the reservation, the full matrix is defensible; if budget is tight, the minimal path still supports every verdict above.

**Residual uncertainty:** harness behavior on first fleet-02 execution (expected one iteration); whether YJIT is already enabled; whether `securerandom` loads under `--disable-gems`; actual Puma 7.2 defaults; neighbor-load noise magnitude. All resolvable only by the gated runs. Every test named in this opinion is **not run**.

## Top three cross-task recommendations

1. **Gate the harness before the baseline:** execute the fake-docker guard regression and the C1–C4 cleanup regressions as the first reserved action; an unverified harness must not produce the evidence everything else depends on.
2. **Make the IMMUTABLE/plan-fold cross-principal regression a standing test now**, independent of whether P2 ever proceeds — it guards the single silent cross-tenant failure mode in this codebase against any future "optimization."
3. **Pre-commit the no-change report shape:** require the final submission to present the tenancy floor, EXPLAIN call counts, and in-container verification facts as first-class deliverables, so a no-change conclusion is a complete, useful artifact rather than an apparent failure — this removes the incentive to manufacture a win.

**Hard contradictions:** none found. The packet is internally consistent; the only tension (brief demands "make the backend fast" vs. a base with nothing meaningful to speed up) is already resolved honestly by the brief's own no-change clause.
