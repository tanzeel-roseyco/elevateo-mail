# ACCEPTANCE-FIXTURE-OBSERVER-R1 — Fable 5 independent opinion (task 2)

Verdict: **support with changes**. The scoped extensions are implementable against the inspected schema and seed, provided the fixture contract is versioned rather than widened, the observer is a new least-privilege PG role coordinated with the schema worker (whose private-schema repair is a hard prerequisite), and the DRAFT-003 contracts lean on the already-inspected operation ledger semantics instead of inventing new hooks. One likely cross-source inconsistency inside the packet needs delta reconciliation before any fixture work (FAB5-08).

**Assumptions stated:** no runtime evidence exists; HTTP validators, response statuses, byte budgets, `acceptance_seed_support`/`Runtime`, `app.draft_scope`, `app.context_uuid`, controllers, the detail write path, the Auth recovery flow and `/auth/complete` are all uninspected and are treated as contracts to freeze, not facts. Obsidian is unavailable; tradeoffs below are analytical only. Nothing here duplicates the schema, existing-case or session-race workers.

## Numbered recommendations

**FAB5-01 — Versioned additive fixture schema v2 (adapt proposal).**
Adopt the prior review's proposal of a typed extension section, concretely: `schema_version: 2` adding an optional `extra_mailbox_memberships` array (actor alias, mailbox alias, capability set) and an optional `extra_mailboxes` map, with `verify_actors` changed from "exactly one row" (`acceptance_seed.rb:136–146`) to an exact-set comparison derived from the contract (base membership plus declared extras, nothing else). This preserves the guard's intent — any undeclared row fails — instead of weakening it. Base actor aliases, capabilities and meanings (including `revoked`/`no_membership`/`disabled`/`other_org`) stay byte-identical for v1 consumers.
*Evidence:* seed lines 136–146; `seed-contract.json` single `mailbox` field per actor; packet contract-gates section. *Counterexample:* accepting "at least the expected rows" would let a stray membership silently grant READ-001-P's "inaccessible comparison mailbox," passing an exclusion assertion falsely. *Verification:* seed run with v2 contract fails on one extra undeclared row; v1 contracts still verify. Review slices: contract+loader diff (~60 lines), `verify_actors` diff (~40 lines). Owner: this worker.

**FAB5-02 — READ-001-P entirely at seed time, never mid-run (new recommendation).**
Membership mutations advance actor-global authorization generations (seed:64–69 shows +4 for two add/delete cycles; +2 for a compose toggle at :90–98), and `authorization_version` is signed from the generation at verify time (:149–151). Therefore the second/third mailbox memberships for the chosen actor (I suggest `reader`, keeping `composer`/`approver` untouched for the sibling's privacy cases) must be inserted before verification and publication. Per-mailbox resources do not isolate generation changes (invariant 3), so no test may add a membership live and expect other cases' frozen versions to survive. Add: one extra mailbox with a strictly larger capability set, one with a strictly smaller set, and one primary-org mailbox with no membership as the exclusion probe. Happy path: login, enumerate the complete authorized ID/capability set, exclusion confirmed. Failures: (a) UI shows the excluded mailbox — leak; (b) capability set shown is the union across mailboxes rather than per-mailbox — authorization-presentation defect. Proof: typed observer fact listing expected vs. actual membership rows; cleanup: dataset is disposable per attempt. Slice: ≤120 lines seed+contract.

**FAB5-03 — AUTH-006-P with an isolated fixture lifecycle (accept proposal, with one constraint).**
Use an existing actor, the private Mailpit capture, the documented server-staged query-free entry and explicit POST acceptance (test-expansion-plan topology table). Because supported recovery may change the password or rotate session state, run it against its **own fresh fixture stack** (the seed already demands fresh Auth data, seed:15–16), either as the last case in a dataset or in a dedicated dataset — never before cases that reuse that actor's published `authorization_version`. Assert: Auth verification precedes Rails session creation; `/auth/complete` carries no secret query; no token/cookie/mail body in artifacts (invariant 1). Dependencies to inspect before implementation: Auth recovery template/config, Mailpit API read path, `/auth/complete` contract. Failures: (a) recovery mail contains a tokened URL that the test would have to click — record as topology gap, do not scrape the token into artifacts; (b) recovery silently invalidates other sessions of other actors — would surface as unrelated case failures; isolation prevents misattribution. Slice: ≤150 lines.

**FAB5-04 — Observer = dedicated read-only PG role, new connection, snapshot after settle (adapt proposal).**
`app_drafts_private` revokes everything from the API/worker/read roles (`tables.sql:2–3`), and `operations` has FORCE RLS (:44–45). The observer therefore needs an explicit role — propose `elevateo_observer` with `SELECT` on the needed `app.*` tables and `app_drafts_private.operations` only (or policies granting it; which mechanism is the **schema worker's** call, and that worker's restricted-role CREATE failure is a prerequisite blocker; do not count it again as a defect here). Each observation: new connection, `BEGIN READ ONLY ISOLATION LEVEL REPEATABLE READ`, fixed parameterized queries keyed to the case's synthetic org/actor/draft/operation IDs, exact content compared privately (payload digest from `operations.payload_digest`, `tables.sql:33`, plus actual `body_text`/`version` — persisted state, not the request copy), exporting only booleans/counts/versions/outcome plus a proof reference. Browser receives no credential, no SQL, no row dump (invariant 4). Observer never takes row locks and never runs inside the race worker's 1-second lock window (invariant 8): it observes only after a named settle/ack. *Counterexample:* snapshotting while a held transaction could still commit misreads "missing" as "no commit" — exactly invariant 5's trap. *Verification:* role can read, cannot write, cannot see other datasets' rows beyond parameter scope; a deliberately delayed commit test shows the observer waits for the settle signal. Slices: role/grant SQL (~40 lines, schema worker), observer module (~180 lines, this worker).

**FAB5-05 — Control channel: minimal fixed file/socket protocol, pending reuse check (accept proposal).**
Per invariant 6, first ask root whether the existing evidence collector already offers a private runner channel (uninspected — the 52 unallocated lines are not authority to look). If not, use a root-owned private channel (named pipe/socket or paired request/response files in the task directory) carrying versioned NDJSON with exactly three verbs: `observe_draft`, `observe_operation`, `ack_phase`. No caller-supplied SQL, no generic fault verbs, nothing on a product route. Failure modes: protocol timeout = evidence failure/unknown, never a pass; malformed frame = case blocked. Slice: ≤120 lines.

**FAB5-06 — Three distinct DRAFT-003 evidence contracts bound to the inspected ledger (accept proposal, sharpened).**
The operation lookup function already defines the needed semantics: not-found → `outcome: unknown` (`operations.sql:13`); recorded detail is `applied` or `conflict` (`tables.sql:36–37`); expiry is a separate `expired` outcome at seven days (`operations.sql:17–20`).
- **P (after-COMMIT loss):** forward the real PUT; hold the response; observer confirms operation row with `applied`, draft at n+1, digest match against the frozen submission; **live observer acknowledgment, then drop**; real same-operation lookup returns the applied detail with `recorded_at`. A held 200 is never COMMIT (invariant 5).
- **F1 (no-forward loss):** abort before forwarding; record the gate as permanently closed; await route/transaction settlement signal; observer confirms zero operation rows and draft unchanged at n; real lookup returns `unknown` — and the test must assert the **client stays uncertain**, because `unknown` is correct product behavior, not rollback proof.
- **F2 (conflict-loss):** create a genuine stale-version conflict so the ledger records `conflict`; drop that response; lookup the same operation and assert explicit conflict plus retained local text. Expiry substitution is structurally impossible here (seven-day window), which directly repairs the prior review's defect 1.
*Dependencies to inspect:* the PUT controller and the detail **write** path (only the read path was supplied); whether every save writes an operation row is assumed from the schema, not proven. *Verification:* each case's observer facts match its contract; a deliberately mislabeled F2-as-expiry fixture fails. Slices: one case family per ≤200-line review.

**FAB5-07 — DRAFT-001-F1/F2 with observer no-overwrite proof (accept proposal).**
F1: two contexts of the same author load version n; B commits n+1; A saves at n; expect the documented 409 `draft_conflict` (contracts-and-reliability `/v1` table), unchanged local text, and observer proof that persisted content equals B's commit. F2: authenticated browser API call with subject length 999 or body 65537 (one past the CHECKs at `drafts.tables.sql:10,12`) or an invalid reply binding; observer proves version and content unchanged before/after. **Do not hardcode the over-limit HTTP status or body shape** — invariant 7 says they are not supplied; assert on observer facts plus "a bounded error occurred," and file the status contract for inspection. Failure modes: API truncates instead of rejecting (data-mutation defect); DB CHECK fires as a 500 (boundary-validation gap). Slice: ≤180 lines.

**FAB5-08 — Reconcile a probable schema/seed mismatch before anything else (new recommendation; blocker).**
The seed inserts `read_state_version` into `app.thread_read_states` (seed:107–109), but the allocated `be02_threads/tables.sql` (same backend base `5785eba`) defines that table **without** such a column (:31–43). Either a later uninspected migration adds it, or the seed fails at runtime. The packet itself warns schema tables may change and demands explicit delta reconciliation. This is the one candidate **confirmed-code-defect-class** finding in this review (pending reconciliation), separate from the sixteen missing acceptance controls and separate from the known private-schema prerequisite. It also matters directly for READ-002-F2's GET-invariance comparison, which must know the real read-state columns. *Verification:* coordinator allocates the migration delta (this is a legitimate use of remaining budget via coordinator allocation, not self-service inspection).

**FAB5-09 — READ-002-F2 using existing nullability plus seeded hostile plaintext (accept proposal).**
`threads.subject` and `messages.sender` are nullable (:6, :18) and the seed already carries literal `<b>` text (seed:86). Add seed rows with NULL subject, NULL sender, empty recipients, and script/image/link-like plaintext. Assert literal DOM rendering, zero remote requests, and — via the observer — byte-identical read-state rows for the actor before and after the GET. No HTML rendering exists by policy (STANDARDS §6), so the hostile samples test plaintext handling and auto-linking, not a sanitizer. Slice: ≤140 lines.

**FAB5-10 — DRAFT-008-F2 reuses the response-loss gate; absent recovery is a reported product gap (accept proposal).**
Establish uncertainty with the FAB5-06-P control, reload, and inspect what the implementation actually recovers (operation identity retention, honest persisted-vs-local claims). If no durable recovery exists, record the matrix-required gap; the prior review already established that `draft.e2e.ts:41–44` reloading a confirmed save cannot close this. Do not implement recovery to make the test pass — that is a product change outside this worker.

**FAB5-11 — Lifecycle: fresh dataset per engine/attempt; destructive cases isolated (accept proposal).**
Fresh disposable Auth/PG dataset per attempt (seed:15–16 enforces this), fixed IDs safe only within that namespace. Generation-mutating cases (AUTH-006-P, anything touching memberships) get fresh stacks or run last; never rewind generations or depend on order (invariant 3). Analytical tradeoff: fresh stacks cost seed time per destructive case but eliminate the whole class of version-poisoning flakes; isolated per-mailbox resources are cheaper but demonstrably insufficient for actor-global generations — prefer fresh stacks. Failed partial seeds are discarded whole, never published (publish-after-verification, seed:23–28).

**FAB5-12 — Race-worker handoff and report integration (accept proposal).**
Hand the sibling the same observer verbs plus `ack_phase`; the race worker owns barrier placement and the authoritative lock-wait/settle signals; the observer only reads after those signals and never stretches the 1-second lock budget. Report integration: one new `db_proof_ref` field plus typed-fact object in the existing `cases.jsonl` record (test-expansion-plan schema), sealed by root's collector; no parallel report format.
