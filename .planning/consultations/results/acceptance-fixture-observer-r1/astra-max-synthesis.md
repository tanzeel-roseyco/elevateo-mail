## Preserved dissent and analytical simulations

These simulations are state traces and cost reasoning only. Obsidian is unavailable; no executable simulation or application test ran.

1. **Shared immutable classes versus fresh cases.** Opus and Fable 5.1 favor cheaper class-based stacks; Fable 5 offers selective isolation. Let a published actor be at generation g. A later membership insertion advances its real generation while another case still holds the old signed version, so an unrelated mailbox request can fail. Case-owned mailbox IDs do not prevent that trace. Recovery also has uninspected session effects. Fresh engine×case×attempt datasets remove both couplings at the cost of repeated seeding; root can reuse image builds and execute sequentially. The original optimization arguments remain in the opinions.
2. **One abort versus a permanent gate.** At t1 the first PUT is aborted; at t2 the gate is removed; at t3 a snapshot sees no operation; at t4 an automatic retry commits. Every early assertion can pass while the intended no-forward contract is false. A permanent gate plus complete transport coverage and closed browser/tasks removes t4. Fable 5.1's contrary mechanism is explicitly rejected.
3. **Separate reads versus one snapshot.** Read D at n, allow a writer to commit, then read O as applied: independent queries can yield a combination that never represented a valid transaction state. The combined query transaction returns a consistent pair. A fresh snapshot begins only after the named phase acknowledgment; no sleep supplies that causal order.
4. **Socket daemon versus private atomic files.** A daemon can reduce per-observation startup latency but adds readiness, reconnect, replay and cleanup states. One-shot files fit the small durable-observation surface if root's deadlines permit. Reusing an already-present inspected channel is preferable to either new mechanism. The one-second race needs a separate preconnected live witness, not a faster variant of the durable snapshot loop.
5. **Administrator reuse versus explicit independent read privilege.** A seed connection likely has broad visibility but its configuration and role are uninspected. A dedicated task role with column SELECT/BYPASSRLS makes the trust boundary explicit while preserving product permissions. It still has independent read authority; success is not evidence of API authorization. FORCE RLS visibility and known committed-operation checks are mandatory. Roles are cluster-scoped, so local bootstrap and cleanup account for that lifecycle.
